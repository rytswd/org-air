** 🌄 Overview

org-air answers one question well — /what deserves my attention right now?/ — and gets out of the way. It reads your Org files through ~org-ql~, classifies each heading into a handful of meaningful buckets, and renders them with a quiet, legible visual language inspired by [[https://github.com/rougier/nano-emacs][N Λ N O]] and mu4e.

org-air is *two surfaces over your Org files*, sharing one visual language, one keymap core, and one context rail:

| Surface              | Command               | What it is                                                                                                                                                                             |
|----------------------+-----------------------+----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| *GTD dashboard*      | ~M-x org-air~         | A read-first board: capture → glance → process. Items grouped into Inbox / Needs attention / Upcoming / High priority / Stale, with a live calendar, filter, sort, and inbox workflow. |
| *Air project viewer* | ~M-x org-air-project~ | A planning-doc tree for repositories managed with [[https://github.com/withre/air][Air]] — state-grouped documents (~airctl status -Da~ parity), a side-rail inspector, and an in-place doc session.                             |

The philosophy:

- *Org files are the source of truth.* org-air never owns your data; it is a view. There are no agenda buffers, no custom-command DSL, no global state.
- *Independent.* A purpose-built view over ~org-ql~ — no shared global state, no command DSL, nothing to configure before it is useful.
- *Planning-first.* Capture is one keystroke into a single inbox; processing (refile, schedule, tag) is a deliberate, separate step.
- *Quiet by design.* Following nano's "1 + 6" model, colour is used to /mean/ something, sparingly. Overdue looks overdue; everything else stays calm.

** ✨ Features

*Dashboard* (~org-air~)

- Five semantic buckets: *Inbox* (~:inbox:~ capture queue), *Needs attention* (overdue, or active with no schedule/deadline), *Upcoming* (within ~org-air-upcoming-days~), *High priority* (~[#A]~ etc.), *Stale* (untouched for ~org-air-stale-days~).
- A month *calendar* marking scheduled/deadline/created days, with today highlighted — navigate months without leaving the board.
- *Filtering* by tag /and/ free text: a bare token substring-matches the title/origin, a ~#tag~ token matches tags; multi-term combines per ~org-air-filter-match~ (AND / OR, toggled live).
- *Scope* the whole dataset to one tag, group, or file.
- *Sort* within each bucket (date / priority / title / recency).
- One-keystroke *capture* to the inbox, a guided *refile / process* flow, and an *inbox walk* that dispositions items one at a time.
- *Note types*, derived from content: an item with a TODO keyword or a schedule/deadline is a *task* and fills the board; prose *knowledge* notes and date-titled *journal* entries stay off it. Your ~org-todo-keywords~ (custom states, fast keys, logging) are respected — org-air reads your Org exactly as Org does.
- *Staleness* flags only *dated* work that has gone quiet; dateless notes are never “stale”.
- Toggleable *columns* — filename (origin), date/schedule, tags — that reflow and stay aligned.

*Notes & Revisit* (~N~)

- A *Revisit* view resurfaces your evergreen knowledge notes *dustiest-first*, with *orphans* (nothing links to them) and *spaced* (a rotating notes-garden) modes.
- *denote-friendly*: reads ID-filenames, ~#+title~ and ~#+filetags~ and follows ~denote:~ links — with no ~denote~ dependency (keep denote for authoring, or drop it entirely).

*Project viewer* (~org-air-project~)

- ~airctl status -Da~ *parity tree*: documents grouped by state (draft → ready → work-in-progress → complete → dropped), directory, or tag.
- A side-rail *inspector* showing the doc's state, tags, path, and metadata.
- An in-place *doc session*: open a planning doc in the same window, edit it live, and jump back to the tree — with a rail *outline* that follows point.

*Everywhere*

- A *context rail* (calendar / summary / filters / inspector / outline) that pops in inline or out into a native side window.
- ~org-air-outline-mode~ — the outline rail + current-heading highlight as a standalone opt-in minor mode for *any* Org buffer (no Air dependency).
- *evil-awareness*: single-key bindings resolve in motion state; a ~C-c~ leader is state-agnostic. Soft dependency — nothing required.
- *dimmer soft-integration*: org-air's own buffers auto-register as excluded.
- *Scale*: a work-buffer scan, a persistent cache, and inbox-first progressive paint keep *thousands* of files responsive — the board opens fast and never hangs; a cold refresh streams in behind a ~scanning N/M~ progress indicator.

*** Installation

~org-ql~ is on MELPA. Put org-air's ~.el~ files on your ~load-path~, then use the ~use-package~ block below (or a plain ~require~).

**** ~use-package~ (recommended)

#+begin_src emacs-lisp
(use-package org-air
  ;; org-ql (+ Org) is the only hard dependency. Loaded eagerly (not deferred):
  ;; org-air gains little from lazy loading, and eager loading keeps bookmark /
  ;; activities / desktop restore working (see below).
  :custom
  ;; Where to look — files and/or directories (scanned recursively for .org).
  (org-air-files '("~/org/"))
  ;; Where `c' / M-x org-air-capture drops new inbox items.
  (org-air-inbox-file "~/org/inbox.org")
  ;; Classification horizons.
  (org-air-upcoming-days 7)
  (org-air-stale-days 21)
  ;; Board columns (defaults shown): filename OFF, dates + tags ON.
  (org-air-show-origin nil)
  (org-air-show-dates t)
  (org-air-show-tags t)
  ;; Multi-tag filter combinator: `all' (AND) or `any' (OR).
  (org-air-filter-match 'all)
  ;; Keep your own mode-line (`default'), or use the calm nano-style one (`calm').
  (org-air-modeline-style 'default)
  ;; Main-window action leader (rail toggle / outline jump / sort / filter).
  (org-air-leader-key "C-c C-a"))

;; Opt-in: the standalone outline rail in ANY Org buffer.
;;   M-x org-air-outline-mode
;; evil and dimmer integrate automatically — no configuration needed.
#+end_src

**** Plain ~require~

#+begin_src emacs-lisp
(require 'org-ql)                       ; from MELPA
(require 'org-air)                      ; after adding the .el files to load-path
(setq org-air-files '("~/org/"))        ; files and/or directories to scan
#+end_src

~org-air-files~ accepts any mix of files and directories; directories are scanned recursively for ~.org~ (and ~.org.gpg~) files.

To keep whole trees out of the scan, set ~org-air-exclude-regexps~ — a list of regexps matched against each candidate's *absolute path*. A matching *directory* (matched in directory-name form, e.g. ~"/archive/"~ or ~"\\.git/"~) is *pruned* — never even descended — so silencing a big tree costs nothing; a matching file is simply dropped. Exclusion wins over an explicit ~org-air-files~ entry, and your ~org-air-inbox-file~ is never excluded.

#+begin_src emacs-lisp
(setq org-air-exclude-regexps '("/archive/" "\\.git/" "/exports/"))
#+end_src

(setq org-air-files '("/tmp/org-air/")

*** Right-edge glyphs in a fringe-less GUI

org-air sizes every line to the window's /usable/ columns, so with a zero right fringe nothing overflows the visible edge. A few header/legend glyphs (the ~·~ separator, ~…~, ~✕~, and the ~↑ ↓ → ↻~ arrows) are Unicode /East-Asian Ambiguous-width/ characters: Emacs measures them as one column (so the layout is exact), but some fonts /paint/ them two columns wide. If you run a fringe-less GUI and see a stray truncation glyph at the extreme right edge, that is a font/~char-width-table~ mismatch, not an org-air layout bug. The fix is a config one: either pick a font that renders those glyphs single-width, or tell Emacs to treat the ambiguous set as one column (e.g. keep the default ~east-asian-ambiguous~ / ~char-width-table~ mapping, or ~(set-language-environment "UTF-8")~). org-air's own width math already compensates for whatever ~char-width-table~ reports — it is purely the painted advance that can differ.

**** Disabling the default keybindings

The stock bindings are useful, but some users already have their own scheme. One boolean opts out of *every* org-air default key at once:

#+begin_src emacs-lisp
(use-package org-air
  :custom (org-air-use-default-keybindings nil))
#+end_src

With it ~nil~, org-air binds *no keys of its own* — not in any org-air buffer, and not in the files you visit from org-air. Specifically, all of the following are skipped:

- the board, project, rail, and doc-session maps;
- the ~z~ column-toggle prefix, the ~g~ prefix, and the ~C-c C-a~ leader (with its project / doc-session subsets);
- ~org-air-outline-mode~'s rail keys and the calendar day-cell keys (~RET~ / ~mouse-1~);
- the read-only snapshot pane's ~q~;
- the evil overriding-map integration; and
- *crucially, the keys org-air would otherwise add to your OWN files*: the ~org-air-return-key~ in a visited source buffer, and the ~C-c C-q~ / ~quit-window~ close keys in an editable doc-session or indirect pane.

The switch is honoured however you set it: ~use-package~ ~:custom~, a plain ~setq~ before loading org-air, or a runtime ~customize~ (the maps re-sync on the next org-air buffer, and immediately on a ~customize~ set).

The org-air keymaps still *exist* and keep their ~special-mode~ parent, so ~q~ (quit), ~g~ (revert), and scrolling still work, and you own all the org-air *action* keys. To re-add them:

- *The whole stock set* — ~M-x org-air--install-default-keybindings~ (or call it from your config).
- *A subset* — ~define-key~ the command symbols you want into the still-live maps:

#+begin_src emacs-lisp
(with-eval-after-load 'org-air
  (define-key org-air-view-mode-map (kbd "C-n") #'org-air-next-item)
  (define-key org-air-view-mode-map (kbd "C-c r") #'org-air-refresh))
#+end_src

The global entry-point keys you bind yourself (e.g. ~C-c a~ → ~org-air~) are *your* bindings, not defaults, so they are unaffected by this switch.

*** The two views

**** The GTD dashboard — ~M-x org-air~

A sticky header shows the date, a visible-item count, and any active filter or scope. Below it, items sit in five sections, each with an icon and a count badge (badges turn attention-coloured when a section demands it). Each row reads left to right: TODO state, priority cookie, title, a semantic date label, tag chips, and (optionally) an origin breadcrumb.

The capture → process loop is two steps:

1. ~c~ captures a titled note straight to ~org-air-inbox-file~, tagged ~:inbox:~. It appears in the Inbox on the next refresh.
2. ~e~ on any item opens the *edit transient*: set tags / category / schedule / deadline / todo / priority / a dated LOGBOOK note (~n~) (applied *in place*, no move), optionally pick a destination to *refile* (creating nested headings / a new file with synthesised Air frontmatter as needed) — one ~RET~ confirms everything.

~I~ walks the whole Inbox one item at a time with single-key dispositions.

*org-air-capture vs org-capture.* ~c~ (~M-x org-air-capture~) is a deliberately small, zero-config front door: it appends a fixed ~* TODO … :inbox:~ entry with a ~CREATED~ stamp — exactly the shape the Inbox bucket and triage flow expect — so capture works the moment you install org-air, with no template to write and no capture buffer. It is *not* a replacement for ~org-capture~ and does nothing ~org-capture~ can't; if you already live in ~org-capture~, the equivalent template is:

#+begin_src emacs-lisp
(add-to-list 'org-capture-templates
  '("i" "org-air inbox" entry (file org-air-inbox-file)
    "* TODO %? :inbox:\n:PROPERTIES:\n:CREATED: %U\n:END:\n" :empty-lines 1))
#+end_src

Anything tagged ~:inbox:~ in ~org-air-inbox-file~ feeds the board's Inbox and the triage flow — however you put it there.

**** The Air project viewer — ~M-x org-air-project~

For repositories planned with [[https://github.com/withre/air][Air]], the project viewer renders the planning docs as a state-grouped tree (parity with ~airctl status -Da~), sortable and filterable, with a side-rail inspector. ~RET~ opens a doc in a same-window *session*: you edit the real file, the rail shows a live outline that follows point, and ~C-c C-q~ returns you to the tree. org-air the package has no runtime dependency on Air or ~airctl~.

*** ~org-air-outline-mode~

The doc-session outline rail — a heading list plus a current-heading highlight that follows point — is also a *standalone, opt-in minor mode* usable in /any/ Org buffer:

#+begin_src emacs-lisp
M-x org-air-outline-mode
#+end_src

Enabling it in an ~org-mode~ buffer pops the org-air context rail showing that buffer's headings (via the same rail machinery the doc session uses) and follows point with the current-heading highlight. It has *no dependency* on ~org-air-project~, org-ql, or airctl — a light, generic scaffold. It is off by default and a no-op outside ~org-mode~. Choose inline vs. side-window placement with ~org-air-outline-rail-placement~.

*** Bookmarks, activities & desktop restore

The board, project viewer, and Revisit buffers support Emacs's ~bookmark~ system, so ~bookmark-set~ (~C-x r m~), ~bookmark-jump~, [[https://github.com/alphapapa/activities.el][activities.el]], burly, and ~desktop~ can save and rebuild them (view, scope, filter, sort, and point are captured; the handler reopens the view cache-first, no blocking rescan).

This works out of the box with the recommended (eagerly-loaded) setup above — and with any package-manager install, whose generated autoloads register the handlers. The one case to watch: if you *defer* org-air's load (use-package ~:commands~/~:defer~ from ~load-path~), a bookmark replayed at startup can fire before org-air has loaded, and the handler won't be defined yet. org-air gains little from deferral, so eager loading is recommended; but if you do defer, register the three handler autoloads (or ~(require 'org-air)~ eagerly):
