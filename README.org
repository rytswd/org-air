** 🌄 Overview

org-air answers one question well — /what deserves my attention right now?/ — and gets out of the way. It reads your Org files through ~org-ql~, classifies each heading into a handful of meaningful buckets, and renders them with a quiet, legible visual language inspired by [[https://github.com/rougier/nano-emacs][N Λ N O]] and mu4e.

org-air is *two surfaces over your Org files*, sharing one visual language, one keymap core, and one context rail:

| Surface              | Command               | What it is                                                                                                                                                                             |
|----------------------+-----------------------+----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| *GTD dashboard*      | ~M-x org-air~         | A read-first board: capture → glance → process. Items grouped into Inbox / Overdue / Upcoming / High priority / Needs attention / Untracked, with a live calendar, filter, sort, and inbox workflow. |
| *Air project viewer* | ~M-x org-air-project~ | A planning-doc tree for repositories managed with [[https://github.com/withre/air][Air]] — state-grouped documents (~airctl status -Da~ parity), a side-rail inspector, and an in-place doc session.                             |

The philosophy:

- *Org files are the source of truth.* org-air never owns your data; it is a view. There are no agenda buffers, no custom-command DSL, no global state.
- *Independent.* A purpose-built view over ~org-ql~ — no shared global state, no command DSL, nothing to configure before it is useful.
- *Planning-first.* Capture is one keystroke into a single inbox; processing (refile, schedule, tag) is a deliberate, separate step.
- *Quiet by design.* Following nano's "1 + 6" model, colour is used to /mean/ something, sparingly. Overdue looks overdue; everything else stays calm.

** ✨ Features

*Dashboard* (~org-air~)

- Six semantic buckets, in board order: *Inbox* (~:inbox:~ capture queue), *Overdue* (a scheduled/deadline date already past), *Upcoming* (a date within ~org-air-upcoming-days~), *High priority* (~[#A]~ etc.), *Needs attention* (no update for longer than its priority allows — see [[#needs-attention][Needs attention]]), and the conditional *Untracked* (no ~SCHEDULED~, no ~DEADLINE~ and no recorded history — see [[#untracked][Untracked]]; hidden when empty). Buckets are *not* exclusive: an overdue ~[#A]~ that has gone quiet appears in all three of its sections.
- A month *calendar* marking scheduled/deadline/created days, with today highlighted — navigate months without leaving the board.
- The date cell is a *proximity heat-ramp* on *every* date slot (deadline / scheduled / neutral): *overdue* reads red, *today* orange, *tomorrow* a blend between today and this-week, anything *2–6 days out* a calmer amber, and a date *a week or more out* keeps its slot colour — warmer means nearer, so urgency is legible at a glance (text /and/ svg pill).
- A *single-day view* — ~RET~ a calendar day (or ~g d~ to jump to any date) focuses that day's items grouped *Deadline / Scheduled / Logged*; ~<~ / ~>~ step to the adjacent day and ~q~ returns to the board. Rows wear your TODO-keyword faces (~org-air-keyword-face-source~) and re-sort by time / keyword / priority / title.
- *Filtering* by tag /and/ free text /and/ date/status /and/ location: a bare token substring-matches the title/origin, a ~#tag~ token matches tags; ~is:overdue~ / ~is:upcoming~ / ~is:attention~ / ~is:untracked~ / ~is:nodate~ / ~is:hipri~ / ~is:done~ / ~is:backlog~ (the retired ~is:stale~ still parses, as an alias for ~is:attention~ — selecting a different set than it did before the recency model), a ~todo:KEYWORD~ keyword-identity token, and ~due:7d~-style windows (with ~scheduled:~ / ~deadline:~ twins) match the planning and status slots; a ~path:tasks/re/air~ token scopes the board/day/review to a directory subtree of your source files (segment-aware — ~path:re~ hits ~…/tasks/re/…~ but not a sibling ~…/tasks/restore~ — and matched relative to your ~org-air-files~ root, no tagging required); multi-term combines per ~org-air-filter-match~ (AND / OR, toggled live).
- *Backlog* (~b~): ack-and-defer a not-urgent task off the attention surfaces onto a Backlog lens via an org-native ~:backlog:~ tag — still trackable (Notes, day view, calendar, ~is:backlog~/~#backlog~), never nagging. The normal board keeps a compact *Backlog N* header/count and hides its rows until ~TAB~; an exact ~is:backlog~ lens reveals them automatically.
- *Scope* the whole dataset to one tag, group, or file.
- *Sort* within each bucket (date / priority / title / recency). ~date~ is per-section "worst first by the number the rows print"; ~recency~ is the /measured/ clock — the same stamps Needs attention reads, never a plan and never a file's mtime — with headings org-air has never measured ranked last.
- One-keystroke *capture* to the inbox, a guided *refile / process* flow, and an *inbox walk* that dispositions items one at a time.
- *Note types*, derived from content: an item with a TODO keyword or a schedule/deadline is a *task* and fills the board; prose *knowledge* notes and date-titled *journal* entries stay off it. Your ~org-todo-keywords~ (custom states, fast keys, logging) are respected — org-air reads your Org exactly as Org does. Prefer keyword-only tasks? ~(setq org-air-task-requires-todo t)~ narrows the task signal to the TODO keyword alone, so keyword-less scheduled routines (~* Water plants  SCHEDULED: <… ++2w>~) leave the task sections — they keep their day-view row and calendar mark, stay reachable via Notes/Revisit, and any single one comes back with a ~:task:~ tag or ~ORG_AIR_TYPE~ override.
- *Needs attention is age-based, never date-based.* Nothing has to be scheduled to stay off it, and scheduling something does not buy it an exemption — see [[#needs-attention][Needs attention]]. Its clock is the heading's *own* recorded history, never its file's modification time, so org-air's own writes cannot hide a row and nothing arrives in a burst.
- Toggleable *columns* — filename (origin), date/schedule, tags — that reflow and stay aligned.

*Notes & Revisit* (~N~)

- A *Revisit* view resurfaces your evergreen knowledge notes *dustiest-first*, with *orphans* (nothing links to them) and *spaced* (a rotating notes-garden) modes.
- *denote-friendly*: reads ID-filenames, ~#+title~ and ~#+filetags~ and follows ~denote:~ links — with no ~denote~ dependency (keep denote for authoring, or drop it entirely).

*Review* (~W~)

- A *retrospective* over a period: items *Completed*, *Time invested* (clocked hours, rolled up by day / tag / directory / origin — ~f~ cycles the basis), *Started*, *Carried over*, and *Dropped* (shown only when there is an abandonment to own). ~<~ / ~>~ / ~.~ move by one unit of the active range; ~+~ / ~-~ widen / narrow and ~m~ cycles the range ladder (week → fortnight → month → quarter → year, per ~org-air-review-ranges~).
- Mirror rows (an item DONE-logged across several files) collapse to one row per real completion, and an over-long clock interval is quarantined as *suspect* and excluded — so every total honestly describes what is shown.

*Project viewer* (~org-air-project~)

- ~airctl status -Da~ *parity tree*: documents grouped by state (draft → ready → work-in-progress → complete → out → off → dropped), directory, or tag.
- A side-rail *inspector* showing the doc's state, tags, path, and metadata.
- An in-place *doc session*: open a planning doc in the same window, edit it live, and jump back to the tree — with a rail *outline* that follows point.

*Everywhere*

- A *context rail* (calendar / summary / filters / inspector / outline) that pops in inline or out into a native side window.
- ~org-air-outline-mode~ — the outline rail + current-heading highlight as a standalone opt-in minor mode for *any* Org buffer (no Air dependency).
- *evil-awareness*: single-key bindings resolve in motion state; a ~C-c~ leader is state-agnostic. Soft dependency — nothing required.
- *dimmer soft-integration*: org-air's own buffers auto-register as excluded.
- *Scale*: a work-buffer scan, a persistent cache, and inbox-first progressive paint keep *thousands* of files responsive — the board opens fast and never hangs; a cold refresh streams in behind a ~scanning N/M~ progress indicator.

*** Installation

~org-ql~ is on MELPA. Put org-air's ~.el~ files on your ~load-path~, then use the ~use-package~ block below (or a plain ~require~).

**** ~use-package~ (recommended)

#+begin_src emacs-lisp
(use-package org-air
  ;; org-ql (+ Org) is the only hard dependency. Loaded eagerly (not deferred):
  ;; org-air gains little from lazy loading, and eager loading keeps bookmark /
  ;; activities / desktop restore working (see below).
  :custom
  ;; Where to look — files and/or directories (scanned recursively for .org).
  (org-air-files '("~/org/"))
  ;; Where `c' / M-x org-air-capture drops new inbox items.  Leave it unset
  ;; (nil) to derive it from `org-air-files' — see "The inbox lives inside
  ;; the scan set" below.  It must be a file the scan can see.
  (org-air-inbox-file "~/org/inbox.org")
  ;; Classification horizons.
  (org-air-upcoming-days 7)
  ;; Needs attention: days of NO UPDATE per priority before an item surfaces.
  ;; #A gets 3 days' grace (High priority already shows it every repaint);
  ;; the nil key is "no priority cookie".  Set a letter to 0 to surface it
  ;; unconditionally.
  (org-air-attention-days '((?A . 3) (?B . 7) (?C . 14)
                            (?D . 30) (?E . 30) (nil . 30)))
  ;; Board columns (defaults shown): filename OFF, dates + tags ON.
  (org-air-show-origin nil)
  (org-air-show-dates t)
  (org-air-show-tags t)
  ;; Multi-tag filter combinator: `all' (AND) or `any' (OR).
  (org-air-filter-match 'all)
  ;; Keep your own mode-line (`default'), or use the calm nano-style one (`calm').
  (org-air-modeline-style 'default)
  ;; Main-window action leader (rail toggle / outline jump / sort / filter).
  (org-air-leader-key "C-c C-a"))

;; Opt-in: the standalone outline rail in ANY Org buffer.
;;   M-x org-air-outline-mode
;; evil and dimmer integrate automatically — no configuration needed.
#+end_src

**** Plain ~require~

#+begin_src emacs-lisp
(require 'org-ql)                       ; from MELPA
(require 'org-air)                      ; after adding the .el files to load-path
(setq org-air-files '("~/org/"))        ; files and/or directories to scan
;; org-air-inbox-file is left nil here on purpose: it then derives to
;; ~/org/inbox.org — inside the scan set, so captures show on the board.
#+end_src

~org-air-files~ accepts any mix of files and directories; directories are scanned recursively for ~.org~ files.

***** Encrypted files are listed but *not* read

~.org.gpg~ files under a scanned directory are *enumerated* and then *skipped*, with the reason ~encrypted~. A background scan must never block on a pinentry prompt, so org-air never decrypts a file on your behalf — which means an encrypted journal contributes *nothing* to the board unless you already have it open and decrypted in a buffer (then it is scanned in place, like any live buffer).

This is deliberate, and it is no longer silent: a scan that skipped anything echoes one line naming the count and the reasons, and ~M-x org-air-scan-report~ lists every skipped file with an explanation. Set ~org-air-report-skipped-files~ to ~nil~ to silence the echo (the report is unaffected).

***** The inbox lives inside the scan set

~c~ / ~M-x org-air-capture~ writes to ~org-air-inbox-file~; the board reads ~org-air-files~. If those two disagree the note is written correctly *and* the board honestly reports Inbox zero — a silent loss. org-air closes that from both ends:

- ~org-air-inbox-file~ defaults to ~nil~, which *derives* the inbox from ~org-air-files~: ~inbox.org~ inside the first configured directory (or beside the first configured file). With ~(setq org-air-files '("~/org/"))~ and nothing else, ~c~ captures to ~~/org/inbox.org~ and the item appears in the Inbox on the next refresh.
- If you *do* set ~org-air-inbox-file~ and it lands outside ~org-air-files~, ~c~ *refuses* with a ~user-error~ naming the fix, before writing anything. It never creates a file the board cannot see.

To keep whole trees out of the scan, set ~org-air-exclude-regexps~ — a list of regexps matched against each candidate's *absolute path*. A matching *directory* (matched in directory-name form, e.g. ~"/archive/"~ or ~"\\.git/"~) is *pruned* — never even descended — so silencing a big tree costs nothing; a matching file is simply dropped. Exclusion wins over an explicit ~org-air-files~ entry, and your ~org-air-inbox-file~ is never excluded.

#+begin_src emacs-lisp
(setq org-air-exclude-regexps '("/archive/" "\\.git/" "/exports/"))
#+end_src

*** Right-edge glyphs in a fringe-less GUI

org-air sizes every line to the window's /usable/ columns, so with a zero right fringe nothing overflows the visible edge. A few header/legend glyphs (the ~·~ separator, ~…~, ~✕~, and the ~↑ ↓ → ↻~ arrows) are Unicode /East-Asian Ambiguous-width/ characters: Emacs measures them as one column (so the layout is exact), but some fonts /paint/ them two columns wide. If you run a fringe-less GUI and see a stray truncation glyph at the extreme right edge, that is a font/~char-width-table~ mismatch, not an org-air layout bug. The fix is a config one: either pick a font that renders those glyphs single-width, or tell Emacs to treat the ambiguous set as one column (e.g. keep the default ~east-asian-ambiguous~ / ~char-width-table~ mapping, or ~(set-language-environment "UTF-8")~). org-air's own width math already compensates for whatever ~char-width-table~ reports — it is purely the painted advance that can differ.

~u~ undoes the most recent board edit (a bounded recent-edits ring — ~?~ lists what ~u~ will undo; refiles and archives are named but not auto-reverted, since a source-side undo beside the moved copy would leave a duplicate). ~U~ re-applies the edit ~u~ just reverted; a fresh edit clears the redo side (refiles and archives are never redoable).

~m~ builds a live source-heading selection for bulk work. Marks survive repaint, filter, sort, scope and section folds in the current board buffer; hidden marks remain targets and the banner reports total/shown counts. With marks active, ~b~ applies one set-all backlog operation and ~t~ prompts once to add one shared tag; ~M~ clears the selection. Other item mutations stay single-item and ask you to press ~M~ first. Marks are not saved in the scan cache or bookmarks, and do not survive killing the board buffer.

Marks are validated, never guessed. A mark records the exact source heading you selected; if that heading has moved, changed its title or effective tags, or vanished, the mark is /pruned/ — never silently re-pointed at whatever now sits at its old position. A refresh reports that as ~Pruned N stale marked item(s)~; a marked ~b~/~t~ reports it as ~N failed — run g r~ and writes nothing for those marks. A marked write is honest about every bucket in one line — what it wrote, ~N ineligible remains marked~ (a heading that left the board, e.g. because you finished it elsewhere) and ~N failed — run g r~.

One case needs a stricter rule. Two headings in the /same file/ that share a title /and/ the same effective tags — a recurring ~Standup~, a templated ~Weekly review~ — are indistinguishable to org-air, which never re-reads your files to derive a mark's identity and never writes an ~ID~ property into them. A mark on such a heading is therefore also validated against that file's modification time, so *any* change to that file on disk invalidates it, even a change to an unrelated heading. Org-air's own marked write is not foreign change; org-air's own ~u~/~U~ currently is, so an undo can drop such a mark. Re-mark and continue: org-air would rather lose a selection than write a heading you did not pick.

***** Needs attention: recency × priority
:PROPERTIES:
:CUSTOM_ID: needs-attention
:END:

*Needs attention shows work that has gone quiet for longer than its priority allows.* Nothing else. It asks one question — /when was this last touched?/ — and compares the answer against a per-priority threshold:

| Priority        | Surfaces after     |
|-----------------+--------------------|
| ~[#A]~          | 3 days of no update  |
| ~[#B]~          | 7 days of no update  |
| ~[#C]~          | 14 days of no update |
| ~[#D]~ / ~[#E]~ | 30 days of no update |
| no cookie       | 30 days of no update |

The table is the ~org-air-attention-days~ defcustom (an alist from the priority *letter* to days; the ~nil~ key is "no priority cookie", and ~org-air-attention-default-days~ is the last resort for a letter you have not listed). It is read live at repaint time — retune it with ~setq~ and the next repaint obeys, with no rescan.

*What counts as an update.* The most recent /inactive/ Org timestamp in the heading's own body: LOGBOOK state changes and notes, clock-outs, ~CLOSED:~ and ~:CREATED:~, plus any ~[2026-06-15 Mon]~ stamp you typed there yourself. Turn on ~org-log-done~ / ~org-log-into-drawer~ and org-air simply reads the trail Org already writes.

/Own body/ means exactly that — *the clock does not read your sub-tasks.* A parent ~TODO~ whose children are being worked has no record of its own, so it ages as if untouched (and, if it carries no date either, it lands in [[#untracked][Untracked]] rather than here). A child's stamp belongs to the child's row. And /any/ inactive stamp in that body counts, wherever it sits: inside property drawers and non-LOGBOOK drawers, in comment lines, even inside a ~#+begin_example~ block quoting a log line. Two spellings are deliberately excluded (below); everything else you write in the body is read as "something happened here".

*Repeaters need Org's repeat logging.* A routine you complete diligently every week gains a record only if Org writes one — ~(setq org-log-repeat 'time)~ (Org's default) keeps a ~:LAST_REPEAT:~ / state-change trail. With repeat logging off, a repeater is never /aged/ at all: it stays dated, so it is not hidden (Upcoming and Overdue still show it on its own date), but this section will never have a number for it. "org-air reads the trail Org already writes" quietly assumes Org is configured to write one.

*What does not count.* ~SCHEDULED~, ~DEADLINE~ and active ~<timestamps>~ are /plans/, not updates — they neither start nor stop this clock. So *nothing has to be scheduled to stay off this section, and scheduling something buys it no exemption*: a task planned for next month that nobody has touched in sixty days still surfaces, and a brand-new dateless capture does not. Two spellings that used to slip through no longer do: a planning date written in the /inactive/ form (~DEADLINE: [2026-06-14 Sun]~ — Org accepts it) is still a plan, and the old date quoted inside a log line (~- Rescheduled from "[2026-06-14 Sun]" on [2026-06-01 Mon]~) is the plan you abandoned, not the moment you wrote the note. Only ~CLOSED:~ counts among the planning keywords, because it records something that happened.

*The clock is the heading's own history — never its file's.* If a heading has no recorded history at all, org-air does not age it here at all. It does /not/ fall back to the file's modification time, which is a fact about the file answering a question about the heading. That fallback used to be how this section treated historyless work, and it had three consequences worth naming plainly:

- *org-air's own writes reset it.* Pressing ~t~, pressing ~b~, refiling, capturing and archiving all rewrite the source file — so acting on /one/ row re-hid every historyless row in that file for another full threshold.
- *For a one-file setup it was all-or-nothing.* If all your tasks live in one ~tasks.org~, every historyless heading in it was hidden while you were working in the file, and every one appeared the moment the whole file went quiet.
- *Recovery was a burst.* Those headings arrived on the same day, carrying the /same/ number, ranked above every heading whose age had actually been measured.

Work with no recorded history is not dropped for this. If it has no date either, it gets a row of its own — see [[#untracked][Untracked]] below. And when a heading's age genuinely cannot be computed the item does *not* surface here, whatever its priority: a threshold is a claim about elapsed time, and org-air will not claim time it never measured. An ~[#A]~ in that state is still on the board, in High priority. (A threshold of ~0~ is the deliberate exception: it surfaces regardless, because at ~0~ there is nothing to measure.)

*Why the row is legible.* In this section the date cell carries the /reason/, not a date: ~12d quiet~ — the age that crossed the threshold. Every number here is a fact about the heading it sits next to; the section prints no estimates. The rail inspector spells it out as ~quiet 12d / 7d~ (age over threshold) next to an ~Updated~ line naming the stamp it read. (Set a priority's threshold to ~0~ and its rows read ~always~ instead: they surface unconditionally, so there is no age to report.) The trade is worth knowing: a row that is /neither/ overdue nor inside the Upcoming horizon shows *no date anywhere on the board* — its dates are one keystroke away in the rail inspector, which always lists both slots. (Absurd numbers are clamped for legibility, not for truth: a heading whose date is a typo reads ~10y+ quiet~ rather than ~739781d quiet~, and still sorts on the real number.)

*Overdue is a separate section*, above Upcoming: a missed date is a different problem from a quiet item and gets its own rows, its own ~▲~ badge and its own ~is:overdue~ filter. It is ordered worst-first by the very number its rows print, including the awkward case where a task is late by its /schedule/ while its deadline is still ahead. Sections *overlap by design* — an overdue ~[#A]~ that has been quiet a month appears in Overdue, High priority /and/ Needs attention, once in each.

*Stale is retired.* Its rule ("dated work that has gone quiet") is exactly what Needs attention now does for every item, dated or not, so the section and the ~org-air-stale-days~ knob are gone. Filter with ~is:attention~; a saved ~is:stale~ still parses as an alias for it, so old bookmarks keep working — but note that they now select a /different set/: ~is:stale~ used to mean "dated /and/ quiet" and now means the aging rule, which ignores dates entirely. The bookmark still renders a board; it simply answers a different question than the day you saved it.

***** Untracked: work org-air cannot rank
:PROPERTIES:
:CUSTOM_ID: untracked
:END:

*Untracked holds the headings org-air knows nothing about: no plan and no record.* No ~SCHEDULED~ and no ~DEADLINE~ — and no LOGBOOK entry, no ~CLOSED:~, no ~:CREATED:~, no body stamp either. A bare ~* TODO Cancel the unused SaaS seats~ typed under an ~Admin~ heading is the canonical member.

"No plan" means precisely the two slots the date sections read. A heading whose only date is a bare active ~<2026-06-14 Sun>~ in its /body/ belongs here: Overdue and Upcoming never look at body timestamps, so without this section such a heading had no row at all — not even with the stamp yesterday.

It exists because the two rules above are honest but incomplete. A dated heading is shown by Overdue or Upcoming when its date arrives; a heading with history is aged by Needs attention. A heading with neither has no clock to age off and no date to be due on — and before this section it simply had no row anywhere. Together the sections now cover everything:

#+begin_quote
*Every board-active, non-deferred task has a row somewhere — unless (a) its own plan puts it beyond the Upcoming horizon, or (b) org-air measured you touching it more recently than its priority's threshold. There is no third case.*
#+end_quote

Both exemptions are promises rather than hiding places: (a) comes back on its own date, (b) comes back when the heading goes quiet.

*It is a statement, not an accusation.* It does not claim the work is late or neglected; it says org-air cannot rank it. The section sits last of the task sections, wears a quiet ~◌~ icon (never the attention badge colour), shows at most four rows before folding, and is hidden entirely when empty. This is deliberately not the pre-recency rule coming back — that rule put undated work in the /alarm/ lane, ranked above genuinely overdue work, with no exit but inventing a date or tagging ~:backlog:~.

*Per heading it can only ever shrink* — one date, or one stamp from ~org-log-done~, and a heading leaves it for good. The /section/ is another matter, and two facts bound it honestly. Anything you capture with ~c~ never enters it at all: org-air's own capture writes a ~:CREATED:~ stamp, so Untracked is fed only by headings typed into files by hand. And for a genuine someday/maybe list neither exit will ever happen — ~Plan a sabbatical~ is not going to acquire a date or a log entry. *~b~ is the third answer*: it moves the item to the *Backlog* lens below, which is a real choice ("I know, and I am fine with it"), not a way of gaming the board.

*The one number it prints is marked as an estimate.* Where the section can say something it does: a row reads ~~210d quiet~ when the /file/ has not changed in 210 days. Every edit to a heading is an edit to its file, so that is a sound *lower* bound — "quiet for at least this long" — and the leading ~~~ says the number is file-level, not heading-level. When the bound is zero or unknown (the file changed today) the row reads ~no history~, because a fresh file says nothing at all about a heading with no history in it. The rail inspector says the same thing in words: ~Untracked · no plan, no record · file quiet ~210d~.

*So the order is a fact about your FILES, not your headings*, and it is capped for that reason. Rows sort longest-bound first (~no history~ last) — which means your /coldest file's/ rows come first — but while the section is folded *no single file may take more than two of the four visible rows*. Without that quota one cold ~someday.org~ owned the whole section and the bare admin ~TODO~s in the file you edit daily sat behind the fold. ~TAB~ expands to every member in the full longest-bound-first order.

*An unprocessed capture is not in here.* A heading in your inbox has no plan and no record /by definition/, so the row would only repeat what the Inbox row above already says — and Inbox is the section with a verb for it (process it). Inbox membership is unconditional, so nothing is hidden by this: the item keeps its row, one section up.

Filter it by name with ~is:untracked~. That is deliberately /not/ a synonym for ~is:nodate~, and neither one contains the other: an undated heading with a LOGBOOK trail answers ~is:nodate~ but not ~is:untracked~ (org-air knows when you last touched it), and a heading whose only date is a body ~<timestamp>~ answers ~is:untracked~ but not ~is:nodate~ (it /is/ dated — it marks a day on the calendar — but no date section will ever show it).

*Keyword-less prose is not in here.* With the default ~org-air-plain-heading-type~ a heading with no TODO keyword is a knowledge note and never reaches the task sections at all. Untracked holds tasks.

*The one-line configuration that empties it.* Turn on Org's own logging and org-air reads the trail Org writes:

#+begin_src elisp
(setq org-log-done 'time
      org-log-into-drawer t
      org-log-reschedule 'time
      org-log-redeadline 'time)
#+end_src

***** Backlog: ack-and-defer (~b~)

Some tasks are real but not urgent — a placeholder heading you will fill in /anytime/. ~b~ (~org-air-item-backlog~) is the third verb between "date it" (a lie) and "drop the keyword" (no longer a task): it toggles an org-native ~:backlog:~ tag (~org-air-backlog-tag~, default ~"backlog"~) on the item at point — one keystroke, no prompt — and presses again to un-defer. A backlogged item routes /off/ the four task sections and the Inbox into a single *Backlog* lens at the bottom of the board, while staying fully trackable elsewhere: Notes, all-items, the day view and the calendar (if dated) are untouched. (Before the recency model, ~b~ was also the only escape from a Needs-attention section that surfaced /every/ dateless task; it is now a genuine choice rather than a way to silence the board.)

On a normal board the Backlog lens is *header-only*: ~Backlog N~ and its Summary count remain visible, but item/fold rows stay hidden until ~TAB~ expands all currently visible backlog rows; a second ~TAB~ collapses them. Expansion survives ordinary repaint/refresh in the live buffer and bookmark expansion state. An exact ~is:backlog~ filter forces the section and reveals it even when ~org-air-show-backlog-section~ is nil; raw ~#backlog~ does not auto-reveal. Outside that explicit lens, setting the show knob nil removes both the ordinary section and ordinary Summary row.

Filter with ~is:backlog~ (exactly the deferred set) or the raw ~#backlog~ tag (its superset — also done/archived carriers); ~b~ is also a ~[b]~ defer disposition in the guided Inbox walk (~I~). A single unmarked ~b~ keeps focus local on the successor (or previous final row), never following the moved heading into its new section. With marks active it uses set-all semantics: if every eligible mark is already backlog, all turn off; otherwise all turn on. The write is in-place and undoable, so one ~u~/~U~ round-trips the whole marked command.

**** Disabling the default keybindings

The stock bindings are useful, but some users already have their own scheme. One boolean opts out of *every* org-air default key at once:

#+begin_src emacs-lisp
(use-package org-air
  :custom (org-air-use-default-keybindings nil))
#+end_src

With it ~nil~, org-air binds *no keys of its own* — not in any org-air buffer, and not in the files you visit from org-air. Specifically, all of the following are skipped:

- the board, project, rail, and doc-session maps;
- the ~z~ column-toggle prefix, the ~g~ prefix, and the ~C-c C-a~ leader (with its project / doc-session subsets);
- ~org-air-outline-mode~'s rail keys and the calendar day-cell keys (~RET~ / ~mouse-1~);
- the read-only snapshot pane's ~q~;
- the evil overriding-map integration; and
- *crucially, the keys org-air would otherwise add to your OWN files*: the ~org-air-return-key~ in a visited source buffer, and the ~C-c C-q~ / ~quit-window~ close keys in an editable doc-session or indirect pane.

The switch is honoured however you set it: ~use-package~ ~:custom~, a plain ~setq~ before loading org-air, or a runtime ~customize~ (the maps re-sync on the next org-air buffer, and immediately on a ~customize~ set).

The org-air keymaps still *exist* and keep their ~special-mode~ parent, so ~q~ (quit), ~g~ (revert), and scrolling still work, and you own all the org-air *action* keys. To re-add them:

- *The whole stock set* — ~M-x org-air--install-default-keybindings~ (or call it from your config).
- *A subset* — ~define-key~ the command symbols you want into the still-live maps:

#+begin_src emacs-lisp
(with-eval-after-load 'org-air
  (define-key org-air-view-mode-map (kbd "C-n") #'org-air-next-item)
  (define-key org-air-view-mode-map (kbd "C-c r") #'org-air-refresh))
#+end_src

If you bind command symbols by hand, note one rename: the deadline verb on ~d~ is ~org-air-item-set-deadline~ (it used to be ~org-air-item-deadline~, which is also the name of an internal data accessor — sharing the name meant any indirect call reached the wrong one). Keys, help text and behaviour are unchanged; only ~M-x~ completion and an explicit ~define-key~ / ~global-set-key~ on the old symbol need the new name. No alias is provided, deliberately — an alias would re-create the clash.

The global entry-point keys you bind yourself (e.g. ~C-c a~ → ~org-air~) are *your* bindings, not defaults, so they are unaffected by this switch.

**** org-air commands only act on org-air buffers

Every org-air verb states its surface up front. Run a board verb (~M-x org-air-refresh~, ~M-x org-air-calendar-today~, …) from one of *your* Org files and it declines with a plain message — ~Not in an org-air board (run `M-x org-air')~ — *before* any prompt, and without touching the buffer. The same holds for the project / review / revisit / rail verbs on their own surfaces.

The surface-scoped commands are also hidden from ~M-x~ completion outside their mode (Emacs' ~interactive~ mode scoping), so ~M-x org-air-~ in an ordinary Org buffer offers only the entry points you can actually use: ~org-air~, ~org-air-capture~, ~org-air-project~, ~org-air-review~, ~org-air-revisit~, ~org-air-goto-date~, ~org-air-process-inbox~, ~org-air-scan-report~, ~org-air-help~ and the return verbs. They remain callable by full name if you want them; the refusal is what protects you, the scoping just keeps the menu honest.

*** The two views

**** The GTD dashboard — ~M-x org-air~

A sticky header shows the date, a visible-item count, and any active filter or scope. Below it, items sit in five fixed sections — *Inbox*, *Overdue*, *Upcoming*, *High priority*, *Needs attention* — followed by the conditional *Untracked* section (at most four rows, at most two from any one file) and the optional *Notes* and *Backlog* lenses last, each with an icon and a count badge (Inbox, Overdue and Needs attention badges turn attention-coloured when they are non-empty; Untracked never does — it is a statement, not an alarm). Each row reads left to right: TODO state, priority cookie, title, a semantic date label, tag chips, and (optionally) an origin breadcrumb.

The capture → process loop is two steps:

1. ~c~ captures a titled note straight to ~org-air-inbox-file~, tagged ~:inbox:~. It appears in the Inbox on the next refresh.
2. ~e~ on any item opens the *edit transient*: set tags / category / schedule / deadline / todo / priority / a dated LOGBOOK note (~n~) (applied *in place*, no move), optionally pick a destination to *refile* (creating nested headings / a new file with synthesised Air frontmatter as needed) — one ~RET~ confirms everything.

~I~ walks the whole Inbox one item at a time with single-key dispositions.

*org-air-capture vs org-capture.* ~c~ (~M-x org-air-capture~) is a deliberately small, zero-config front door: it appends a fixed ~* TODO … :inbox:~ entry with a ~CREATED~ stamp — exactly the shape the Inbox bucket and triage flow expect — so capture works the moment you install org-air, with no template to write and no capture buffer. It is *not* a replacement for ~org-capture~ and does nothing ~org-capture~ can't; if you already live in ~org-capture~, the equivalent template is:

#+begin_src emacs-lisp
(add-to-list 'org-capture-templates
  '("i" "org-air inbox" entry (file org-air-inbox-file)
    "* TODO %? :inbox:\n:PROPERTIES:\n:CREATED: %U\n:END:\n" :empty-lines 1))
#+end_src

Anything tagged ~:inbox:~ in ~org-air-inbox-file~ feeds the board's Inbox and the triage flow — however you put it there.

**** The Air project viewer — ~M-x org-air-project~

For repositories planned with [[https://github.com/withre/air][Air]], the project viewer renders the planning docs as a state-grouped tree (parity with ~airctl status -Da~), sortable and filterable, with a side-rail inspector. ~RET~ opens a doc in a same-window *session*: you edit the real file, the rail shows a live outline that follows point, and ~C-c C-q~ returns you to the tree. org-air the package has no runtime dependency on Air or ~airctl~.

*** ~org-air-outline-mode~

The doc-session outline rail — a heading list plus a current-heading highlight that follows point — is also a *standalone, opt-in minor mode* usable in /any/ Org buffer:

#+begin_src emacs-lisp
M-x org-air-outline-mode
#+end_src

Enabling it in an ~org-mode~ buffer pops the org-air context rail showing that buffer's headings (via the same rail machinery the doc session uses) and follows point with the current-heading highlight. It has *no dependency* on ~org-air-project~, org-ql, or airctl — a light, generic scaffold. It is off by default and a no-op outside ~org-mode~. Choose inline vs. side-window placement with ~org-air-outline-rail-placement~.

*** Bookmarks, activities & desktop restore

The board, project viewer, and Revisit buffers support Emacs's ~bookmark~ system, so ~bookmark-set~ (~C-x r m~), ~bookmark-jump~, [[https://github.com/alphapapa/activities.el][activities.el]], burly, and ~desktop~ can save and rebuild them (view, scope, filter, sort, and point are captured; the handler reopens the view cache-first, no blocking rescan).

This works out of the box with the recommended (eagerly-loaded) setup above — and with any package-manager install, whose generated autoloads register the handlers. The one case to watch: if you *defer* org-air's load (use-package ~:commands~/~:defer~ from ~load-path~), a bookmark replayed at startup can fire before org-air has loaded, and the handler won't be defined yet. org-air gains little from deferral, so eager loading is recommended; but if you do defer, register the three handler autoloads (or ~(require 'org-air)~ eagerly):

#+begin_src emacs-lisp
(autoload 'org-air-view-bookmark-jump    "org-air-view")
(autoload 'org-air-project-bookmark-jump "org-air-project")
(autoload 'org-air-revisit-bookmark-jump "org-air-revisit")
#+end_src
