* R29-1 — fringe-less GUI x-overflow: one width term diverges on the side-window path [BUG]

** Reproduction — the exact term, found
The renderer has exactly TWO live width sources, and they disagree by
one column in a fringe-less GUI:

1. =org-air-view--render-width= ->
   =org-air-layout-current-width= ->
   =org-air-layout--usable-columns=: in a real graphical window this
   is =window-max-chars-per-line=, which RESERVES the column the
   continuation/truncation glyph occupies when the right fringe is
   absent (that helper exists because of exactly this bug class — its
   own docstring cites S7).  TTY/batch tier: plain
   =window-body-width=.  Used by the inline (two-pane / stacked) and
   board-only compositions — measured: they FIT.

2. =org-air-rail--host-width= (R27-2) — the seam that re-measures the
   host window AFTER the rail side window is ensured — returns raw
   =(max org-air-item-pane-min (window-body-width win))=.  Under
   =side-window= orientation it OVERWRITES the width from source 1
   (=org-air-view--render=: "compose at the board window's REAL body
   width"), so the whole board — banner, rule, every row — is composed
   one column wider than the window can display.  Measured: body=51,
   usable=50, rendered-width=51, longest line 51 — OVERFLOW.  The
   header composes to 51 with its status ending at column 50 (=W-1=,
   contract held!) — but 50 is the window's LAST displayable column,
   so the status glyph sits flush at the edge and the 51-wide rows
   force the horizontal overflow the screenshots show.  ~One char too
   wide, precisely.

Same raw measurement in two more places, same off-by-one:
- =org-air-rail--show= composes the rail's OWN content at
  =(max 1 (window-body-width win))= — measured rail buffer: body=28,
  usable=27, longest=28, overflow;
- =org-air-project--doc-rail-show= resolves the doc-session host at
  =(max 40 (window-body-width win))=.
The PROJECT view inherits the board's bug through the shared helper
(=org-air-project--host-width= -> =org-air-rail--host-width=), and its
default placement IS =side-window= (R26-5) — so the user's project
tree overflows the same way.

Why every existing gate stayed green:
- batch goldens run the width seam, which bypasses the host-width
  helper entirely;
- the S7 ERT asserts the header ends at W-1 of the COMPOSE width —
  true on both paths; the bug is the compose width itself;
- the R27-2 ERTs assert =rendered-width == (window-body-width win)= in
  a TTY-ish batch frame where =usable-columns == window-body-width= —
  the equality the GUI breaks is exactly the one the harness cannot
  see without the fringe-less stub;
- a GUI WITH fringes has =window-max-chars-per-line ==
  window-body-width=, so only minimal fringe-less configs (this user,
  per R28-1) ever render the divergence.

** Decision — one width primitive: every live measurement flows through usable-columns
The fix REUSES =org-air-layout--usable-columns= (no new mechanism, no
fork) at the three raw call sites — each a one-term change:

1. =org-air-rail--host-width= (org-air-view.el):
   =(max org-air-item-pane-min (org-air-layout--usable-columns win))=.
   This fixes the board AND the project in one place (shared helper,
   R27-2's own "one primitive, no fork" rule).
2. =org-air-rail--show= rail width:
   =(max 1 (org-air-layout--usable-columns win))= — the rail's own
   lines also fit fringe-less windows.
3. =org-air-project--doc-rail-show= host fallback:
   =(max 40 (org-air-layout--usable-columns win))=.

Contract restatement (docs + R27-2 ERTs): the R27-2 host-width
contract is "the compose width equals the host window's USABLE
columns" — =org-air-layout--usable-columns=, not raw
=window-body-width=.  In the batch/TTY harness the two are equal, so
the existing R27-2 assertions keep their exact measured values; they
are restated in terms of the usable-columns primitive so the contract
can never drift GUI-side again.  S7 is unchanged and now holds where
the user looks: status ends at W-1 with W = usable columns, so the
final blank margin column is INSIDE the displayable area and no
continuation/truncation glyph can ever overprint the status.

Verified on this checkout (fix-check transcript above): with
host-width measuring usable columns, the popped board composes at 50
in the 51-body window — longest line 50, fits, zero dead columns
(the reserved column is the continuation-glyph column; it is not
usable for text in a fringe-less GUI, so composing to 50 IS the full
usable width).

Explicitly out of scope: fringe-width detection subtleties
(=window-max-chars-per-line= already owns that logic — we inherit,
never reimplement) and any batch/golden re-bless (nothing changes).

* R29-2 — cursor lands at column 0: the dead-zone predicate is dead in the user's configuration [BUG]

** Reproduction — no whitelist to miss; the predicate itself never fires
The suspected motion-command whitelist does NOT exist:
=org-air-view--normalize-point= (R22-2, buffer-local
=post-command-hook= in both views) is already command-agnostic.  Its
GUARD is what fails.  It snaps only when point's column carries NO row
property while the line owns one — and that dead zone exists only in
some compositions:

- BOARD, two-pane (inline rail): the pane compose indents rows with an
  UNPROPERTIZED outer margin, so the leading columns are property-free
  — the snap fires (measured: col 0 -> 13).  This is the shape the
  R22-2 ERTs exercise (width seam => two-pane), which is why they are
  green while the user suffers.
- BOARD, board-only / side-window (the user's config — rail popped):
  =org-air-view--insert-item='s margin lives INSIDE the row string and
  =org-air-view--insert-row= adds =org-air-item= over the WHOLE line —
  column 0 included.  Guard false everywhere on the row; the snap
  NEVER fires.  Measured: =<down>= sticks at column 0 on item rows.
- PROJECT, every doc row: full-row =org-air-doc= coverage (measured:
  zero property-free columns).  Snap never fires in ANY grouping.

Second layer: the project map binds no =j=/=k= (they live in
=org-air-view-mode-map= only, R3), so under evil motion state the
R27-4 overriding map has nothing to override — =j=/=k= resolve to
=evil-next-line= / =evil-previous-line=.  Evil's goal-column semantics
then pin point at column 0 forever (each motion re-targets the stored
goal column 0), exactly "moving between rows still leaves the cursor
at the very beginning of the line".  Arrows behave the same on BOTH
views even where =j=/=k= are org-air's.  Evil-state interaction was
measured sound where registration ran (motion state, overriding map
honoured) — but registration happens at MODE INIT behind an =fboundp=
gate, so an evil loaded AFTER the first org-air buffer (deferred
=use-package=) silently gets NO registration; hardened below.

** Decision — line-motion-gated snap on the title mark; j/k to the core map
One rule, no command list, no evil dependency:

1. Dead zone, redefined (=org-air-view--dead-zone-p=): on a line that
   owns a row (=org-air-view--row-property= finds =org-air-item= /
   =org-air-doc=), point is in the dead zone when its column is BEFORE
   the row's title mark (the R21-2 =org-air-row-title= position via
   =org-air-view--row-title-pos= — margin, todo cell, priority cell),
   OR when point's column carries no row property at all (the existing
   R22-2 clause: two-pane rail/pad columns keep snapping exactly as
   today).  Section headings, banner and blank lines own no row —
   never touched (unchanged).
2. Snap gate — LINE MOTION, not command identity: a buffer-local
   =pre-command-hook= records the current line; the post-command
   normalize snaps to the title iff the dead zone holds AND (the line
   changed since pre-command OR no snapshot exists — the command
   ENTERED this buffer, e.g. returning from the pane or a doc
   session).  The snapshot is consumed (cleared) every post-command.
   Command-agnostic by construction: =evil-next-line=,
   =evil-previous-line=, =evil-next-visual-line=, =evil-goto-line=,
   arrows, =C-n=/=C-p=, and any future package all converge on the
   title glyph.
3. In-row horizontal motion is NEVER hijacked: =h=/=l=, =C-f=/=C-b=,
   =0=/=^= stay on the same line -> gate false -> no snap, even when
   they move INTO the gutter (evil =h= from the title's first char
   parks on the todo cell and STAYS — explicit spec point; only a
   LINE-crossing motion that lands in the dead zone snaps).
4. =j=/=k= move from =org-air-view-mode-map= to the shared
   =org-air-view-core-map= (R18 D-P3 parent of both views): the
   project gains =org-air-next-line=/=org-air-prev-line= — identical
   bindings on the board (byte- and behavior-identical there), title
   landing by construction on the project, and the R27-4 overriding
   map now has the keys to override under evil.  The R27-4 parity
   table's documented override set shrinks by j/k accordingly.
5. Restore/entry tails normalize EXPLICITLY (no hook timing games):
   the R21-1 point-restore tail of the refresh/render path (including
   the R26-8 swap restore) and the pane/doc-session return paths call
   the same snap function directly after placing point, so a restored
   dead column is corrected immediately, not on the next keystroke.
6. Registration hardening (defense-in-depth, the R28-1 soft-dep
   idiom): =with-eval-after-load 'evil= re-runs
   =org-air-view--setup-evil= over the R27-4 mode table — idempotent
   (=evil-make-overriding-map= / =evil-set-initial-state= are), so a
   late-loading evil still gets motion state + overriding maps for
   already-defined modes.

Explicitly accepted: a line-crossing =C-f= (over a newline into the
next row's margin) now lands on that row's title — consistent with the
rule and with n/p's landing; documented, asserted, and strictly better
than parking on a margin space.  Non-evil =C-n=/=C-p= from the title
column are UNCHANGED on the board (V6: all titles share one left edge,
so the preserved goal column lands on/after the title mark — gate
irrelevant).
