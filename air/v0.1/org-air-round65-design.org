* Summary

REAL USER NEED, verbatim intent: when an item is viewed in the VIEW
PANE (the =v= command → =org-air-view-pane=), the item's CONTENT must
NOT be collapsed — the body (and any sub-headings) should be VISIBLE.
The =:PROPERTIES:= drawer MAY stay collapsed (permissive: keeping it
folded is fine/desired).  Today the content shows COLLAPSED.

Root cause (MEASURED this round, probes under =/tmp/org-air-r65/=,
batch Emacs 30.2 / Org 9.7.11): the default interactive pane path
=org-air-view-pane--render-editable= (org-air-view.el:6755) →
=org-air-view-pane--indirect= (:6651) creates the pane with
=make-indirect-buffer BASE NAME t= — and CLONE=t *inherits the base

- =org-fold-core-style= =text-properties= (the Org 9.6 default —
  i.e. every stock Emacs 29 user): folds are text properties on the

* Root cause, precisely

=org-air-view-pane--indirect= (:6651):

#+begin_example
(make-indirect-buffer base NAME t)   ; CLONE = inherit org-mode
...
(org-narrow-to-subtree)              ; nothing unfolds afterwards
#+end_example

Why the pane inherits the fold — per style:

- *text-properties style* (Org 9.6 default; =defcustom
  org-fold-core-style= flipped its default to =overlays= only in Org
  9.7, and only for Emacs ≥ 29): org-fold stores folds as text
  properties named by buffer-unique symbols
  (=org-fold-core-get-folding-property-symbol=), routed into
  =invisible= via a buffer-local =char-property-alias-alist=.  Text
  properties live on the text, which an indirect buffer SHARES; and
  CLONE=t copies the base's local variables — including
  =char-property-alias-alist= — so the fresh pane resolves the BASE's
  fold properties and displays folded.
- *overlays style* (Org 9.7 default on Emacs ≥ 29): folds are
  overlays.  Overlays are per-buffer, BUT since the Emacs 29 itree
  overlay rewrite =make-indirect-buffer= with CLONE=t *copies* every
  base overlay into the new indirect buffer.  Probe (Emacs 30.2):
  the copy is a DISTINCT object (=eq= → nil), CLONE=nil copies
  nothing, deleting the pane's copy leaves the base's overlay alive,
  and overlays created in the base AFTER the clone never appear in
  the pane.  So the pane starts with its own private copy of the
  base's fold overlays — folded.

Either way: the user keeps their source file at =org-startup-folded=
/ overview, presses =v=, and the pane shows a collapsed heading with
no body.

* The leak gotcha, investigated (why a pane-local reveal is safe)

The obvious fix — unfold in the pane — looks dangerous under
text-properties style: fold state is text properties on SHARED text,
so a naive expectation is that =org-fold-show-subtree= in the pane
strips the BASE's fold properties and unfolds the user's real source
buffer.  Measured, that does NOT happen at org-air's platform floor
(=Package-Requires: ((emacs "29.1") (org "9.6") …)=), for two
platform reasons — both verified by probe:

1. *Emacs ≥ 29 runs =clone-indirect-buffer-hook= from
   =make-indirect-buffer= itself* (NEWS.29: "The
   'clone-indirect-buffer-hook' is now run by 'make-indirect-buffer'").
   =org-fold-core-initialize= registers
   =org-fold-core-decouple-indirect-buffer-folds= on that hook
   buffer-locally in every Org buffer; CLONE=t copies the local hook,
   so the decouple runs AT PANE CREATION.  Probe: immediately after
   =org-air-view-pane--indirect= returns, (a) the pane is registered
   in the base's =org-fold-core--indirect-buffers= (both styles), and
   (b) under text-properties style the pane's
   =char-property-alias-alist= =invisible= entry already differs from
   the base's — the fold state has been *copied onto pane-unique
   property symbols* (preserving the folded appearance, which is
   exactly the bug's mechanics) and every subsequent fold/unfold in
   the pane touches only the pane's own symbols.  Belt-and-braces:
   even if the hook were somehow skipped, org-fold-core's
   =org-fold-core--property-symbol-get-create= performs the same
   decouple lazily on the FIRST fold operation issued in the pane
   (the "carried-over properties" branch), i.e. before our reveal
   could ever touch a base-owned property.
2. *Under overlays style the pane's fold overlays are private
   copies* (itree CLONE copy, probe above), so removing/adding them
   in the pane cannot affect the base by construction.

Probe results S2/S4/S6/E1 confirm end to end, under BOTH styles: after
the pane reveals the subtree AND re-folds the drawers, the base
buffer's body/child/preamble stay invisible exactly as before, an
OPEN base drawer stays open (no reverse leak from the pane's drawer
re-fold), and =buffer-modified-p= on the base stays nil (org-fold
wraps property writes in =with-silent-modifications=; overlays never
modify).

Chosen mechanism, argued against the alternatives:

- *In-pane org-fold reveal (CHOSEN)*: zero new machinery; uses the
  documented org-fold API whose per-buffer isolation is a designed,
  probed property at org-air's exact platform floor (Emacs 29.1 is
  the first release with BOTH the hook-on-make-indirect-buffer and
  itree overlay copy; Org 9.6 is the first with org-fold-core and its
  decouple).  The isolation is additionally PINNED by leak ERTs under
  both styles (test plan), so a platform regression turns the gate
  red instead of silently un-folding user files.
- /Overlay-based local reveal (manual overlays over the fold
  regions)/: rejected — re-implements org-fold's display layer,
  fights org's own fold bookkeeping inside an EDITABLE buffer (org
  commands in the pane would still consult org-fold state, now
  disagreeing with what the user sees), and buys nothing the probed
  isolation doesn't already give.
- /Save + restore the base's fold spec around the reveal/: rejected —
  racy by design (the pane is long-lived and editable; "around" has
  no bracket), O(file) fold-state capture per pane open on large
  files (R53), and needless: the state never becomes shared in the
  first place.
- /Switch the default pane to the snapshot path/: rejected — regresses
  R19-3's headline feature (live write-through editing in the pane).

The naive alternative — reveal in the BASE (before/instead of the
pane) — measurably leaks (probe: base body becomes visible), which is
precisely the anti-behavior the leak ERTs assert against; it anchors
their RED story.

* Design

** R65-1: =org-air-view-pane--reveal= + the two call sites

New internal helper (org-air-view.el, next to =--indirect=):

- =org-air-view-pane--reveal (&optional wide)= — "Reveal the pane's
  content, then re-fold drawers; pane-buffer-local; never errors."
  Runs in the current (pane) buffer:
  1. Whole body wrapped in =(condition-case nil … (error nil))= —
     R53's never-error posture: any failure degrades to today's
     behavior (a folded pane), never a broken =v=.
  2. Narrowed branch (WIDE nil; point is at =point-min= = the
     heading, exactly where both call sites leave it):
     =(org-fold-show-subtree)= — reveals the heading's ENTIRE
     subtree: body, sub-headings AND their bodies.  This is why
     show-subtree is chosen over show-entry + show-children: the
     user's need is "the body (and any sub-headings) VISIBLE", and
     =org-fold-show-children= leaves the children's own bodies
     folded while =org-fold-show-entry= reveals only the first body.
     show-subtree also correctly splits a fold that STARTS BEFORE the
     narrow (viewing a child item buried under an overview-folded
     parent — probe E1: heading, body and grandchild all reveal).
  3. Wide branch (WIDE non-nil; the heading-less / pos-nil file-head
     case, where =--indirect= leaves the buffer wide):
     =(org-fold-show-all)= — there is no subtree to bound; the pane
     already shows (and font-locks) the whole file in this branch, so
     the O(buffer) reveal adds no new cost class (R53 note below).
  4. THEN =(org-fold-hide-drawer-all)= — ZERO-ARG deliberately: the
     Org 9.6 signature takes no arguments and the 9.7 BEGIN/END are
     optional, and under the subtree narrowing the zero-arg call is
     already bounded to =point-min=..=point-max= = the subtree.
     Re-folds the =:PROPERTIES:= drawer(s) — including sub-headings'
     — plus any other drawers (LOGBOOK etc.), matching Org's own
     cycle idiom (reveal, then =org-cycle-hide-drawers=).  Probed:
     the re-fold is pane-local too (S4 — an OPEN drawer in the base
     stays open).
  5. API floor + fallback: org-air's floor (Org 9.6) has the whole
     =org-fold-*= API, but follow the existing defensive precedent at
     org-air-view.el:9790 (=org-fold-show-context= vs
     =org-show-context=): each call goes through an =fboundp= ladder
     — =org-fold-show-subtree= → =org-show-subtree=,
     =org-fold-show-all= → =org-show-all=,
     =org-fold-hide-drawer-all= → =(org-cycle-hide-drawers 'all)= —
     so an exotic older external Org still degrades sanely (where
     pre-org-fold Org folds with overlays, which Emacs ≥ 29 clones
     privately — isolation still holds).

Call site 1 — =org-air-view-pane--indirect= (:6651): in the
=with-current-buffer ind= block, after the narrow/widen decision and
the final =(goto-char (point-min))=, call
=(org-air-view-pane--reveal WIDE)= where WIDE is non-nil in the
heading-less/pos-nil branches.  Docstring gains the R65 contract
sentence (content revealed, drawers re-folded, pane-local).

Call site 2 — =org-air-view-pane--renarrow= (:6769): same call, same
placement — after =(goto-char (point-min))=, before the header-line
refresh; WIDE non-nil in its =org-before-first-heading-p= branch.
The reuse path may carry the PREVIOUS item's reveal state outside the
new narrow — harmless (invisible outside the narrow, pane-private)
and probed (S6: second heading reveals correctly on reuse).

Explicitly UNCHANGED: the =make-indirect-buffer … t= call (CLONE=t is
what makes edits+modes work and, on Emacs ≥ 29, what triggers the
fold decouple), the narrowing semantics, point placement, chrome,
teardown, follow debounce, and the =--render= funnel logic.

** R65-2: snapshot — body pinned visible, =:PROPERTIES:= folded display-only

Probe S5 confirms the snapshot ALREADY shows the body under both
styles: =--entry-text='s =buffer-substring= does carry the base's
fold text properties (text-properties style), but they are inert in
the =*org-air-view*= buffer — nothing aliases them into =invisible=
and no fold overlay is copied by string insertion.  R65 pins this
with an assert (T5) so it can never silently regress.

Decision for the raw =:PROPERTIES:= dump: *FOLD, don't omit.*
Omitting drawer lines would change buffer BYTES — breaking the pane
byte goldens, the R58 printable bookmark stash context and plain
copy-out of the snapshot text.  Instead =--render-snapshot= (:6724),
after inserting the entry text and applying =--apply-max-lines=,
walks the inserted region for property drawers
(=^[ \t]*:PROPERTIES:[ \t]*$= … matching =^[ \t]*:END:[ \t]*$=; skip
unterminated) and puts a display-only
='invisible 'org-air-pane-drawer= text property from the end of the
=:PROPERTIES:= line through the end of the =:END:= line, with
=(add-to-invisibility-spec '(org-air-pane-drawer . t))= in the pane
buffer (ellipsis shown, matching the folded look).  Scope: property
drawers only — the minimal, prompt-scoped consistency fix (the
editable pane folds all drawers because that is org's own one-call
idiom; the deliberate asymmetry is called out here and is fine under
the permissive drawer contract).  Probe E3: buffer bytes unchanged;
=equal= on strings ignores text properties, so the R16 golden
comparisons (=buffer-substring-no-properties= / string =equal=) are
untouched.  The truncation marker interplay is nil: the fold is
applied AFTER =--apply-max-lines= on whatever drawer lines survive.
Goldens/fixtures: ZERO shifts expected; if any fixture run ever
shows a diff here, that is a spec violation, not a re-bless.

** Scope: everywhere =v= opens a pane

No per-view work: =v= → =org-air-view-pane= is bound once on
=org-air-view-core-map= and inherited by the board, project, review
and revisit keymaps; every render funnels through
=org-air-view-pane--render= (:6793) into exactly the three functions
above (=--indirect= / =--renarrow= / =--render-snapshot=), including
the follow-mode re-renders.  T7 guards the funnel.

** Edge cases (all probed or bounded)

- Child item under a wider enclosing fold (E1) — reveals fully;
  org-fold splits the pane's private fold at the narrow boundary.
- Heading-less file / pos-nil file head (E2) — wide branch reveals
  prose, re-folds drawers, no error; R53 file-items covered.
- Item with no drawer / no body / no children — show-subtree and
  hide-drawer-all are no-ops; nothing signals.
- Drawer OPEN in the source (S4) — pane re-folds its copy; source
  drawer stays open (no reverse leak).
- Unterminated =:PROPERTIES:= (no =:END:=) in the snapshot — no
  property applied for that drawer (never-error).
- Repeated =v= / follow on the same file (S6) — the =--renarrow=
  reuse path re-reveals per item; stale reveal state outside the
  narrow is invisible and pane-private.
- R53 cost: no scan, no extra file visit, no timer; narrowed-branch
  work is O(subtree); wide-branch O(file) matches the branch's
  existing font-lock cost; never-error wrapper throughout.

* Non-goals

- No change, ever, to the fold state of the user's source buffers
  (that is the round's central invariant, not a feature).
- No new fold customization knobs; no re-fold of the pane after user
  edits inside it (the user's in-pane folding is theirs).
- No snapshot folding of non-property drawers; no drawer OMISSION
  anywhere (bytes are sacred to the goldens/bookmarks).
- No org-agenda, no new dependencies, no query-engine change
  (org-ql remains the only query path).

* Compatibility

- *R53 (never-hang / never-error)*: no scans, no extra file visits,
  O(subtree) work in the narrowed pane, the wide branch stays in its
  existing O(file) cost class, and the whole reveal is
  condition-case-guarded — a fold failure yields today's folded pane,
  never a broken =v=.
- *R64 (refile form, parallel round)*: disjoint — R64 lives in
  org-air-inbox.el + the transient form; R65 touches only the three
  pane internals in org-air-view.el.  No shared functions, no
  ordering constraint.
- *R16/R19/R20 pane contracts*: narrowing, write-through editing,
  chrome, teardown, follow reuse and every byte golden preserved;
  R35.1 keybinding gating untouched (the fix is render-side, not
  key-side).
- *Platform floor*: =emacs 29.1 / org 9.6= is exactly the floor
  where both isolation guarantees hold (make-indirect-buffer runs
  clone-indirect-buffer-hook; itree clones copy overlays; org-fold
  decouples indirect fold state) — verified by probe on 30.2/9.7.11
  and pinned across both fold styles by T2/T3.
