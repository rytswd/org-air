* Decision 1 — r's fate: DROP (no deprecated alias)

=e= becomes THE binding; =r= is removed from
=org-air--register-default-keys 'org-air-view-mode-map= (:1599) and
left UNBOUND on the board (the map's comment row updates: triage
verbs =c/m/s/d/e/f/t/T/a/D/x/u/I=).  No one-release =r= alias:

- The user's own framing rules it: /"it's no longer refile"/.  The
  muscle memory being protected is the requester's, and the request
  is the rebind.
- Legend truth (R30-2/R50-1): every legend/help key derives via
  `where-is-internal' FIRSTONLY.  A second binding to the same
  command makes the DISPLAYED key an accident of keymap internals —
  the exact argument R67's Non-goals used to refuse an =e= alias
  when =r= was primary; it cuts the same way reversed.  One binding
  keeps the derivation deterministic: help shows =e=, period.
- An unbound =r= is LOUD (="r is undefined"=) — active retraining;
  a silent alias postpones the same relearning and adds a test
  surface for a key already scheduled to die.  v0.1 pre-release
  carries no compat obligation.
- =g r= (refresh, the g-prefix) is untouched — a different map.

The knob-off contract (R35-1) follows automatically: with
=org-air-use-default-keybindings= nil, =e= — like every installer key
— is absent from the map.

* Decision 2 — the walk's =?r= row stays "[r]efile"

=org-air-process-inbox= (:9545) dispatches =?r= from its char menu
to the same command.  It KEEPS the key and the =[r]efile= label:

- It is a modal =read-char= menu, not a keymap — no `where-is' /

- In the guided walk the user's intent IS filing (the countdown to

- The in-place leg remains reachable from the walk too (open, edit

Likewise UNTOUCHED: =org-air-item-file-group= (board =f=) keeps

* Decision 3 — the note writer: setup + synchronous store, never the prompt

** Why not org's own interactive note flow

An =org-add-log-setup 'note= left to its own devices defers
=org-add-log-note= to =post-command-hook=, which pops a full-frame
=*Org Note*= buffer awaiting =C-c C-c= — against a source buffer the
user never saw, inside a transient session: the R68 trap class,
verbatim.  R68's answer for IMPLICIT logging was downgrade + flush;
this round's case is the opposite pole — an EXPLICIT user note —
so the text must be APPLIED, with org still owning the formatting,
placement and timestamp.

** The core primitive (org-air-inbox.el, next to the R68 flush)

=org-air-inbox--append-log-note (text)= — point at the heading in
its source buffer; appends TEXT as a dated note.  The probed,
unmocked-in-batch emulation of =org-add-log-note='s finishing
branch, with the note buffer PRE-FILLED instead of user-edited:

#+begin_src emacs-lisp
(org-add-log-setup 'note nil nil 'note)   ; marker, purpose, effective time
(remove-hook 'post-command-hook #'org-add-log-note)
(setq org-log-setup nil)
(setq org-log-note-window-configuration (current-window-configuration))
(move-marker org-log-note-return-to (point))
(let ((buf (generate-new-buffer " *org-air-note*"))
      (current-prefix-arg nil)          ; store's abort gates: forced off
      (org-note-abort nil))
  (with-current-buffer buf (insert text))
  (with-current-buffer buf (org-store-log-note)))
#+end_src

Every internal it touches, and why (org 9.7.11 source, read):

- =org-add-log-setup= is the org-owned seam: it records
  =org-log-note-marker= (point), =org-log-note-purpose= ='note=
  (which selects the ="Note taken on %t"= template from
  =org-log-note-headings=) and =org-log-note-effective-time= (the
  =[ts]=), and queues the hook — which we immediately dequeue
  (+ clear =org-log-setup=), taking over its ONLY remaining job.
- =org-log-note-window-configuration= / =org-log-note-return-to=:
  =org-store-log-note='s epilogue restores both unconditionally —
  set here so the restore is a no-op bracket (the same
  save/restore =org-add-log-note= itself performs on the R68 flush
  path, probed batch-safe there and here).
- =org-store-log-note= reads the note TEXT from the current buffer
  (killing it — hence a =generate-new-buffer=, never
  =with-temp-buffer='s double-kill), prefixes the dated heading
  line (=… \\= exactly when text follows), indents continuation
  lines, and inserts at =(org-log-beginning t)= via MARKER —
  display-independent, and the drawer decision
  (=org-log-into-drawer= / =#+STARTUP: logdrawer= /
  =LOG_INTO_DRAWER=) is org's own, read file-locally in the SOURCE
  buffer.  =current-prefix-arg= / =org-note-abort= are its two
  abort gates — let-bound nil so a stray prefix can never silently
  drop the note.

** Composition with the R68 discipline — disjoint by construction

The R68 bindings (=org-inhibit-logging 'note=,
reschedule/redeadline ='note=→='time=) act on the DOLOG computation
inside =org-todo= / =org--deadline-or-schedule= — an explicit
=org-add-log-setup 'note= never consults them (probed: the note
lands in full under the binding).  And the R68 flush
(=org-air-inbox--flush-pending-log-note=) gates on hook membership
+ =how ∈ (time state)=: after this primitive the hook is already
clean, so a surrounding =org-air-view--at-item-source= (or the
macro's own post-body flush) no-ops — no double-insert, no
suppression, no interaction.  The two mechanisms answer opposite
problems: implicit log records are downgraded+flushed; an explicit
user note is applied.

** The item-level wrapper

=org-air-inbox--add-item-note (item text)= — the apply-side twin of
=org-air-inbox--apply-item-edits= (same file, same inlined
=--at-item-source= semantics — view.el requires inbox.el, so the
macro is unreachable here by design): stale guard when =fboundp=,
=org-air-inbox--source-buffer=, =org-with-wide-buffer=, goto the
R26-8 marker-or-=(FILE . POS)= position, =org-back-to-heading t=,
then ONE =atomic-change-group= around =--append-log-note= (probed:
a signal rolls the note back byte-exactly), ONE =save-buffer= (the
note is part of the same saved bytes — the R53 scan sees the
complete edit), and the triage-undo recording when =boundp= (the
board's =u= covers a note like every single-field verb).  NOT the
engine: no cut, no paste, no destination.  Returns non-nil on
apply.

* Decision 4 — the reader: minibuffer, not a note buffer

=read-string "Note: "= against the DISPLAYED board — the board's
established idiom for every quick text read (R64/R67 fields, R68's
todo completion).  A dedicated note-buffer read is exactly the
modal =*Org Note*= interaction shape this round exists to avoid;
multi-line text still travels (yank, =C-q C-j=) and org indents the
continuation lines (probed).  Long-form writing belongs in the
source buffer via =RET= visit, where org's full note UI applies
untouched (the R68 Decision-2 boundary, unchanged).  Empty input ⇒
a gentle =message "Empty note — nothing added"= — no write, no
error (R53).

* Decision 5 — the suffix: immediate apply, transient stays open

=org-air-refile-form-note= (the =refile-form-*= family name — the
prompt's no-rename rule extends to the new sibling), key
="S-<return>"=, placed in the bottom group between RET and =q=,
label ="add note"=, =:transient t=.

- *An ACTION suffix, not a deferred field* — deliberately unlike
  =t/c/s/d/k/,=.  A note is append-only journaling, not item state:
  it has no meaningful "current value" row, no WYSIWYG preview
  line, and deferring it to RET would entangle it with the refile
  leg (engine plumbing for a =:note= parameter, before/after-move
  ordering) for zero user value.  The R64 one-confirm contract is
  honoured at its own scale: typing the note and pressing RET in
  the minibuffer IS the note's one confirm — S-RET alone (empty
  read, =C-g=) writes nothing, so prompt-time no-mutation holds
  for every FORM field exactly as before.
- *Stays open* (=:transient t=): the natural flow is "jot a note,
  maybe also bump a field" — closing would force a reopen; RET/=q=
  remain the ONLY exits (the clean modal invariant).  Two S-RETs =
  two dated notes — journaling, as org means it.  The immediate
  write cannot stale the form: a note appends BELOW the heading
  line, so every seeded field, the item's marker, and a later
  refile (the note travels with the subtree) stay correct.
- Tail: =message "Added note to \"%s\""= + the execute-leg's
  board-refresh-when-on-the-board guard (the save has bumped mtime;
  the refresh repaints under the open transient harmlessly).
- Key choice: =[S-return]= is what a GUI delivers, and what
  CSI-u/modifyOtherKeys terminals normalise to via xterm.el; the
  board's belt-and-braces =\"S-RET\"= CHAR registration is a keymap
  nicety the transient menu cannot mirror without a duplicate menu
  row — one entry, the symbol form, is the honest binding.  A
  plain terminal cannot send S-RET at all (it sends RET) — the
  same hardware limit the board's S-RET visit already lives with;
  noted as GUI residue, not worked around.

* Compatibility

- *R53 (never-hang / never-error)*: strengthened where it counts —
  the one historically trap-prone org UI (the note prompt) is
  entered only via its synchronous, display-independent finishing
  path (probed unmocked in batch).  One =find-file-noselect= on the
  item's own file — the same buffer every board verb visits; no
  scans; empty input is a message, not an error.
- *R57*: untouched (no vocabulary surface).
- *R64 (one-confirm, prompt-time no-mutation)*: the FORM fields keep
  the contract byte-for-byte; the note is a self-confirming action
  (Decision 5) — S-RET without text mutates nothing.
- *R67 (the editor)*: both execute legs untouched; the heading
  reframe is string-level (the r19 structural pin survives); the
  in-place leg and the note wrapper are siblings sharing the same
  inlined =--at-item-source= semantics and atomicity discipline.
- *R68 (logging discipline)*: intact and PROVEN disjoint — the
  discipline downgrades implicit records; the explicit note path
  neither consults its knobs nor leaves anything for its flush
  (r70-8).  The flush helper itself is unchanged.
- *R30-2/R50-1 (derived legend keys)*: strengthened — one binding,
  one derivable key; help/legend can never disagree about =e=.
- *R26-6*: the discovery guarantee relocates with the key — help
  documents =e=; still no row nudges, still no rail cell.
- Cache: no schema change; the note save bumps mtime and the
  ordinary refresh pipeline picks it up like every board write.
