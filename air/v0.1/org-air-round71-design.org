#+title: org-air Round 71 — The comment becomes a form FIELD: `n' drafts the note, ONE RET confirms edit + note together (the R70 S-RET action retires)
#+state: complete
#+tags: board editor transient field notes logbook ux

* Summary

USER CLARIFICATION on R70-2: the R70 spec made S-RET a SEPARATE
note-only action (write now, keep editing).  The user actually wants
the comment to be part of ONE confirm — =RET= applies the edit AND
the note together — and prefers it as a transient FIELD (like =t=
tags / =c= category / =s= schedule / =k= todo / =,= priority / =d=
deadline), NOT an S-RET action.  This round revises exactly that
delivery UX; the R70 note WRITER (the probed synchronous
=org-add-log-setup= + pre-filled =org-store-log-note= emulation) is
kept verbatim and re-plumbed.

Two work packages:

- *R71-1 (the field)* — the ="S-<return>"= row is REMOVED from
  =org-air-refile-transient= (S-RET is no longer a transient action;
  the key is left UNBOUND in the transient — Decision 1).
  =org-air-refile-form-note= keeps its NAME (the =refile-form-*=
  family no-rename rule) but is REPURPOSED action → FIELD: key =n=,
  the LAST row of the Metadata group (=t/c/s/d/k/,/n=; audited free —
  probe table below), =:transient t=.  It reads the comment text from
  the minibuffer (multi-line ok — yank, =C-q C-j=) PRE-FILLED with the
  pending value (re-press = re-edit; empty input CLEARS — Decision 2)
  and stores it in the form state as the DIRTY field =:note= — NO
  write happens at read time (the R64-2 prompt-time no-mutation
  contract now covers the note; R70's action was the form's ONLY
  immediate write, and its removal makes the prefix docstring's
  "every write is deferred to execute" claim TRUE again —
  Decision 6).  The field row renders like every sibling
  (=note     <first line>…=, =–= when unset) and the live Preview
  gains a =note: <first line>…= segment on its extras line.
- *R71-2 (the application)* — on EXECUTE (=RET=) the =:note= dirty
  field is APPLIED along with the other metadata + the optional
  refile, inside the SAME atomic application, one save, one undo:
  - /in-place leg (no destination)/: =:note= becomes a first-class
    EDITS field of =org-air-inbox--apply-item-edits= — applied via
    =org-air-inbox--append-log-note= as the change group's LAST form,
    AFTER the R68 flush (the probed globals-overwrite hazard,
    Decision 4), inside the ONE =atomic-change-group= + ONE
    =save-buffer= + the triage-undo recording the applier already
    owns; ='note= joins the applied-fields message.
  - /refile leg (destination set)/: =org-air-refile-item= gains a
    trailing additive NOTE parameter (the R67-3 DEADLINE precedent —
    every pre-R71 caller passes unchanged), applied at the MOVED
    heading in the TARGET buffer after the metadata block —
    flush-first, inside the engine's existing transaction, before its
    ONE transactional save; the drawer decision is the WRITE TARGET
    file's own =org-log-into-drawer= (the R67-4 write-target law,
    Decision 5).
  So =RET= = confirm edit + note in one action; the note lands in
  BOTH legs.  Empty/absent =:note= = no note written.  The R70
  standalone wrapper =org-air-inbox--add-item-note= FOLDS INTO the
  applier's =:note= leg and retires (Decision 3) — its whole body was
  the one-field special case of what =--apply-item-edits= already
  does.

* Decision 1 — S-RET: removed, freed, left unbound

The ="S-<return>"= group row is deleted; NOTHING replaces it in the
transient.  S-RET inside an open editor now gets transient's own
undefined-key feedback — loud, like R70's dropped =r= (active
retraining; the requester's own muscle memory is the one being
retrained, and the request is the move).  No alias, no
"S-RET now lives on n" courtesy binding: a second key for the same
suffix would put TWO rows in the menu (the transient renders every
binding — R70 Non-goals refused a duplicate row for exactly this
reason) and the field's home is the Metadata group where its
siblings live.  The BOARD's own S-RET visit (=org-air-visit-item=)
is untouched — it was never the transient's binding; the modal
shadowing that made R70's reuse safe simply ends.

* Decision 2 — the field: key `n', minibuffer pre-fill, empty clears

** The key

=n=, the last Metadata row (=t/c/s/d/k/,/n=).  Audited free three
ways (probe table): no layout suffix uses it, and neither
=transient-map= nor =transient-base-map= carries it (no common
command is shadowed).  The BOARD map's =n= (=org-air-next-item=) is
irrelevant while the transient is open — the modal keymap shadows the
board, the same argument R70 used for S-RET, now in the harmless
direction.  Mnemonic: =n=ote.

** The reader

#+begin_src emacs-lisp
(read-string "Note (empty clears): " (org-air-inbox--form-get :note))
#+end_src

- INITIAL-INPUT (the pre-fill), deliberately NOT a DEFAULT: the field
  must be RE-EDITABLE (press =n= again, the pending text is sitting
  in the minibuffer to amend) and CLEARABLE (kill the text, =RET= ⇒
  =:note= nil).  A DEFAULT would invert the second half — an empty
  =RET= re-asserts the default instead of clearing, leaving the field
  no way out.  The =k= todo field's empty-clears shape, applied to
  free text.
- Multi-line still travels (yank, =C-q C-j=) — the R70 Decision-4
  reader, unchanged; org indents continuation lines at apply time
  (probed in R70).
- Store: =(org-air-inbox--form-put :note (unless (string-empty-p
  text) text))= — the form never holds ""; empty IS nil IS "no note".
- NO write, NO message about writing — the read stores a field.
  =C-g= at the prompt leaves the previous value (the sibling fields'
  behaviour).

** The rendering

A tiny pure helper =org-air-inbox--form-note-label (note)= — the
FIRST line of NOTE, truncated to width 24 via
=truncate-string-to-width= with an ="…"= ellipsis, the ellipsis also
appended when further lines follow (a short first line must not
masquerade as the whole note).  Used twice, WYSIWYG by construction:

- the field row: =(org-air-inbox--form-field "note" …)= — =–= when
  unset, like every sibling;
- the Preview extras line (line 2), a new trailing segment after
  SCHEDULED / DEADLINE / =:CATEGORY:=: =note: <label>= — the
  =  ·  =-joined list the extras already use.

** The semantics shift: field REPLACES, not journals

R70's "two S-RETs = two dated notes" journaling law dies WITH the
action — a field has ONE pending value per confirm; pressing =n=
twice EDITS the same draft (the second read pre-filled with the
first).  One =RET= ⇒ at most ONE dated note.  Journaling is still
two keystrokes away — =RET=, then =e= again — and the field model
buys what the action could not: the note is PREVIEWABLE before any
byte moves, and =C-g=/=q= ABANDON a drafted note (R70's immediate
write was irrevocable-by-design; the user's one-confirm framing
says the note belongs inside the confirm, so abandon must cover it).

* Decision 3 — the wrapper folds: `--add-item-note' retires

=org-air-inbox--add-item-note= existed to give the R70 ACTION a
one-field atomic write path.  Its duties — stale guard, R26-8
marker-or-=(FILE . POS)= position, =org-back-to-heading= under
=org-with-wide-buffer=, ONE =atomic-change-group=, ONE =save-buffer=,
triage-undo recording — are =org-air-inbox--apply-item-edits='s
duties, verbatim (R70 called it "the apply-side twin").  With =:note=
a first-class EDITS field, the twin IS the applier: a note-only
=RET= is =--apply-item-edits item '(:note "…")= — same path, same
discipline, one code shape for every in-place confirm.  The
standalone symbol is REMOVED, not kept as a delegator: no UI calls
it, and a function whose only callers would be tests is a test-only
API — a maintenance lie the r70 pins should not prop up (they flip
to the real executed path; table in the reframe section).
=org-air-inbox--append-log-note= — the actual writer — is kept
byte-for-byte and gains its second caller (the engine).

* Decision 4 — application order: flush FIRST, note LAST (the probed hazard)

The R68 flush and the note's =org-add-log-setup= share org's
=org-log-note-*= GLOBALS.  If the metadata mutators queued a
downgraded ='time=/='state= record (a =lognotereschedule= config
under the R68 discipline, say) and the note setup runs BEFORE the
flush, the setup OVERWRITES the shared globals (=how= time→note) and
=--append-log-note='s own =remove-hook= dequeues the pending record —
the reschedule line is SILENTLY LOST (probed, table above; the exact
overwrite R68's flush was built to prevent, re-entered through the
new side door).  So in BOTH legs the order is pinned:

  mutators (under the R68 discipline) → =--flush-pending-log-note= →
  =:note= via =--append-log-note= → the ONE save

all inside the ONE transaction.  In =--apply-item-edits= the note
displaces the flush as the change group's LAST form (the R68-2
comment updates; rollback covers metadata + record + note together —
probed byte-exact).  Point is re-anchored with =org-back-to-heading
t= before the append (the mutators may drift it).  R68 disjointness
is UNCHANGED: the explicit note neither consults
=org-inhibit-logging= nor leaves anything for the flush (the R70
probes carry over) — the discipline downgrades implicit records, the
explicit note is applied, and now their ORDER inside one transaction
is part of the contract.

* Decision 5 — the engine: a trailing NOTE parameter, applied at the moved heading

=org-air-refile-item (&optional item target-file target-heading tags
scheduled category todo priority deadline note)= — the R67-3
precedent replayed: a trailing ADDITIVE parameter, every pre-R71
caller passes unchanged, nil/"" = no note.  Inside the engine the
note is applied where the marker is still alive — in the inner
=unwind-protect=, after the metadata let-block:

#+begin_src emacs-lisp
;; still inside the atomic-change-group, insert-pos still a marker:
(org-air-inbox--flush-pending-log-note)   ; FIRST — Decision 4
(when (and note (not (string-empty-p note)))
  (goto-char insert-pos)
  (org-back-to-heading t)
  (org-air-inbox--append-log-note note))
#+end_src

with the engine's existing pre-save flush call MOVED here (from
between the group's paste block and its =save-buffer=) — a
behaviour-neutral relocation: same transaction, still before the ONE
transactional save, and now provably ordered before the note.

The note lands at the MOVED heading in the TARGET buffer, so the
drawer decision is the WRITE TARGET file's own =org-log-into-drawer=
/ =#+STARTUP: logdrawer= — the R67-4 write-target law (=k='s
vocabulary and =,='s range already read the file the write lands
in), and exactly how every other metadata field behaves in this leg.
Writing at the SOURCE before the cut was considered and rejected: a
post-cut failure restores TEXT with the note already inside — a
half-applied confirm surviving a failed edit breaks the
all-or-nothing contract; at the target, the signal path rolls the
note back with everything else and the source restore is
byte-identical (the R64 discipline untouched).

* Decision 6 — the execute leg + the restored R64-2 claim

=org-air-refile-form-execute= changes minimally:

- /refile leg/: the engine call grows the tenth argument —
  =(org-air-refile-item item file olp (or (cdr eff) :none) scheduled
  category todo priority deadline (org-air-inbox--form-get :note))=.
  =--refile-last= recording unchanged — the note is per-confirm
  payload, never part of the =l= recall.
- /in-place leg/: =(when note (setq edits (plist-put edits :note
  note)))= — a note-only form is a REAL edit (edits non-null ⇒ the
  applier runs; the "Nothing to change" no-op now fires only when
  the form is truly untouched).  The completion message enumerates
  ='note= like any field ("Edited \"…\" — priority, note").

The transient prefix docstring updates: the field list gains the
note, and its "every write is deferred to execute (R64-2)" sentence
— which R70's immediate-write action quietly contradicted — is
STRENGTHENED to name the note as deferred too.  =RET='s dynamic
label ("refile" / "edit in place") is untouched: the note rides
whichever leg the label already announces.
