* Summary

next week or so."  Today the =/= filter (=org-air-view--filter-tags= /
=org-air-view--filter-token-match-p=, org-air-view.el ~2054-2110)
speaks exactly two token shapes — =#tag= (tag membership) and bare

show overdue/upcoming/stale/dateless, but nothing can ISOLATE "only
overdue" or "scheduled within N days": the information is on the
board, the lens is missing.

This round adds a DATE/STATUS token layer to the SAME mini-language,
applied by the SAME fold over cached items (R53: no rescan — every
predicate reads slots the item already carries under the R54 date

  =org-tag-re= admits no colon — a literal =:is:overdue:= in a

* Decision 1 — the syntax: `qualifier:value', no bare keywords, no new sigil

Three candidate shapes were argued:

1. /Bare reserved words/ (=overdue=, =upcoming=…) — REJECTED, twice
   over.  The tag chips (org-air-view.el ~2351) toggle BARE tag
   names into the filter: a user with a literal =:overdue:= tag
   clicks its chip and gets the token ="overdue"= — reserving the
   word would silently flip that chip from "show my overdue-tagged
   items" to a date predicate.  And free text loses a word: today
   ="overdue"= substring-searches titles; a reserved set breaks the
   R24-6 mini-language's simplest contract (bare = text).
2. /A new sigil/ (=!overdue=, =.overdue=) — REJECTED.  =!= / =.= are
   legitimate title text (substring tokens), so the collision moves
   rather than dies; a third sigil beside =#=/bare grows the
   grammar the user must memorise; and it cannot express the
   parametrised window (=!7d=?) without inventing more syntax.
3. /=qualifier:value=/ (GitHub/notmuch idiom) — CHOSEN.  The colon
   is UNAMBIGUOUS against both existing shapes by grammar, not by
   convention: an org tag can never contain =:= (probed —
   =org-tag-re= is =[[:alnum:]_@#%]+=), so no =#tag= or chip token
   collides; the qualifiers are a tiny closed set, so free text is
   only affected when it matches =\`is:(overdue|…)\'= EXACTLY —
   and anything that does NOT parse falls through to today's
   substring rule unchanged (Decision 5).  The value slot gives the
   window its parameter (=due:7d=) for free, and the idiom is
   already in the user's fingers from every forge search box.

The =#= branch of =org-air-view--filter-token-match-p= stays FIRST
and the parser refuses =#=-prefixed tokens outright, so =#overdue= —
and any =#=-spelled literal tag that "looks like" a keyword — is a
tag match forever (the disambiguation seam, r72-8).  Tokens are
stored VERBATIM (R24-6), parsed at match time; matching is
case-insensitive like the rest of the mini-language.

* Decision 2 — the vocabulary, each predicate defined against cached slots

One NOW per filter application (Decision 3 binds it); =sched= / =dl=
are the item's =scheduled= / =deadline= slots (org timestamp
objects, cache-hydrated verbatim); GATE is
=org-air-classify--board-active-p= (Decision 3).  All day arithmetic
is =org-air-classify--days-between= over =org-air-classify--time= —
the buckets' own calendar-day comparisons, repeaters and hour parts
behaving exactly as they already do in the buckets (shared code, not
parallel reimplementation).

| Token              | Predicate (all conjoined with GATE)                                                  |
|--------------------+---------------------------------------------------------------------------------------|
| =is:overdue=       | =(or (org-air-classify--past-p sched now) (org-air-classify--past-p dl now))= — the Needs-attention bucket's overdue disjunct, verbatim |
| =is:upcoming=      | =(org-air-classify--due-within-p item now org-air-upcoming-days)= — the Upcoming bucket predicate, verbatim |
| =is:stale=         | =(org-air-classify--stale-p item now)= — R54-1 eligibility gate (scheduled ∨ deadline ∨ active-ts) AND activity gap ≥ =org-air-stale-days=; the Stale bucket body, hoisted |
| =is:nodate=        | =(not (org-air-classify--stale-eligible-p item))= — truly dateless under the R54 date model: no scheduled, no deadline, no active =<ts>= anywhere in the subtree.  Deliberately the R54-1 negation, NOT the attention bucket's narrower =(null sched)(null dl)=: an item whose only date is a body =<ts>= is dated (it feeds the calendar and the stale clock) and must not answer "nodate" |
| =is:hipri=         | =(org-air-classify--hipri-p item)= — the High-priority bucket test (=priority ≥ org-priority-highest=), hoisted |
| =due:Nd= / =due:Nw= | ∃ ts ∈ {sched, dl}: =0 ≤ days(now→ts) ≤ N= — i.e. =(org-air-classify--due-within-p item now N)=; =w= = 7×N days |
| =scheduled:Nd/w=   | the same window over =sched= ONLY                                                    |
| =deadline:Nd/w=    | the same window over =dl= ONLY                                                       |

Rulings inside the table:

- *Overdue does NOT count in a window.*  =due:7d= answers "what is
  coming"; =is:overdue= already owns the past, and =M-/= =any=
  composes the union in two tokens.  Keeping the window's inequality
  identical to =--future-or-today-p= (=0 ≤ d ≤ N=) is also what
  makes =due:7d= ≡ the Upcoming bucket a THEOREM at the default
  horizon (probed EXACT), not a test hope.  =due:0d= = today only.
- *The GATE on every token.*  A DONE or ARCHIVED past-due item
  classifies into ZERO buckets (probed) — it renders nowhere; a
  filter that matched it would inflate "N of M shown" with
  invisible rows and break every filter⇔bucket agreement seam.  So
  every date/status predicate conjoins the buckets' own top gate.
- *Value grammar is strict*: =\`(due|scheduled|deadline):[0-9]+[dw]\'=
  — a unit is REQUIRED (=due:7= does not parse; self-documenting
  tokens, and the fall-through stays predictable).  No =due:today= /
  =due:1m= aliases this round (Non-goals).

* Decision 3 — agreement by construction: the classify hoist + one NOW

The filter must not reimplement the buckets' date logic; it must
CALL it.  org-air-classify.el therefore exports the bucket bodies as
named pure predicates, and =--heading-buckets= is rewritten to use
them — a behaviour-neutral refactor, pinned byte-exact (r72-12):

- =org-air-classify--board-active-p (item)= — the factored =unless=
  gate: not =--done-p=, no =org-archive-tag= in tags.
- =org-air-classify--future-or-today-p (timestamp now &optional days)=
  — DAYS horizon, defaulting to =org-air-upcoming-days=; every
  existing caller unchanged.
- =org-air-classify--overdue-p (item now)= — the past-p disjunction.
- =org-air-classify--due-within-p (item now days &optional slot)= —
  SLOT ∈ {=due= (default: scheduled ∨ deadline), =scheduled=,
  =deadline=}; the Upcoming bucket becomes
  =(org-air-classify--due-within-p item now org-air-upcoming-days)=.
- =org-air-classify--stale-p (item now)= — eligibility + clock, the
  bucket's =when=-chain hoisted whole.
- =org-air-classify--hipri-p (item)= — the priority test hoisted.

On the view side, =org-air-view--filter-date-token-match-p (parsed
item now)= dispatches the table of Decision 2 onto exactly these
symbols — the filter contains NO date arithmetic of its own.

*One NOW*: a new defvar =org-air-view--filter-now= (nil ⇒
=current-time=).  =org-air-view--compute-partition= binds it to the
SAME =now= it classifies with, so within one render the filter and
the buckets evaluate against a single instant (and ERT freezes time
by let-binding it).  Off-partition calls fall back to
=current-time= — day-granular predicates, same as classify.

*R53 — no rescan, restated as a contract*: applying a filter is
=setq org-air-view--tag-filter= + a re-render over the CACHED
=org-air-view--items=.  Every predicate above reads struct slots
(=scheduled=/=deadline=/=active-ts=/=activity=/=priority=/=donep=/
=tags=); the only probe in the chain is =--stale-eligible-p='s
live-marker fallback, which resolves ONLY against an already-live
buffer (a cache-hydrated =(FILE . POS)= cons returns nil — the R53
P2 law) and can never open a file.  Pinned with spies (r72-9).

* Decision 4 — an active window token WIDENS the Upcoming horizon

The probe exposed the hole: =sched-plus-8= classifies into ZERO
buckets — the board renders rows bucket-by-bucket, so a =due:2w=
filter would "show" 1 of M while painting no row anywhere.  The
user's literal ask ("the next week or so") lands exactly in this
hole with the default 7-day horizon.

Ruling: /the filter narrows sections; it never invents rows the
buckets don't own — with ONE principled widening: an active window
token extends the Upcoming horizon to its span, so every item the
window selects has a home row./

- =org-air-view--filter-window-days ()= — the MAX days over the
  active filter's parsed window tokens, nil when none.
- Effective horizon = =(max org-air-upcoming-days (or that 0))= —
  widening only, never narrowing (=due:2d= still renders the full
  7-day Upcoming section; the FILTER does the narrowing, the bucket
  keeps its shape — no surprise shrink of an unfiltered axis).
- =org-air-view--classify-cached= binds =org-air-upcoming-days= to
  the effective horizon around its =org-air-classify-item= call —
  the ONE classify choke point (the partition, the sections, the
  rail Summary counts and the fallback path all flow through it),
  and the temp pane buffers already carry the filter var across
  (=--render-lines= binds =org-air-view--tag-filter=).
- The memo key grows: =org-air-view--classify-cache-day= becomes
  the pair (DAY . EFFECTIVE-HORIZON), so toggling a window filter
  rebuilds the memo instead of serving stale buckets — a pure
  slot-fold rebuild, the measured R53 0.26 s warm-refresh class at
  15.9k items, and a NO-OP when the horizon is unchanged (=due:7d=
  at defaults keys identically to no filter — pinned).
- The Upcoming empty-state string (org-air-view.el:2569 reads the
  raw knob) reads the effective horizon too, so it can never
  announce "next 7 days" under a 14-day lens.

=is:upcoming= keeps meaning the KNOB horizon (it widens nothing);
under a mixed =any= filter its matches are a subset of any wider
active window, so every selected row still has a home.  Agreement
survives widening by construction: bucket and filter both read the
same dynamic value.

* Decision 5 — fall-through, labels: the quoting is the tell

=org-air-view--filter-token-parse= returns nil for ANYTHING outside
the closed grammar — =is:urgent=, =due:7=, =due:7x=, a trailing
space (probed table) — and the matcher then runs the existing
#tag/substring branches byte-for-byte.  Nothing errors, nothing
warns mid-fold (R53 never-error; a typo degrades to a text search,
exactly what the pre-R72 board did with the same input).

The tell is the LABEL: =org-air-view--filter-token-label= renders a
token that PARSES verbatim-unquoted (like a =#tag=), while an
unparsed bare token keeps its R24-6 quotes.  So the rail/banner/
mode-line read =is:overdue AND #work= for the real thing but
="is:urgent"= for the typo — the user sees at a glance whether the
board understood a date token or is text-searching.  Storage stays
verbatim either way (R24-6); no face change (TTY-safe goldens).

* Decision 6 — composition: one more predicate under the untouched fold

=org-air-view--tokens-pass-filter-p (text tags &optional item)= —
the ONLY signature change in the fold.  The combinator dispatch
(=seq-every-p= / =seq-some= on =org-air-filter-match=), =M-/=, =\\=,
the pre-filled prompt, chips, scope interplay: all byte-untouched.
A date/status token is just another element of the token list, so
=is:overdue,#work= under =all= is "overdue AND work-tagged",
=is:overdue,due:7d= under =any= is "past OR next week" — the
user's two asks are each ONE filter away, and mixing in free text
(=is:overdue,#work,release= under =all=) needs no new rules
(r72-7).

=org-air-view--passes-filter-p= threads the item;
=--tags-pass-filter-p= (legacy tags-only wrapper) passes no item —
date tokens are vacuously false there, correctly (no slots, no
claim).
