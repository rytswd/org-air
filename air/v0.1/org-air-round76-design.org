#+state: ready

* Summary

USER BUG (verbatim intent): in the edit transient (=e=), the =,=
priority field only walks DOWN — /"when an item starts from C, I can
only choose from C, D, and E"/.  Root cause is by construction:
=org-air-refile-form-priority= (org-air-inbox.el:1337, the cycle at
:1353–:1361) computes =next = (1+ current)= — a ONE-WAY cycle
– → A → … → lowest → – .  From C the only route UP to A is FOUR more
presses through D, E and the unset step; the available range is never
shown; and the unset step doesn't even mean "clear" — =:priority nil=
means UNTOUCHED (both execute legs skip nil), so the form cannot
REMOVE an existing cookie at all today.  Three defects in one field:
no direct up, no visible range, no real clear.

FIX — the R68 law applied to =,=: a chooser, not a blind cycle
(exactly as R68-1 turned the board's =T= from a silent cycle into
select-over-the-vocabulary).  Pressing =,= reads ONE character over
the write target's WHOLE priority range:

- prompt ="Priority %c-%c, SPC clears[, RET keeps %c]: "= — org's own
  =org-priority= idiom (source-read: ="Priority %c-%c, SPC to
  remove: "=), extended with the pre-filled current value, so the
  user SEES every choice;
- ANY in-range letter sets it — A from C is ONE keystroke, up or
  down; lowercase is upcased (org's own rule, source-read + probed);
- SPC (or =-=, the field's own "–" unset glyph) CLEARS — a REAL
  clear: the new =?\s= sentinel in =:priority= flows through BOTH
  existing apply legs byte-unchanged and =(org-priority ?\s)= itself
  removes the cookie (probed, org 9.7.11);
- RET keeps (the field stays as it was; C-g likewise);
- out-of-range input is REJECTED honestly with org's own wording —
  never clamped, never a hang;
- the range is the WRITE TARGET's (=org-air-inbox--target-priority-range=
  over =org-air-inbox--form-write-target= — destination file when
  set, else the item's own file; the R67-4 law byte-kept), read in
  the same buffer the apply-time =org-priority= runs in, so the
  picker and the apply agree by construction;
- =:transient t= stays — the form stays open; the field row and the
  live Preview reflect the pick (WYSIWYG: a cleared pick drops the
  =[#C]= from the previewed heading exactly as RET will write it).

* Decision 1 — the field becomes a one-key FULL-RANGE picker (the R68 chooser law)

The R68 ruling transfers verbatim: /"the user's expectation is
explicit ('give me the list'); a silent cycle is invisible … which
state comes next is undiscoverable"/.  For priority the "list" is a
contiguous char range — small enough to show IN the prompt, so the
chooser is a single =read-char=, not a completion buffer.

New reader in org-air-inbox.el, next to
=org-air-inbox--read-todo-keyword= (the R68-1 shared-reader shape):

- =org-air-inbox--read-priority-char (file &optional current)=:
  1. =range ← (org-air-inbox--target-priority-range file)= — the
     EXISTING helper, untouched: (HIGHEST . LOWEST) read inside
     FILE's own buffer (R57-class: a per-file =#+PRIORITIES:= line
     wins; probe row 7 shows apply-time =org-priority= honours the
     same buffer-local range — reader and apply agree by
     construction).
  2. prompt =(format "Priority %c-%c, SPC clears%s: " high low
     (if current (format ", RET keeps %c" current) ""))= — the range
     (the user-asked "Priority A-E, SPC clears:" surface, org's own
     idiom), the clear option, AND the pre-filled current value, all
     visible before the keystroke.
  3. =read-char-exclusive= with the prompt passed as its PROMPT
     argument (not a separate =message= — the ERT stub then captures
     the prompt as its arg; org's alphabetic branch reads exactly
     this way, source-read).
  4. normalize via Decision 3; invalid → the honest reject; returns
     an in-range CHAR, or ='clear=, or ='keep=.

- The suffix =org-air-refile-form-priority= (name, =,= binding,
  =:transient t=, the description lambda's slot all KEPT — muscle
  memory; nothing pins the cycle) becomes:
  1. =current ← (or (form-get :priority) (item's own char))= — the
     same effective-current expression the cycle uses today, minus
     the =?\s= sentinel (a pending clear shows no "current" to keep:
     =current= is nil then, the prompt omits the RET token).
  2. =choice ← (org-air-inbox--read-priority-char
     (org-air-inbox--form-write-target) current)=.
  3. ='keep= → no =form-put= at all (an untouched field stays
     untouched — the R67 dirty-only law; RET on a virgin field
     leaves =:priority= nil and execute's "Nothing to change" gentle
     no-op intact).
  4. ='clear= → Decision 4's state-aware arming.
  5. a char → =(form-put :priority CHAR)=.

Note (standing class, unchanged): a char picked over one write
target's range is NOT re-validated when the user then changes the
destination — exactly the =k= field's free-typed-keyword class,
which R68 ruled acceptable: apply-time org rejects with an honest
=user-error= inside the transaction (rollback, no partial state),
and re-pressing the field after choosing the destination reads the
NEW range (the R67-4 law does that for free).  Cross-field
revalidation is a Non-goal.

* Decision 2 — reader = single `read-char', argued

- /ADOPTED: one =read-char-exclusive= over the prompt-shown range/.
  Closest to org: =org-priority='s own set branch is exactly this
  read (source table row 8).  Fastest: the user's complaint is
  press-count — every priority, up, down or clear, becomes ONE
  keystroke.  The domain is tiny, contiguous and fully disclosed in
  the prompt, so a selection UI adds nothing.
- /Rejected: =completing-read= over the range letters + "clear"/ —
  minimum two keystrokes (type + RET), minibuffer churn for a
  ≤26-element single-char domain the prompt already shows in three
  characters ("A-E"), and it abandons org's own priority-entry
  muscle memory.  Completion earns its keep where the domain is
  open-ended (files, todo vocabularies) — not here.
- /Rejected: repairing the cycle (two-way — =C-u ,= or a second key
  to go up)/ — still hides the range, still O(distance) presses,
  adds an undiscoverable modifier, and R68 already settled
  chooser-over-blind-cycle as the board's answer to exactly this
  complaint shape.
- /Rejected: delegating to org's own interactive =org-priority=
  (action ='set=) in the target buffer/ — it MUTATES at read time,
  violating the form's R64-2 prompt-time no-mutation contract
  (every field collects; only RET writes), and it would write to the
  item's buffer even when the pick belongs to a refile destination.

* Decision 3 — the pure normalizer; reject over clamp

=org-air-inbox--priority-normalize (key range)= — PURE (no buffer,
no state, no read): maps a raw key to the verb.  The honest
non-interactive seam the batch tests drive WITHOUT any stub:

- =?\s= or =?-= → ='clear= (SPC is org's own remove key; =-= is the
  field's unset glyph "–" made typeable; =?-= (45) can never collide
  with a range char — org cookie chars are alphanumeric, all ≥ =?0=
  (48)).
- =?\r= / =?\n= → ='keep= (RET; C-g never reaches the normalizer —
  =read-char-exclusive= quits first, the suffix is skipped, the
  field keeps its previous value: the R71 note-field C-g shape).
- a char whose upcase lies in [HIGH..LOW] → that char, UPCASED when
  both range ends are uppercase — org's own rule, source-read and
  probed (=?a= → =[#A]=); a lowercase press must not cost a shift.
- anything else → nil.

The reader turns nil into =(user-error "Priority must be between
`%c' and `%c' (SPC clears)")= — org's exact wording (probe row 5)
plus the clear hint.  Under the =:transient t= suffix a =user-error=
surfaces in the echo area and the form STAYS OPEN — one honest line,
press =,= again.

/Reject over clamp, argued/: a clamp writes a priority the user
never pressed — silent wrong data in a field whose entire bug report
is about control; org itself rejects (probe row 5); and R53's
never-error discipline is about not SIGNALLING from background
machinery — a =user-error= on a bad interactive keystroke is the
honest surface (the R68 free-typed-keyword precedent verbatim).
/No re-prompt loop/: single-shot read; a retry loop over invalid
keys is a batch hang risk (R53 never-hang) for zero UX gain.

* Decision 4 — the clear: `?\s' sentinel, org's own vocabulary, armed state-aware

=:priority= becomes an honest TRI-STATE (the defvar doc at :888
updated): nil = untouched (writes nothing — unchanged), CHAR = set,
=?\s= = CLEAR (remove the cookie at apply).

/Why =?\s=/: it is org's own remove vocabulary end-to-end — probed:
=(org-priority ?\s)= removes the cookie, and the source shows the
=(equal new ?\s)= remove branch fires for a PASSED integer action,
not just the interactive read.  Both apply legs —
=--apply-item-edits= =(org-priority (if (stringp p) (aref p 0) p))=
and the engine's identical form at :781 — therefore pass the
sentinel through BYTE-UNCHANGED and org does the removal: ZERO
apply-leg edits, the refile leg strips the cut heading's carried
cookie at the destination, the in-place leg strips it at the source,
and both stay inside their existing transactions (atomic group /
engine transaction, one save — R64/R67 discipline untouched).  The
=(when priority …)= / =(when-let* ((p …)))= gates pass (32 is
truthy).

/Rejected sentinels/:
- ='remove= (also works, probed) — but then =:priority= sometimes
  holds a non-char and every consumer (preview, field row, execute,
  any future reader) needs symbol-awareness; =?\s= keeps the slot
  "a char, in org's own extended alphabet".
- ="" = (the =:scheduled= clear idiom) — =(aref "" 0)= ERRORS in both
  legs; adopting it forces exactly the apply-leg edits this design
  avoids.

/State-aware arming (probe row 6 forces it)/: =(org-priority ?\s)=
on a heading with NO cookie signals =user-error "No priority cookie
found in line"= — inside the in-place atomic group that would roll
back EVERY collected field and error at the user.  So the suffix
arms the sentinel only when there is factually a cookie to remove:

- item HAS a cookie → ='clear= stores =?\s= (a real removal rides
  RET);
- item has NO cookie → ='clear= stores nil — "back to untouched":
  the honest meaning of SPC after picking =?B= on a cookie-less item
  is "drop my pick", and untouched writes nothing.  The field row
  falls back to "–", truthfully identical to never-touched.

Either way SPC means "no priority on the written heading", and the
sentinel can only ever reach an apply leg when the cookie exists —
the user-error class is unreachable BY CONSTRUCTION, not caught.

This also closes the hidden second bug: today the form has NO way to
remove a priority at all (the cycle's unset step is =:priority nil=
= untouched).  R76 gives removal a key, a preview, and a seam.

* Non-goals

- No numeric =#+PRIORITIES= support (e.g. =1 64 32=): a multi-digit
  range needs org's =read-string= branch and the board's entire
  priority model is single-char (=--item-priority-char=,
  =org-air-priority-show=, the badge renderer); the range helper's
  char assumption predates this round.  Alphabetic and single-char
  ranges — the board's documented domain — are covered.
- No board-level priority KEY: the board has no priority verb (the
  R68 audit table confirmed it); adding one — presumably over this
  same reader — is a separate round.
- No cross-field revalidation when the destination changes after a
  pick (the standing =k=-field class; apply-time org rejects
  honestly inside the transaction; re-pressing reads the new range).
- No re-prompt loop on invalid input; no clamping.
- No change to the apply legs, the engine signature, the range
  helper, or =--form-execute='s dirty-only gates.
- No new key, no new defcustom, no transient layout change.
