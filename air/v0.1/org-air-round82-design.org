#+title: org-air Round 82 — The edit-form `,' priority PROMPT is annoying: drop R76's read-char picker for a forward-WRAPPING one-key cycle (none → A → … → E → none), no minibuffer, full up-reachability via wraparound
#+state: ready
#+tags: bug transient refile inbox ux

* Summary

USER REQUEST (verbatim): /"priority change from transient using ',' prompting
explicit A, etc. is annoying, just cycle through instead"/.

R76 reworked the =e= editor's =,= priority field
(=org-air-refile-form-priority=, org-air-inbox.el:1397) from a one-way
cycle into a full-range one-key PICKER: pressing =,= fires
=read-char-exclusive= with the prompt ="Priority %c-%c, SPC clears[,
RET keeps %c]: "= and the user then types an explicit letter (A–E; SPC/=-=
clears; RET keeps).  That fixed R76's real complaint — the pre-R76 cycle
=next = (1+ current)= could not reach a HIGHER priority without walking
D → E → unset → A (and its unset step meant =:priority nil= = UNTOUCHED,
so it could never actually REMOVE a cookie).  But the picker traded the
walk for a PROMPT, and the user now finds the prompt itself annoying:
one keystroke should just advance, not open a minibuffer read.

FIX — keep R76's *reachability + real clear*, drop its *prompt*: =,=
becomes a forward-WRAPPING cycle over the write target's own range, one
slot per press, NO =read-char=, NO minibuffer.  The ring INCLUDES the
cleared slot so clearing stays reachable, and it WRAPS so every priority
stays reachable UP as well as down — R76's up-reachability delivered by
WRAPAROUND, not by a prompt:

: none → A → B → C → D → E → none → A → …          (range A–E)

- One press = one slot forward.  From =[#C]= one press lands =[#D]=;
  from the lowest (=E=) one press lands the cleared slot, the next lands
  =A= (straight back to the top — the wraparound that R76 needed a
  prompt for).
- The cleared slot reuses R76's honest tri-state: on an item that HAS a
  cookie it arms the =?\s= sentinel (a REAL removal at apply — R76
  Decision 4, byte-unchanged); on a cookie-less item it stores nil
  ("back to untouched", writes nothing — same visible no-cookie).
- The range (and thus the ring's span + wrap point) is the WRITE
  TARGET's own =#+PRIORITIES:= range — the EXISTING
  =org-air-inbox--target-priority-range= over
  =org-air-inbox--form-write-target= (R67-4 / R57), read in the same
  buffer the apply-time =org-priority= runs in, unchanged.
- =:transient t= stays: the field row + the live Preview repaint on each
  press (WYSIWYG — the previewed heading shows =[#D]=, then no cookie,
  then =[#A]= as the ring advances), with ZERO preview/field-row code
  change (R76 Decision 5 already renders the tri-state).

ZERO apply-leg changes: =org-air-inbox--apply-item-edits= (:1577) and
the =org-air-refile-item= engine (:784) still pass =:priority= through
=(org-priority (if (stringp p) (aref p 0) p))= untouched — the =?\s=
sentinel rides both legs exactly as R76 shipped it, and the cycle only
ever PRODUCES an in-range char or the clear sentinel, so the apply-time
range check (R76's "range-clamp") is never even exercised by the cycle.
One pure helper REPLACES two (the picker's reader + normalizer are
retired), the suffix body swapped picker → cycle, the =,= binding /
suffix name / =:transient t= / description lambda all KEPT.  No new key,
no defcustom, no README change, org/org-ql only.  NO prompt survives.

* Decision 1 — the field becomes a forward-WRAPPING cycle (the user's ask, R76's reachability kept)

R76's ruling was "chooser over blind cycle"; the user's counter is
narrower and correct for THIS field: a priority is a tiny CONTIGUOUS
ordered domain (≤ range+1 slots incl. "none"), so a forward-wrapping
cycle is fully predictable AND press-cheap — every slot reachable in
≤ range+1 presses, no undiscoverable modifier, no minibuffer.  The
pre-R76 cycle's ONLY real defects were (a) it could not wrap UP cheaply
because its unset step was a dead end (=nil= = untouched, and it sat
between the lowest and =A= so "up from C" still cost four presses) and
(b) it had no real clear.  R82 fixes BOTH inside the cycle: the ring
WRAPS (so "up" is just "keep pressing — you come back around"), and its
"none" slot is R76's honest clear sentinel, not a dead untouched step.

- The suffix =org-air-refile-form-priority= (name, =,= binding,
  =:transient t=, the description lambda's slot all KEPT — muscle memory;
  nothing pins the picker in the codebase, grepped) becomes: compute the
  effective current slot, advance ONE slot via the pure Decision 3
  helper, store the new value.  No =read-char-exclusive=, no =message=,
  no minibuffer, no reject branch (a cycle cannot be "out of range" — it
  only ever hands back an in-range char or the clear slot).

* Decision 2 — the exact ring order + wraparound (INCLUDING the "none" slot)

The ring, over the write target's range =(HIGH . LOW)= (char codes,
=HIGH ≤ LOW=; e.g. =(?A . ?E)=):

: none → HIGH → HIGH+1 → … → LOW → none → HIGH → …

- =range+1= slots: the =(LOW − HIGH + 1)= priority letters PLUS one
  "none" slot.  For A–E that is =none A B C D E= (6 slots) — every
  priority AND the cleared state reachable, the "none" slot deliberately
  IN the ring so clearing needs no separate key (R76's SPC is retired).
- *Advance rule* (one press):
  - =none= (or a nil/untouched cookie-less start) → =HIGH= (the top
    priority — first press lands =A=, the fastest possible "give me the
    highest").
  - a char strictly inside =[HIGH, LOW)= → the NEXT char up
    (=1+ current= — codes are contiguous within an alphabetic range).
  - the char =LOW= (the lowest priority) → =none= (wrap point into the
    cleared slot).
  - an OUT-OF-RANGE or nil current → restart at =HIGH= (see Decision 3).
- *Where a press starts.*  The effective current slot is the field's
  present value, so a press ADVANCES past it (a cycle press is a move,
  never a no-op):
  - field untouched, item =[#C]= → current =C= → press → =D=.
  - field untouched, cookie-less item → current =none= → press → =A=.
  - field already holds a pending char =X= → press → =X='s successor.
  - field holds the =?\s= clear sentinel → current =none= → press → =A=.
- *One-letter range* =(?B . ?B)= (=#+PRIORITIES: B B B=): the ring
  collapses to =none ↔ B= — a clean two-state toggle (press B→none→B).
- Full trace, =[#C]= item, range A–E, starting untouched:
  : C(own) →,→ D →,→ E →,→ none(clear) →,→ A →,→ B →,→ C →,→ D → …
  Six presses return to =C= (now an explicit, byte-identical
  same-value set — R76 r76-12's guarantee), and every slot is passed.

* Decision 3 — the pure cycle helper; effective-current + state-aware "none" arming

One PURE helper REPLACES R76's reader + normalizer — the honest,
stub-free batch seam (no buffer, no state, no read), mirroring R76's
=--priority-normalize= shape (verb-returning, the suffix does the arming):

#+begin_src emacs-lisp
(defun org-air-inbox--priority-cycle-next (current range)
  "Return the priority slot AFTER CURRENT over RANGE — PURE (R82).
The forward-WRAPPING ring the `,' field walks, one slot per press, with
NO prompt and NO read.  RANGE is a (HIGH . LOW) char pair
\(`org-air-inbox--target-priority-range' shape; HIGH <= LOW as codes).
CURRENT is the effective current slot: a CHAR in [HIGH..LOW], or the
symbol `none' (the cleared/untouched slot — nil is read as `none' too).
Returns the NEXT slot: a CHAR in [HIGH..LOW], or the symbol `none'.  The
ring is  none -> HIGH -> HIGH+1 -> ... -> LOW -> none -> ...  so every
priority AND the cleared slot stay reachable in <= range+1 presses
\(R76's up-reachability by WRAPAROUND, not a prompt).  An OUT-OF-RANGE
or nil CURRENT restarts the ring at HIGH — the first press lands the top
priority (a stale pick from a since-narrowed destination self-heals)."
  (let ((high (car range))
        (low  (cdr range)))
    (cond
     ((or (null current) (eq current 'none)) high)
     ((and (integerp current) (<= high current) (< current low)) (1+ current))
     ((and (integerp current) (= current low)) 'none)
     (t high))))
#+end_src

The suffix body (picker → cycle):

#+begin_src emacs-lisp
(transient-define-suffix org-air-refile-form-priority ()
  "CYCLE the priority one slot forward over the WRITE TARGET's range —
one key, NO prompt (R82).  The destination file when one is set, else
the item's OWN file (R67-4).  The ring wraps
none -> A -> B -> ... -> E -> none  (the write target's own range), so
every priority AND the cleared slot stay reachable; `,' advances ONE
slot per press with no minibuffer.  The cleared slot arms R76's `?\\s'
clear sentinel when the item HAS a cookie (a real removal at apply),
else leaves the field untouched (a cookie-less item has nothing to
remove).  RET (execute) applies; the field/preview repaint each press."
  :transient t
  :description (lambda ()                       ; UNCHANGED from R76
                 (org-air-inbox--form-field
                  "priority"
                  (let ((c (or (org-air-inbox--form-get :priority)
                               (let ((item (org-air-inbox--form-get :item)))
                                 (and item
                                      (org-air-inbox--item-priority-char
                                       item))))))
                    (cond ((eq c ?\s) "clear")
                          (c (string c))))))
  (interactive)
  (let* ((item    (org-air-inbox--form-get :item))
         (own     (and item (org-air-inbox--item-priority-char item)))
         (pending (org-air-inbox--form-get :priority))
         (range   (org-air-inbox--target-priority-range
                   (org-air-inbox--form-write-target)))
         ;; effective current slot: a pending clear reads as `none', a
         ;; pending char as itself, else the item's OWN cookie (nil own
         ;; => `none').  A press ADVANCES past this — never a no-op.
         (current (cond ((eq pending ?\s) 'none)
                        (pending pending)
                        (own own)
                        (t 'none)))
         (next (org-air-inbox--priority-cycle-next current range)))
    ;; state-aware `none' arming (R76 Decision 4, verbatim): `?\\s' only
    ;; when the item factually has a cookie to remove — else nil (back to
    ;; untouched); a char stores directly.
    (if (eq next 'none)
        (org-air-inbox--form-put :priority (and own ?\s))
      (org-air-inbox--form-put :priority next))))
#+end_src

- The =none=-slot arming is R76 Decision 4 unchanged: =(and own ?\s)= —
  a real =?\s= removal when a cookie exists, nil otherwise.  This is why
  the apply legs need ZERO edits: the cycle can only ever store a nil,
  an in-range char, or the =?\s= sentinel — exactly the tri-state R76's
  legs already consume.
- =current= reuses R76's effective-current expression =(or (form-get
  :priority) own)= plus the =?\s→none= read; the ONLY new logic is the
  advance, isolated in the pure helper.

* Decision 4 — forward-only; no reverse key (keep it simple)

The ask is "just cycle through".  Forward-wrapping alone makes every
slot reachable in ≤ range+1 presses (≤ 5 for A–E), so a reverse cycle
would save at most a couple of presses at the cost of a SECOND binding,
a second description token, and new muscle memory — reintroducing exactly
the discoverability weight the user just asked us to shed.  R76's audit
confirmed the editor form has no shifted-key/modifier convention to hang
a reverse off cleanly.  DECISION: forward-only, no reverse key this
round.

- A reverse is TRIVIALLY addable later if the user asks — the mirror
  helper is one =cond= (=none→LOW=, =HIGH→none=, else =1- current=) and
  a second suffix bound to, e.g., a =<= — but it is deliberately NOT
  wired now (clearly labelled DEFERRED, Non-goals).  No dead code ships.

* Risks / edges

  is visually identical to "no priority" and writes nothing — correct
  (there is nothing to clear), and r82-9 pins it errors-free.  On a
  cookie'd item it arms =?\s= (real removal); the no-cookie
  =(org-priority ?\s)= error class is unreachable BY CONSTRUCTION.
- A stale pending char from a since-narrowed destination self-heals to
  =HIGH= on the next press (Decision 3's out-of-range restart); r82-5
