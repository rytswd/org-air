* Summary

User feedback on the running board (verbatim):

#+begin_quote
Today SVG is highlighted in blue, and Tomorrow is red -- this is odd.
Anything within a week should be Today's colour now, overdue to be red,
today to be orange, tomorrow is somewhere between today's and this week --
anything more than a week away could be the current default colour
#+end_quote

R85 introduced two DISTINCT standout faces — =org-air-face-day-today= (bold
teal =#00897B= light / =#88C0D0= dark, which *reads blue*) and
=org-air-face-day-tomorrow= (bold rose =#C2185B= / =#BF616A=, which *reads
red*) — and R87 extended them (rule A) across the deadline / scheduled /
neutral arms of =org-air-view--date-label=.  The colour CHOICE was
near-complementary "today ≠ tomorrow" — but the user reads the result as
*wrong-signed*: TOMORROW in red is *alarming* (red should mean OVERDUE,
the genuinely critical case), and TODAY in a cool teal/blue reads *calm*
exactly when it should read *hot*.  The two faces stand out, but they do
not encode *urgency* — a nearer date is not visibly hotter than a further
one, and the hottest colour (red) is spent on TOMORROW instead of OVERDUE.

R88 replaces the *binary* today/tomorrow highlight with a *PROXIMITY
HEAT-RAMP*: the date cell's colour now encodes how *close / urgent* the
date is, warmest when nearest.  Five buckets, keyed on the SAME
=--days-between= delta R85/R87 already compute:

| bucket    | delta   | colour                                          |
|-----------+---------+-------------------------------------------------|
| OVERDUE   | < 0     | RED (the existing =org-air-face-overdue=, urgent)|
| TODAY     | = 0     | ORANGE (=org-air-face-day-today=, recoloured)   |
| TOMORROW  | = 1     | a BLEND between today's orange and this-week    |
|           |         | (=org-air-face-day-tomorrow=, recoloured)       |
| THIS WEEK | 2 … 6   | AMBER — a calmer warm (=org-air-face-day-week=, NEW)|
| BEYOND    | ≥ 7     | the slot's CURRENT DEFAULT face (deadline /     |
|           |         | scheduled / date — UNCHANGED)                   |

That is a natural rougier RED → ORANGE → AMBER → default ramp: read from
overdue outward it *cools* monotonically, so "hotter = more urgent /
nearer" is legible at a glance, and RED is reserved for OVERDUE exactly as
the user asked.

*What R88 keeps from R87 verbatim* (only the RAMP of faces changes):

- *R87 rule A — the reach across all three arms.*  The ramp is applied on
  the deadline, scheduled AND neutral date arms (a today/tomorrow/this-week
  date wins its slot); a BEYOND date falls through to the slot face
  (deadline keeps deadline, scheduled keeps scheduled).  R88 does NOT edit
  those arms — it only widens what =org-air-view--day-relative-face=
  returns (2 levels → 5) and recolours / adds the faces it returns.
- *The svg-pill mechanism.*  The board date pill has NO separate colour
  path — =org-air-view--svg-pillify= draws its label =:fill (face-
  foreground FACE)=, so the pill colour IS the text face's foreground.
  Recolouring the faces therefore repaints the pill automatically, in the
  same face-only move that repaints the plain text; no svg edit, no new
  pill parameter (R87 §Investigation, unchanged).

*The one alignment R88 must make.*  =org-air-face-overdue= reads red in
LIGHT (=#C62828=, Red800) but its DARK tier inherits =org-air-face-critical=
= *Nord13 =#EBCB8B=, a pale AURORA YELLOW* — NOT red.  A yellow overdue is
*cooler* than a this-week amber and would INVERT the ramp in dark mode
(overdue would look less urgent than a nearer date).  So R88 gives
=org-air-face-overdue= an explicit R79 spec that reads RED in *both* tiers
(light =#C62828= kept, dark aligned to *Nord11 =#BF616A=*, the aurora RED)
— the "else align" the brief flagged.

This stays a *face-only* change (R53): the label BYTES
("Today"/"Tomorrow"/"Wed"/"17 Jul") are untouched — the helper returns
only a FACE — so every text golden is byte-identical; only the GUI pill /
coloured-text PIXELS repaint.  R79 (explicit light+dark hex + TTY
=:inherit= fallback + "exact hex GUI-confirm-only") is respected for all
four faces.

SPEC ONLY: no =.el= or test edits in this change.  The R85/R87 today
/tomorrow COLOUR assertions and the R87 delta≥2 seam are now WRONG under
the ramp and are enumerated for re-blessing (§ERT).

* Decision (stated first — the proximity ramp supersedes the binary highlight)

*The date cell is coloured by PROXIMITY on a five-level heat-ramp, keyed
on the SAME =org-air-view--days-between= delta as =--human-date=:*

#+begin_example
delta < 0   → OVERDUE   → org-air-face-overdue      (RED, urgent)
delta = 0   → TODAY     → org-air-face-day-today    (ORANGE)
delta = 1   → TOMORROW  → org-air-face-day-tomorrow (orange↔week BLEND)
2 ≤ delta ≤ 6 → THIS WEEK → org-air-face-day-week   (AMBER, calmer warm)   ← NEW
delta ≥ 7   → BEYOND    → (the slot face, UNCHANGED: deadline / scheduled / date)
```

*Boundary exactly as the brief states — "a week = 7":* delta 6 is the LAST
this-week day (=org-air-face-day-week=); delta 7 is the FIRST beyond day
(falls through to the slot face).  The band is =2 ≤ delta ≤ 6=, i.e.
=(<= 2 delta 6)=.

*Why a heat-ramp, superseding R85's "distinct" / R87's "reach":*

1. *The user's model is URGENCY, not identity.*  R85 chose two
   *near-complementary* hues so today and tomorrow were unmistakably
   DIFFERENT from each other — a *categorical* distinction.  The user does
   not want categories; they want a *gradient*: "overdue to be red, today
   orange, tomorrow between today's and this week."  A ramp where warmth
   tracks nearness is exactly that, and it fixes the two specific
   complaints — TOMORROW stops being red (red now means only OVERDUE) and
   TODAY stops being blue/teal (it is now the hot orange).

2. *Red must mean the critical case.*  Spending the hottest, most-alarming
   colour on TOMORROW (a not-yet-late date) while OVERDUE sat in a
   *different* red — or in dark mode a *yellow* — is precisely the "odd"
   the user reported.  On the ramp, RED is the single most-urgent bucket
   (OVERDUE); everything not-yet-due is warm-but-not-red; everything far is
   calm.  One colour, one meaning.

3. *A gradient degrades gracefully to "default" at the horizon.*  Beyond a
   week the cell returns to its slot identity (deadline orange, scheduled
   blue/purple, neutral grey) — so the board is not a wall of warm cells;
   the heat is spent only where proximity matters (the coming week), and a
   far date reads exactly as it does today.  This is the user's "anything
   more than a week away could be the current default colour," verbatim.

4. *Minimal change surface — R87's routing already delivers the reach.*
   R87 wired =(or (org-air-view--day-relative-face SLOT now) 'org-air-face-
   SLOT)= into the deadline / scheduled / notes arms.  A five-level helper
   drops straight into that same call — no arm edit, no new call site.
   R88 is therefore a *faces + one helper body* change: recolour two
   faces, add one, align one, and widen the helper's =cond=.

*The one nuance to state up front — the user's "within a week should be
Today's colour" is refined by their own follow-on.*  The opening clause
reads "anything within a week should be Today's colour", but the same
sentence then graduates it — "today to be orange, tomorrow is somewhere
between today's and this week."  So THIS-WEEK is NOT literally today's
orange; it is its own *calmer warm* (amber), one step cooler than
tomorrow, so the ramp reads as *decreasing* urgency from today outward.
Taking the refined, graduated reading (5 distinct buckets) honours the
whole sentence; a literal "everything within a week is identical orange"
would contradict the "tomorrow between today and this-week" clause that
immediately follows.  *This is the interpretation flagged for confirm* —
if the user truly wants a flat within-a-week orange (only 3 buckets:
overdue-red / week-orange / beyond-default), collapsing TOMORROW and
THIS-WEEK onto =org-air-face-day-today= is a one-line helper change and
=org-air-face-day-{tomorrow,week}= simply go unused; the spec is written so
that pivot is trivial.

*OVERDUE is a SLOT concern, never the helper's.*  A delta<0 date is caught
by the two =overdue= arms of =--date-label= that PRECEDE the deadline
/scheduled arms — they emit "OVERDUE Nd" in =org-air-face-overdue= (RED).
The helper is only ever consulted on the deadline / scheduled / notes arms,
where a deadline/scheduled delta<0 is UNREACHABLE (the overdue arm fired
first) and a *neutral* delta<0 is an ordinary OLD log date that must stay
its default grey — an old note is *not* "overdue."  So the helper returns
=nil= for delta<0 (fall through to the slot's default), and the RED-for-
overdue bucket is realised structurally by the pre-existing overdue arms,
not by the helper.  This is the correct split: it keeps a stale note from
ever flashing critical-red.

* Investigation (read the code)

** The helper and the delta convention — the two levels R85/R87 built

=org-air-view--day-relative-face= (org-air-view.el:2030) today:

#+begin_example
(let ((now (or now (current-time))))
  (pcase (org-air-view--days-between now time)
    (0 'org-air-face-day-today)
    (1 'org-air-face-day-tomorrow)))
```

=(org-air-view--days-between now time)= = =(- (time-to-days time)
(time-to-days now))= — POSITIVE in the FUTURE (delta 0 = today, 1 =
tomorrow, ≥2 = further out), NEGATIVE in the past.  This is the SAME delta
=--human-date= (org-air-view.el:2017) keys on, so "Today"/"Tomorrow"/"%a"
and the face agree by construction.  The helper answers only {0,1} today
and =nil= otherwise; R88 widens it to the five-level =cond= (D2) — the
delta and its sign are already computed, nothing new is read (R53).

** The call sites — R87's three-arm wiring, REUSED VERBATIM

=org-air-view--date-label= (org-air-view.el:2064) cond, after R87 lands
(rule A):

#+begin_example
(cond
 ((and deadline  (> (days-between deadline now) 0)) …'org-air-face-overdue) ; OVERDUE past DL
 ((and scheduled (> (days-between scheduled now) 0)) …'org-air-face-overdue) ; OVERDUE past SCHED
 (deadline  (cons (--human-date deadline now)
                  (or (--day-relative-face deadline now)  'org-air-face-deadline)))  ; ARM 3
 (scheduled (cons (--human-date scheduled now)
                  (or (--day-relative-face scheduled now) 'org-air-face-scheduled))) ; ARM 4
 ((eq bucket 'attention) (cons "no date" 'org-air-face-date))
 ((eq bucket 'notes)
  (when-let* ((activity (org-air-item-activity item)))
    (cons (--human-date activity now)
          (or (--day-relative-face activity now) 'org-air-face-date))))          ; ARM 6
 ((eq bucket 'stale) (cons "· Nd quiet" 'org-air-face-date)))
```

- Arms 3 / 4 / 6 all read =(or (--day-relative-face SLOT now) 'org-air-face-
  SLOT)= — the helper WINS when non-nil, else the slot face.  R88 does NOT
  touch these arms.  Widening the helper to return =org-air-face-day-week=
  for delta 2..6 makes those arms paint amber for a this-week date, and
  the helper's =nil= for delta ≥7 (and delta <0 on the notes arm) falls
  through to the slot face exactly as now.
- The two =overdue= arms PRECEDE 3/4 and fire for PAST deadline/scheduled
  → =org-air-face-overdue= (the RED bucket).  A deadline/scheduled delta<0
  never reaches the helper.
- =attention= ("no date") and =stale= ("· Nd quiet") never emit a relative
  date and never call the helper — untouched.

*Consequence:* R88's render-side change is *zero arm edits* — the helper
body plus the faces are the entire surface.  (Prerequisite: R87's rule-A
routing, currently =ready=; R88 layers on it.  If R88 lands before R87, it
must land R87's arm rewire too — but the arm form is R87's, not R88's.)

** The svg crux — unchanged from R87 (the pill colour IS the face fg)

=org-air-view--item-date-text= (org-air-view.el:3615) hands the =(LABEL .
FACE)= to both the plain-text branch and =org-air-view--svg-pillify=

** D2 — extend the helper to the five-level ramp

=org-air-view--day-relative-face= (org-air-view.el:2030) gains the
this-week band; delta<0 and delta≥7 stay =nil= (fall through):

#+begin_example
(defun org-air-view--day-relative-face (time &optional now)
  "Return the R88 PROXIMITY heat-ramp face for TIME relative to NOW, else nil.
Keyed on the SAME `org-air-view--days-between' delta as `--human-date' (so
the label and the face agree by construction):
  delta = 0     → `org-air-face-day-today'    (ORANGE)
  delta = 1     → `org-air-face-day-tomorrow' (the today↔week blend)
  2 ≤ delta ≤ 6 → `org-air-face-day-week'     (AMBER — this week)
  delta < 0     → nil  (a PAST date: a deadline/scheduled is already caught
                        by the OVERDUE arm → `org-air-face-overdue'; a
                        neutral note keeps its default `org-air-face-date')
  delta ≥ 7     → nil  (BEYOND a week → the slot's default face)
Returned to the deadline / scheduled / notes arms of `org-air-view--date-
label' (R87 rule A), so ANY date within the coming week reads warmer the
nearer it is; a date ≥7 days out reads the slot default.  OVERDUE (delta<0)
is owned by the slot's OVERDUE arm, not this helper (a stale note must not
flash critical-red)."
  (let* ((now (or now (current-time)))
         (delta (org-air-view--days-between now time)))
    (cond
     ((= delta 0) 'org-air-face-day-today)
     ((= delta 1) 'org-air-face-day-tomorrow)
     ((<= 2 delta 6) 'org-air-face-day-week))))   ; delta<0 and delta≥7 ⇒ nil
```

- The band =(<= 2 delta 6)= is the exact "a week = 7" boundary: delta 6 →
  amber, delta 7 → =nil= → slot face.
- delta<0 → =nil= by construction (no cond arm matches) — the split that
  keeps a past neutral note on its default face and lets the OVERDUE arm
  own the red (§Decision).
- delta≥7 → =nil= → slot face — BEYOND reads the slot default.

That is the WHOLE render change: one =cond= widened.  The three
=--date-label= arms are R87's and are UNTOUCHED; =--human-date= (label
bytes), =--item-date-text=, =--svg-pillify=, =--compute-meta-widths= are
all UNTOUCHED.
