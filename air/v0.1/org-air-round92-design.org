* Summary

R91 fixed the reported board defect (=m= scrolled the buffer) and was
approved.  The distinguished review of R91
(=/tmp/org-air-ace/fable-review/REPORT-r91.md=) then found three things the
round's own audit should have caught, one of them *introduced by R91*:

1. *R91 regression.*  =org-air-view--refresh-current= wrapped the WHOLE mode
   dispatch in the scroll seam, but the project / revisit / review renders
   deliberately RE-LAND point on their first row.  Pinning a *stale* offset
   onto a *deliberate new* landing scrolled those views' banner,
   state-summary line and column header off the top of the window.
2. *Two in-class misses, pre-existing.*  =org-air-review-toggle-section=
   (TAB) and =org-air-project-toggle-dropped= (TAB) are the user's original
   complaint verbatim in other views — point preserved on the very row the
   user is standing on, =window-start= collapsed to =point-min=, the row
   thrown off-screen.  R91's claim "same class hunted elsewhere — nothing
   else to fix" is *retracted*.
3. *The landing policy is itself the defect, and a worse one.*  =g=, sort,
   group-by, rollup, surface, period nav and the shared =b= backlog verb in
   the project / revisit / review views threw the cursor to row 1.  There
   *point itself* is lost, not merely the viewport.

R92 answers all three with ONE rule, plus the two per-window / correctness
follow-ups the review filed:

#+begin_quote
*A repaint PRESERVES the row the user is on — in every org-air view.  It
lands on the view's first row ONLY when that row's identity has genuinely
vanished, and when it does, it says so, and the scroll seam stands down for
the window that jumped.*
#+end_quote

Implemented on 2026-07-28.  Four production files changed
(=org-air-view.el=, =org-air-project.el=, =org-air-revisit.el=,
=org-air-review.el=); no test, fixture, golden, README or known-failures
byte was touched.

* Why the R91 suite could not see its own regression

This matters more than the bug.  =tests/org-air-round91-test.el= is a good
file — 31 tests, 22 RED on the parent, four mutations each pinned — and it
is *blind to the regression the same round shipped*.  Two reasons:

1. *The other-view tests assert only ON-SCREEN-NESS.*
   =org-air-r91-review-shared-refresh-lands-on-screen= and its revisit twin
   assert =offset < window-body-height= and =window-point = point=.  Both
   are true *with* and *without* the header-scrolls-off behaviour: the
   landing is on screen in both worlds; what differs is *what else is on
   screen above it*.  The reviewer confirmed this independently — the
   minimal fix changes the behaviour and all 31 tests still pass.
2. *No test names the view's own chrome.*  The banner, the state-summary
   line and the column header are the only things that disappear, and no
   assertion in the file (or in the other 94) says "the banner is visible".
   The suite asserts what the renderer PRODUCES; the regression is about
   what the WINDOW SHOWS.

The lesson R92 records: for a viewport rule, "the landing is visible" is
not an assertion with teeth.  The assertion with teeth is *"row X is on
screen line N AND the view's first line is/ is not above it"*.  Every
measurement in this document is stated in that form.

Green tests were therefore NOT treated as evidence in this round.  Every
claim below is a measured number in a real window, taken twice: once on a
clean checkout of =main= (=pppqmqrtvqyz=, R91) at =/tmp/org-air-r92-parent=,
once on this working copy.

* Decision 1 — the uniform landing rule

The board has had =org-air-view--save-position= / =--restore-position=
since D5.  The other three views ended their render with an unconditional

: (goto-char (point-min))  +  --next-doc / --goto-first-row

i.e. an unconditional JUMP.  R92 gives them the same pair, generalised.

** The token

=org-air-view--landing-save= returns

: (:ids ((PROP . VALUE) ...) :line LINE :column COLUMN)

taken from the row point is on, BEFORE the erase.  =:ids= is the row's
identity properties in preference order, per mode:

| mode      | identity properties, in order                            |
|-----------+----------------------------------------------------------|
| project   | =org-air-marker= (the doc's FILE), =org-air-dropped-fold=, =org-air-section= |
| revisit   | =org-air-marker= (the note's FILE), =org-air-more-row=      |
| review    | =org-air-marker= (the item's =(FILE . POS)=), =org-air-section= |

Keying on =org-air-marker= rather than on the =org-air-doc= / entry /
=org-air-item= value itself is load-bearing: those carry state and mtime
slots that CHANGE under =g=, so an =equal= match on the whole value would
make every refresh look like a vanished row and would have re-introduced
the very defect being fixed.  The marker is the stable identity the render
already puts on every row.

The token is nil — so the render lands on its own first row exactly as
before — when the buffer is empty (first paint), when point is not on a row
(the banner, a blank line), or when the render is an explicit ENTRY.

** The restore

=org-air-view--landing-restore TOKEN FALLBACK=:

- the first identity that still resolves wins; point lands on that row's
  TITLE (R21-2) and then advances to the saved column *only when the column
  is to the RIGHT of the title* (R21-1) — never into the gutter, never past
  the row's last visible glyph.  This is the two-edged clamp
  =org-air-view--normalize-point-now= applies on the board, expressed
  directly, because that helper is board/project-only;
- when nothing resolves, FALLBACK places the view's own first-row landing
  and the buffer-local =org-air-view--landing-jumped= records that this
  repaint JUMPED.

** Where the pair is applied

Inside each view's own =--render=, which is the single funnel every command
in that view goes through.  =org-air-project--render=,
=org-air-revisit--render= and =org-air-review--render= are now three-line
wrappers around a =--render-body=; the wrapper also opens the R91 scroll
seam (Decision 3).  Nothing else had to change for =g=, =s= sort, the
group-by keys, =(= filenames, =/= filter, =<= =>= =.= period nav, =m=
range/surface, =+= =-=, =f= rollup, =s= =S= scope, =z c=, paging, the
debounced resize repaint, the paced cold-fill repaints and the shared =b=
backlog verb to inherit it.

** The exceptions that genuinely remain

Every one is an explicit JUMP — the caller asked to go somewhere else, so
it owns its landing:

| exception                          | mechanism                                        |
|------------------------------------+--------------------------------------------------|
| bookmark restore (R58/R61-6)       | =--bookmark-consume= runs AFTER the landing restore and overrides it; the seam excludes the jumping window (Decision 4) |
| view ENTRY: =org-air-project=, =org-air-revisit=, =org-air-review= (and their bookmark handlers, which share =--open-core=) | =org-air-view--landing-entry= bound to t: no token is taken, the first-row landing stands.  Board OPEN was already excluded for the same reason |
| board OPEN (=org-air=, cold/cached/deferred first paints) | unchanged from R91                     |
| =org-air-visit-item='s =recenter=  | a different buffer, an explicit jump; unchanged  |
| plain motion (=org-air-next-section=, =n=/=p=, TAB's third branch) | no repaint, so no seam and no landing pair; ordinary Emacs scrolling is right |

That is the whole list.  There is no per-view exception left: the
"land on the first row" behaviour survives only where it is *correct*
(nothing to preserve), not where it was merely *inherited*.

* Decision 2 — the R91 regression dissolves into the rule

The fix the reviewer verified (wrap only the board leg of
=org-air-view--refresh-current=) restores parent behaviour, but it is a
per-view exception in the shared dispatch — exactly the shape the review
warned about.  With Decision 1 in place a better answer exists, and the
brief asked for it: keep the dispatch UNIFORM and make the *render* say
whether it preserved or jumped.

- render PRESERVED the row → the seam anchors it.  That is now meaningful
  in all four views, which it never was before.
- render JUMPED (=org-air-view--landing-jumped=) → =--scroll-restore=
  leaves the ACTING window's =window-start= to redisplay.  The window's
  POINT is still repaired (the erase clobbered that marker too); only the
  invented offset is dropped.

That is what keeps the project banner on screen, and it keeps it on screen
*by rule* rather than by mode dispatch.

A command that re-lands point ITSELF after the render (the two TABs of
Decision 3) calls =org-air-view--landing-claimed= to clear the mark: its
landing is the user's row, so the seam must anchor it.

* Decision 4 — the R58 bookmark exclusion is now PER WINDOW

R91 returned nil from =--scroll-anchors= whenever a bookmark locator was
armed, i.e. it dropped EVERY window on that board, not just the one
jumping.  The rule is now stated the way the design always argued it: *the
jumping window owns its landing AND its viewport; a bystander owns its
own.*

The jumping window is the SELECTED window when it displays the buffer (a
bookmark jump runs there); otherwise the window whose point is the buffer
point.  Every other window keeps its own identity token and its own offset.

* Decision 5 — three seam-correctness fixes

** (a) =--with-scroll-stable= is UNWIND-protected, not =prog1=

A repaint that signals mid-render skipped the restore entirely and left
every displaying window's =window-start= at =point-min= — the erase had
already clobbered it — so the one case where the user most needs their
place kept was the one case that lost it.  Both halves still swallow their
own errors, so the restore can never turn a render failure into a second
failure.

Measured (board, 60 rows, window body 22, row parked at screen line 6; a
repaint that re-inserts the text and then signals in its tail):

| revision | after the signal        |
|----------+-------------------------|
| R91      | ws=3241 → *1*, off 6 → *46* (off-screen) |
| R92      | ws=3241 → 3241, off 6 → 6 |

** (b) ONE anchor/restore pair per keystroke

=--refresh-current= → =--render-current= nested two pairs per =m=.
=org-air-view--scroll-stable-active= now records the BUFFER whose seam is
open, and an inner seam over the SAME buffer is a pass-through.  The buffer
is recorded rather than a bare flag so a repaint that renders a DIFFERENT
org-air buffer inside the seam still anchors that buffer's own windows.
The OUTER pair is by construction the one taken before the erase and closed
after the final landing, so collapsing to it is not merely cheaper, it is
the correct pair.

Measured, one =m= on the board: =anchors=2 restores=2= (R91) →
=anchors=1 restores=1= (R92).

** (c) =--scroll-anchors= no longer invents an offset

=count-screen-lines= takes the ABSOLUTE distance between its bounds, so a
window whose point sits ABOVE its =window-start= (the user scrolled the row
off the top) measured a fictitious offset and anchored it.  There is no
screen line to preserve for a row that was not on screen.  OFFSET is now
nil for such a window and the seam does not set its =window-start=;
ordinary redisplay re-anchors, which is exactly what Emacs does for an
off-screen point.  That window's POINT is still repaired.

Measured (board, window scrolled 10 lines past point):

| revision | offset recorded | after =m=                       |
|----------+-----------------+---------------------------------|
| R91      | 10 (fictitious) | ws=2917 (a made-up anchor)      |
| R92      | nil             | seam does not set it — redisplay owns it |

* Retraction

R91's design says:

#+begin_quote
"Same class hunted elsewhere — nothing else to fix. … The project, revisit
and review views' OWN commands do move the viewport — but they do so
because those renders deliberately RE-LAND POINT on the first row … it is a
LANDING-POLICY question, not the R91 scroll class."
#+end_quote

That is *retracted*.  Two of those commands (=org-air-review-toggle-section=,
=org-air-project-toggle-dropped=) are the R91 class exactly — point
preserved, viewport lost — and the landing policy itself was a defect, not
a policy.  R91's hunt drove every =erase-buffer= site and every view's
=--render-current= entry point; it never drove the views' TAB commands,
which repaint and THEN move point, so the miss was structural.
