#+state: complete

* Summary

The board's =Needs attention= rule was *"board-active AND (overdue OR (no
scheduled AND no deadline, non-inbox))"*.  The second disjunct made
"not having a date" the single largest reason to be nagged, which
inverted the product: the cheapest way to stop being nagged was to lie
(invent a date) or to game the board (=:backlog:= everything).  R93
deletes that disjunct outright and rebuilds the surface around what the
user actually asked for:

- *Needs attention* = board-active AND (days since last update) >=
  threshold(priority).  =#A= threshold 0, so it always surfaces.  No date
  is required, and no date grants an exemption.
- *Overdue* is its own bucket and its own section.
- *Stale* is retired; its "dated but quiet" rule is subsumed.
- Section order is now *Inbox, Overdue, Upcoming, High priority, Needs
  attention*, then Notes, then Backlog last.
- Recency is a real per-heading scan-time fact (=updated=), not a guess.

Design and implementation landed together, on 2026-07-29.

* Decisions and who made them

** Made by the user (implemented, not relitigated)

2. *Aging thresholds*, tunable via defcustom: =#A= always; =#B= 7 days;

3. *Overlap stays*: buckets remain non-exclusive; an item may appear in

4. Design and implementation land in the same round.

** Ruled by the requesting seat (design rulings, all followed)

5. *Overdue is its own bucket and section*, no longer part of attention.
6. *Needs attention = board-active AND age >= threshold(priority)*; =#A=
   threshold 0 means it always surfaces; no date required, no date
   exemption.
7. *Stale is RETIRED.*  Keep =is:stale= as an alias for the new aging

   cheap (one alist entry); kept as a *parse-only* alias.
8. *Section order*: Inbox, Overdue, Upcoming, High priority, Needs

9. *Filter/bucket agreement by construction* preserved: one predicate per

** Judged by this seat (with reasons)

10. *No inbox carve-out in the attention rule.*  The pre-R93 code
    suppressed the no-date default for inbox dwellers (ruling
    =xsqrnoyn=: "a schedule-less inbox capture is unfiled, not needs
    attention").  That exemption existed only to protect captures from
    the *no-date default*, and that default is gone.  Ruling 6 states a
    *total* rule, and adding a carve-out would make it un-teachable.  A
    capture that has sat untouched past its threshold genuinely does
    need attention; it simply shows in *both* Inbox and Needs attention,
    which is the standing overlap rule (decision 3), and a *fresh*
    capture (age 0, or a =:CREATED:= stamp) never surfaces at all.  The
    xsqrnoyn intent — "do not nag about brand-new captures" — is
    preserved by the clock rather than by an exception.
11. *=is:attention= added, =is:stale= kept but not offered.*  Ruling 9
    asked for an aging predicate token; the honest spelling is
    =is:attention=.  =is:stale= still parses (aliased) so bookmarks and
    muscle memory degrade honestly, but it is *removed from ~/~
    completion* so the vocabulary org-air teaches is the current one.
12. *The row reason lives in the existing date cell*, not a new column
    (see [[*Making the reason legible][Making the reason legible]]).
13. *The R74 inspector =Updated= line gained the new fact as a fourth,
    strictly-greater candidate* so that the number the inspector shows
    and the number the bucket used cannot drift.  Not asked for; the
    alternative was two adjacent numbers in the same pane disagreeing.

* The recency fact

** Definition

=org-air-item-updated= — a new scan-time slot, an INTEGER epoch or nil:

#+begin_quote
The newest *non-future inactive* Org timestamp in the heading's *own
body* (the region between the heading line and its first child),
=nil= when the region holds none.
#+end_quote

That single definition subsumes every shape Org writes when something
*happened*, because Org writes them all as inactive stamps in that
region:

| Shape                                   | Example                                     |
|-----------------------------------------+---------------------------------------------|
| LOGBOOK state change                    | =- State "DONE" from "TODO" [2026-06-15 …]= |
| LOGBOOK note                            | =- Note taken on [2026-06-15 …]=            |
| Clock-out                               | =CLOCK: [… 10:00]--[2026-06-15 11:00]=      |
| Completion stamp                        | =CLOSED: [2026-06-15 …]=                    |
| Capture stamp                           | =:CREATED: [2026-06-01 …]=                  |
| A stamp the user typed in the body      | =[2026-06-14 Sun]=                          |

Active =<timestamps>= are *not matched by the regexp at all*
(=org-ts-regexp-inactive=), which is the mechanical guarantee behind the
ruling: a =SCHEDULED=, a =DEADLINE= or a bare plan date can never move
this clock.  A plan is not an update.

Two deliberate refinements:

- *Own body, not subtree.*  A child's LOGBOOK belongs to the child's
  row; crediting it to the parent would make a busy child silence its
  parent forever.  This matches R61's rollup reasoning exactly and reuses
  its already-computed =child-pos= bound.
- *Future stamps are skipped.*  A stamp dated after the scan day is a
  note *about* the future, not an update; letting it win would silence
  the heading until that date arrived.  Age is additionally floored at 0
  at classify time, so clock skew can never read as negative (which
  would have suppressed a =#A=).

** The coarse fallback, stated plainly

When a heading carries *no history at all* — no LOGBOOK, no =CLOSED:=,
no =:CREATED:=, no body stamp — =org-air-classify-updated= falls back to
the *file's* scan-time modification time, read out of the per-file meta
table (=org-air-query-file-meta= =:mtime=): a hash lookup on a table the
cache hydrates, never a =file-attributes= call at classify time.

*This is coarse and we are not hiding it:* one edit anywhere in a file
refreshes the clock for *every* historyless heading in that file.  A user
with one 2000-line =tasks.org= of bare =* TODO= lines therefore sees
Needs attention behave file-at-a-time until those headings gain real
stamps.  We chose this over the alternatives:

- Guessing a per-heading date from position or file order — dishonest.
- Writing =:CREATED:= into the user's files on first sight — org-air
  does not write to files it was not asked to write to.
- Treating "no history" as infinitely old — every fresh corpus would
  nag on day one.
- Treating "no history" as fresh forever — an untouched file would never
  surface, which is the exact failure the user reported.

The floor self-heals: the moment a heading gains one state change, note
or =CLOSED:= stamp it gets its own clock.  Turning on =org-log-done= and
=org-log-into-drawer= is the one-line configuration that makes org-air's
attention model per-heading accurate, and the README says so.

Nil at both levels (no slot *and* no file meta — an item built outside
the scan, e.g. in a capture buffer) means *unknown*, never "fresh": a
=#A= still surfaces (threshold 0 is unconditional), everything else does
not.  org-air refuses to nag about something it cannot date.

** Cost: one pass, no extra reads, no timers

The probe is one bounded =re-search-forward= walk over the *same*
=[body-start, bound)= region =org-air-query--harvest-at-point= already
walks twice (clock lines, log lines), reusing the same =end= and
=child-pos= it already computed.  No second pass over the buffer, no
extra file read, no new timer, no new buffer.

Inside the walk, stamps are compared as *strings*: Org's
=YYYY-MM-DD Dow HH:MM= shape sorts lexicographically by construction (the
date sorts first, and a given date always carries the same day name), so
the region costs one regexp walk plus *exactly one*
=org-parse-time-string= per heading instead of one per stamp.  The whole
thing rides the harvest's existing per-heading =condition-case= net, so a
malformed entry degrades that heading to =nil= and nothing else.

The probe reads =org-ts-regexp-inactive= *group 0*, not group 1:
whether group 1 includes the brackets has differed across Org versions
(Emacs 30's Org excludes them), and group 0 is the whole =[…]= in every
version.  This was found by measurement, not by reading — the first
implementation silently returned =nil= for every heading.

* The classification rules

** New / changed predicates (org-air-classify.el)

| Predicate                               | Meaning                                        |
|-----------------------------------------+------------------------------------------------|
| =org-air-classify--overdue-p=           | unchanged body, now the *Overdue bucket* itself |
| =org-air-classify--attention-p=         | NEW: age >= threshold(priority), or threshold 0 |
| =org-air-classify-attention-threshold=  | NEW (public): the days for this item's priority |
| =org-air-classify-updated=              | NEW (public): the recency epoch, no file access  |
| =org-air-classify-quiet-days=           | NEW (public): age in days, floored at 0          |
| =org-air-classify--priority-char=       | NEW: cookie value → letter                       |
| =org-air-classify--dated-p=             | renamed from =--stale-eligible-p= (alias kept)   |
| =org-air-classify--stale-p=             | *DELETED*                                        |
| =org-air-stale-days=                    | *DELETED*                                        |

Three of them are *public* on purpose: the row label, the rail inspector
and the bucket must all quote the same number, so they call the same
function rather than each re-deriving it.

** The thresholds

#+begin_src elisp
(defcustom org-air-attention-days
  '((?A . 0) (?B . 7) (?C . 14) (?D . 30) (?E . 30) (nil . 30)) …)
(defcustom org-air-attention-default-days 30 …)
#+end_src

Keyed by the priority *letter* (Org stores the cookie as
=1000 × (org-priority-lowest − letter)=; =--priority-char= inverts that),
with the =nil= key for "no cookie".  =?D= and =?E= are listed explicitly
even though they equal the =nil= fallback — a user reading the alist
should see the whole table, not have to infer it.

The alist joins the render-time classify memo key alongside
=org-air-backlog-tag=, so retuning it mid-session self-invalidates on the
next repaint (a slot-fold rebuild) and never forces a rescan.  It is not
a *scan* key input: no threshold changes what a file means.

* Sections, order and presentation

** Order

#+begin_src elisp
'((inbox         "Inbox"          "Inbox zero — nothing to process.")
  (overdue       "Overdue"        "Nothing overdue. Nice.")
  (upcoming      "Upcoming"       org-air-view--empty-upcoming)
  (high-priority "High priority"  "No #A items.")
  (attention     "Needs attention" "Nothing has gone quiet."))
#+end_src

Then the conditional *Notes* lens, then *Backlog* last — unchanged.
The order reads as a sentence: process (Inbox), repair (Overdue), plan
(Upcoming), choose (High priority), sweep (Needs attention).  Needs
attention moved to the bottom of the task sections deliberately: it is
the *slow* signal, and putting it under the three time-critical ones is
what "brings up what matters for planning at the top" means in practice.

** Empty-state lines

=Nothing overdue. Nice.= moved from attention to *Overdue*, where it was
always secretly about — a small piece of evidence that the old bucket was
two ideas in a trench coat.  The new attention line is =Nothing has gone
quiet.=, which matches the retired =Nothing has gone stale.= cadence and
teaches the new vocabulary ("quiet") that the row labels also use.

** Icons — no new glyph invented

- *Overdue* takes the urgent =▲= (ASCII =!=) that Needs attention used to
  carry.  A missed date IS the alarm.
- *Needs attention* takes the retired Stale =○= (ASCII =~=).  A quiet
  item is an absence, not an alarm.

The glyph table gained =overdue= and lost =stale=; total entries
unchanged.  =org-air-glyphs= is a defcustom, so a user override still
carrying a =stale= key is simply never consulted.

** Making the reason legible

Ruling: "the user must be able to see WHY something surfaced … using
existing row/rail affordances rather than new chrome … do not add a
column that breaks alignment."

*In the row*, the *existing* date cell carries the reason for
Needs-attention rows only (the arm sits first in
=org-air-view--date-label=, ahead of every date arm):

- =12d quiet= — the age that crossed the threshold.
- =always= — a threshold-0 item; the =[#A]= cookie in the same row's
  prefix says which priority did it.

No new column, no new glyph, no alignment change: the cell is measured
board-wide by the existing =--compute-meta-widths= pass exactly like a
date label, and both labels wear the quiet =org-air-face-date= — never a
heat colour.  This section is a nudge; Overdue is the alarm.

Nothing is lost by displacing the date there: an overdue or upcoming item
has its *own* section row showing its date, and the inspector always
lists both dates.

*In the rail*, the inspector's =Bucket= line gained the same reason in
words — =Attention · quiet 12d / 7d= (age over threshold) or
=Attention · always surfaces= — computed from the same two public helpers
the row uses, so they cannot drift.  It replaces the old =stale Nd=
suffix in the same slot.  Directly above it, the R74 =Updated= line names
the stamp the clock actually read (=state=, =note=, =clock=, =created=,
=stamp=, or =~file= for the coarse fallback).

* Filter / bucket agreement

The R72 law is preserved by construction — each section body *is* the
token's predicate:

| Token           | Predicate                          | Bucket          |
|-----------------+------------------------------------+-----------------|
| =is:overdue=    | =org-air-classify--overdue-p=      | =overdue=       |
| =is:upcoming=   | =org-air-classify--due-within-p=   | =upcoming=      |
| =is:hipri=      | =org-air-classify--hipri-p=        | =high-priority= |
| =is:attention=  | =org-air-classify--attention-p=    | =attention=     |
| =is:stale=      | (alias) =--attention-p=            | =attention=     |
| =is:backlog=    | =org-air-classify--backlog-p=      | =backlog=       |
| =is:nodate=     | ¬ =org-air-classify--dated-p=      | (axis, no bucket) |

Verified by probe over a scanned corpus: for every item, token ⇔ bucket
membership, with *one* documented exception that is *pre-existing and
shared by every sibling token*: a =:backlog:=-tagged item is routed to
the single =backlog= bucket by R83, while =is:upcoming= / =is:hipri= /
=is:overdue= / =is:attention= still match it on its own merits.  Measured
on trunk-equivalent code: a backlogged =[#A]= scheduled +2d answers =t=
to =is:upcoming=, =is:hipri= *and* =is:backlog= while classifying to
=(backlog)= alone.  R93 adds no new inconsistency here; it makes the new
token behave exactly like its siblings.  (Fixing that is an R83 question,
not an R93 one, and would change what a filtered board shows.)

=is:nodate= keeps its meaning exactly: it is the negation of "has a
date", which survived the Stale retirement intact under its honest name
=org-air-classify--dated-p= (=--stale-eligible-p= remains as a
=defalias=, so existing callers do not signal).

* Cache

=org-air-view--cache-version= 6 → *7*.

The struct gained one new *trailing* slot (=updated=), so serialisation
rides the existing print/=read= machinery with zero new code — the bump
exists precisely for the record length.  A v6 cache is the established
clean one-time cold miss: skeleton + the R56 paced rescan, never a hang.

The bump is *required*, not defensive.  A v6 record would hydrate with no
=updated= at all, and *every* heading would then age off the coarse file
mtime — a whole board of wrong reasons, silently, rather than an honest
one-time refill.

The per-file =:mtime= the fallback reads was already persisted and
hydrated (R54-2), and hydration happens in =org-air-view--cache-load=
*before* items are used, so the warm path answers with zero file opens.

* Performance

Corpora: 1000 and 5000 files × 4 headings each, every heading carrying a
LOGBOOK state change, a closed CLOCK line, a body inactive stamp and a
SCHEDULED date (i.e. the probe always has work to do).  Both trees
byte-compiled; best-of-N per configuration to control machine noise.  The
baseline is the *parent commit* (=uwuoxlnlnpnq=, R92 FIX — what =main=
was at branch time), extracted with =jj file show= into a separate
directory and byte-compiled there; verified byte-identical to =@-= for
the three files R93 changes in the hot path.

| Phase               | parent (R92 FIX) | R93     | Δ        |
|---------------------+------------------+---------+----------|
| SCAN 1k / 4k items  | 1.514 s          | 1.564 s | +3.3 %   |
| SCAN 5k / 20k items | 7.530 s          | 7.633 s | +1.4 %   |
| CLASSIFY 4k items   | 0.072 s          | 0.076 s | +0.004 s |
| CLASSIFY 20k items  | 0.366 s          | 0.370 s | +0.004 s |

Linear at both scales: 5×the files costs 4.9× the scan and 4.9× the
classify.  The recency probe costs 1–3 % of scan wall time — one extra
bounded regexp walk over a region already walked twice — and
classification is unchanged (the retired Stale predicate's
=--stale-eligible-p= + =--last-activity= chain came out; the aging rule is
a slot read plus at most one hash lookup, so the two roughly cancel).

No new file reads, no new timers, no new buffers, no second buffer pass.

** 9. PRODUCT JUDGMENT (reported, NOT acted on)

  *The finding.*  High priority is exactly the =#A= set and =#A= has
  threshold 0, so *every High-priority row is permanently also a
  Needs-attention row*: Needs attention is a superset of High priority,
  by construction, forever.  Pinned as an invariant by r93-15 so it is a
  decision rather than a surprise.

  *Quantified.*  Standard fixture (23 items): High priority 3 rows, Needs
  attention 5 rows, of which *3 (60 %) are the whole High priority
  section repeated* — 5 board lines (header + 3 rows + separator) of a
  33-line board, ~15 % of the vertical budget, teaching nothing new.  On
  a larger realistic corpus (66 tasks, 12 % =#A=, mixed recency and
  planning): High priority 7, Needs attention 27 — *7 of 27 (26 %)
  duplicated when expanded, 100 % of High priority duplicated always*;
  collapsed at the cap of 6 only 1 of 6 visible rows happened to be a
  duplicate there, because the section is date-sorted.  So the cost is
  *variable and unpredictable*: between 17 % and 60 % of the visible
  Needs-attention budget, depending on nothing the user controls.

  Two further tells that the overlap is a seam, not a feature:
  - the row label has to *make an excuse* for those rows — =always= is
    the section admitting the row is not there for having gone quiet;
  - the section's cap (6) is spent re-showing rows that are already on
    screen a few lines above.

  *Recommendation: raise the =#A= threshold above 0* (=(?A . 3)= would
  do), of the three options offered:

  - /Keep the overlap/ — cheapest, and the user chose it, but it leaves
    two sections teaching one set and makes Needs attention's promise
    ("what has gone quiet") false for up to 60 % of its rows.
  - /Exclude what a section above already showed/ — *do not do this*.  It
    breaks the R72 law that each section body IS its =is:= token's
    predicate (=is:attention= would stop equalling the Needs-attention
    section), which is load-bearing across R72, R77, R83 and R93 itself,
    and it makes a row's membership depend on what else is on the board.
  - /Raise =#A= above 0/ — *recommended*.  Each section keeps one job:
    High priority owns "always visible", Needs attention owns "gone
    quiet".  An =#A= is still seen instantly (it is in High priority),
    and it *additionally* surfaces in Needs attention only once it has
    genuinely been ignored for a few days — which is more informative
    than a permanent duplicate.  The =always= label then disappears from
    the board, the reason cell always carries a real number, and no law
    is bent.  Cost: one defcustom default changes; nothing else moves.

** 1. The defect the audit found (§2 above), restated

** 2. The fix, and the principle it is stated under

  The =date= key never meant "every section by date".  It now says so,
  in the =--sort-items= docstring, as one rule:

  #+begin_quote
  Each section is ordered WORST FIRST by the very number its own rows
  print in the date cell.
  #+end_quote

  A section whose rows print no number has nothing to be worst-first BY
  and keeps query order — deliberately, not by omission.

*** The per-section sort table (the deliverable)

| Section        | Sorted by                                        | The number its rows print | Why that is the right planning order                                                                                             |
|----------------+--------------------------------------------------+---------------------------+----------------------------------------------------------------------------------------------------------------------------------|
| Inbox          | QUERY (capture/scan) order                       | none                      | A processing queue.  Inbox zero is worked in the order things arrived; ranking it would invent a priority the user never gave.     |
| Overdue        | =--sort-by-date= asc (earliest deadline first)   | =OVERDUE Nd=              | *FIXED HERE.*  Worst-first: the most-broken promise leads, and the 6-row cap then shows the six WORST rather than six arbitrary ones. |

| Needs attention| =--sort-by-quiet= desc (longest silent first)    | =Nd quiet= / =always=     | *CHANGED HERE* — see §3.                                                                                                          |

** 3. The second section of the same class — Needs attention

  The audit filed this as a "related presentational note, not a defect".
  Re-examined against the rule in §2 it IS the same class, caused by the
  same split, and it is fixed here.

  - *What changed under it.*  R93 moved every overdue row OUT and made
    the section a pure AGING rule.  Its date sort survived the move with
    nothing left to do: R93 also made the date cell of an attention row
    print the REASON (=273d quiet= / =always=), never a date
    (=org-air-view--date-label=, the =attention= arm sits ahead of every
    date arm).  So the section was ordered by a fact it does not show,
    and its now-large dateless half fell to the tail in SCAN order.
  - *The visible symptom, shipped in the R93 goldens.*  At width 120:
    =225d quiet= rendered ABOVE =273d quiet=.  Two rows, both printing a
    number, in the wrong order — the identical failure mode as Overdue,
    one section lower.
  - *The fix.*  =org-air-view--sort-by-quiet=: key
    =org-air-classify-quiet-days= (the SAME public helper the row label
    and the rail inspector quote, so order/label/bucket cannot drift),
    descending, unknown age last, stable.  One classify call per item —
    the age is precomputed into the sort key, not recomputed per
    comparison — and no file access, so the R53 data-purity fence is
    untouched (verified: =find-file-noselect= count still 0 across both
    renders in =org-air-r53-3=).
  - *Why "longest silent first" and not "keep the dates first".*  A
    committed row's date is already ranked, twice, by the two sections
    directly above (Overdue and Upcoming).  Ranking commitments a THIRD
    time here adds nothing and costs the one thing no other section
    shows: how long something has been ignored.
  - *The =always= rows.*  A threshold-0 (=#A=) row sorts by its REAL
    age, not parked at either end: an =#A= silent 200 days needs
    attention more than a =#C= silent 20, and the label suppresses the
    number only because the threshold — not the age — is why it
    surfaced.  A freshly touched =#A= therefore sinks to the bottom of
    this section, which is honest (it is not neglected) and costs no
    visibility (it is in High priority, immediately above).
  - *Considered and rejected:* a hybrid ("committed rows by date first,
    then the rest by silence").  Implemented and measured — it produces
    the identical test outcome, so it was not chosen for safety; it was
    rejected because it orders half a section by an invisible key and
    needs two sentences to explain instead of one.
