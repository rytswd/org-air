#+title: org-air Round 94 — the recency signal made honest: the file floor leaves the clock, Untracked gives homeless work a home
#+state: complete
#+tags: board classify planning attention recency untracked provenance overdue cache

* Summary

R93 built a real recency model and then let a *file* fact answer a
*heading* question.  When a heading carried no history of its own, its
age came from the source file's mtime — which moves whenever any byte of
that file moves, org-air's own writes included.  The R93 review measured
what that cost:

- a =tasks.org= edited today hid *15 of its 20 headings*;
- the project's shipped demo board lost =Untracked idea with no dates=
  and =Read Structure and Interpretation= entirely — *2 of 23*;
- *52 %* of Needs-attention members and *83 %* of the rows visible under
  its cap were floor-derived numbers wearing the same clothes as measured
  ones;
- three amplifiers the R93 design never named: org-air's own writes
  (=t=, =b=, refile, capture, archive) reset the floor; for a one-file
  user it is all-or-nothing; recovery is a *burst* where ten headings
  arrive on the same day with the same number and outrank every measured
  age.

R94's answer is structural rather than cosmetic.

1. *The attention clock is MEASURED ONLY.*  =org-air-classify-updated=
   no longer falls back to the file mtime.  Membership of Needs
   attention is decided entirely by the heading's own recorded history,
   so org-air's own writes cannot change who is in it, a one-file setup
   is no longer all-or-nothing, and there is no burst.
2. *A new =untracked= bucket and conditional section* — no plan and no
   record — gives the work that removal would otherwise strand a
   permanent, non-accusing row.  Nothing became invisible; two of the
   demo board's own headings became visible for the first time since
   R93.
3. *The floor survives, honestly scoped*, as
   =org-air-classify-updated-floor=: a sound LOWER bound used only to
   rank and label Untracked rows, printed with a leading =~= so a
   file-level number can never be read as a heading-level one.

Plus the four correctness follow-ups the review filed: the Overdue sort
key now reads the slot the row's own label chose; inactive
=SCHEDULED:=/=DEADLINE:= values and quoted old plan dates inside
reschedule log lines stop moving the recency clock; and the rail
inspector reads the SCAN mtime instead of a live stat, so decision 13
("one number everywhere") holds for the file path too.

Parent =rqvllzqvouxq= (= =main=, R93 RETEST-2).  Source + README +
goldens + this document only.  *No =tests/*.el= byte was touched.*

* The primary problem, and the answer

** What the floor actually is

Any edit to a heading is an edit to its file, so:

: last-change(heading)  <=  mtime(file)

The age derived from the mtime is therefore a *sound LOWER bound* on the
heading's real age.  Restating that as a rule about use:

#+begin_quote
The file mtime is *sound when it accuses* ("this file has not changed in
210 days, so this heading has been quiet at least that long") and
*unsound when it excuses* ("this file changed today, so this heading is
fresh").  R93 used it for both.
#+end_quote

Every measured symptom in the review is the excuse direction.  The
accusation direction was never wrong — it was merely *coarse*, and it is
the half worth keeping.

** The options, weighed

The brief offered four.  All four were implemented or costed; two were
taken, one was dissolved, one was rejected with arithmetic.

*** (a) Render floor-derived ages as =~210d quiet=, tie-break toward measured — TAKEN, but relocated

Marking an estimate is right.  But annotating a number does not stop it
deciding *membership*, which is where the hiding happened: an item at
=~0d= is not shown with a tilde, it is not shown at all.  R94 therefore
does the stronger thing — a floor-derived number never reaches Needs
attention, so that section prints *no* estimates and needs no marker —
and puts the =~= where a file-level bound is the honest answer: the
Untracked row (=~210d quiet=) and the rail (=file quiet ~210d=, next to
the =~file= label R74 already shipped).

The tie-break is implemented anyway, in =org-air-view--sort-by-quiet=:
equal ages order MEASURED first
(=org-air-classify-updated-source=).  Under the defaults it is dormant
on the board; it is kept so the ordering law does not depend on the
current bucket wiring.

*Where this seat disagrees with the review, and why.*  §9.2 recommends
that a measured age ALWAYS outrank a bound — "ranking a measured 87d
above a guessed 210d is defensible".  It is not, and the lower-bound
argument above says why: =~210d= means "at least 210 days", which is a
*stronger* claim of neglect than a measured 87.  Systematically demoting
bounds would re-hide exactly the oldest work, which is constraint 1's
failure mode in a new dress.  What made the review's five identical
=210d= rows useless was not that they were bounds; it was that they came
from one =someday.org= and were being asked to compete in a section about
heading history.  R94 removes them from that competition entirely
instead of demoting them inside it.

*** (b) Cap how much freshness a file mtime may grant — REJECTED, with the arithmetic

A cap means =effective-age = max(mtime-age, X)= for some floor-of-the-floor
=X=.  Against the shipped thresholds (=#A= 3, =#B= 7, =#C= 14, everything
else 30) there is no value of =X= that works:

| =X=      | effect                                                                      |
|----------+-----------------------------------------------------------------------------|
| =X < 3=  | changes nothing for anybody — every threshold is larger                      |
| =3..29=  | every historyless =#A=/=#B=/=#C= surfaces permanently; the common no-cookie case (threshold 30) is still hidden |
| =X >= 30= | every historyless heading is a permanent Needs-attention row — the deleted "undated means attention" rule, restored |

The knob cannot separate "hidden" from "nagged" because the quantity it
adjusts is the wrong one: the problem is not the SIZE of the excuse, it
is that an excuse exists at all.  Rejected.

*** (c) Treat org-air's own writes as not refreshing the floor — DEFANGED, not implemented

This attacks one amplifier and needs new state: a per-file "the mtime
bump at T was ours" ledger, threaded through every write path (=t=, =b=,
refile, capture, archive), fragile against any concurrent user edit, and
touching the R90 write-discipline seams.  High risk, partial cure.

Under R94 it is *unnecessary*: the floor no longer decides membership, so
an org-air write cannot hide anything.  The amplifier is removed by
construction rather than tracked.  (It is still named in the README,
because users were told the floor existed and deserve to be told what
changed.)

*** (d) Surface historyless items through a distinct, quiet affordance — TAKEN

This is the only option that satisfies constraint 1 without touching
constraint 2, because Needs attention IS the accusation surface: anything
put there is, by definition, a nag.  A separate section can show the same
work while claiming nothing about it.

** The ruling

1. *Needs attention is measured-only.*  =org-air-classify-quiet-days=
   reads the heading's own =updated= slot and nothing else.
2. *=untracked= = no plan AND no record.*  A new bucket, a new
   conditional section, a new =is:untracked= token — one predicate,
   =org-air-classify--untracked-p=, shared by all three (the R72 law).
3. *The floor is a bound, and it is marked.*
   =org-air-classify-updated-floor= ranks and labels Untracked rows only.
4. *Provenance is public.*  =org-air-classify-updated-source= returns
   =measured= / =file= / nil; the row, the sort and the rail all ask it
   rather than each re-deriving it.

** The coverage theorem this buys

#+begin_quote
Every board-active, non-deferred task heading has a row somewhere —
UNLESS its own plan puts it beyond the Upcoming horizon, which is a
promise org-air keeps rather than a hiding place.
#+end_quote

Proof by exhaustion of the two facts a heading can carry:

| has a plan? | has a record? | home                                                                |
|-------------+---------------+---------------------------------------------------------------------|
| yes         | either        | Overdue (past), Upcoming (<= 7d), or *its own future date*, on time   |
| no          | yes           | Needs attention, once it crosses its priority's threshold             |
| no          | no            | *Untracked*, permanently, from the first repaint                       |

Inbox, High priority and Backlog overlay this table without changing it.

** Why Untracked is not the deleted rule under a new name

The pre-R93 rule and this section share a membership overlap; they share
nothing else.

| Axis                | pre-R93 "undated means attention"                      | R94 Untracked                                        |
|---------------------+--------------------------------------------------------+------------------------------------------------------|
| Claim it makes      | this work is *neglected*                                | org-air *cannot rank* this work                       |
| Lane                | the alarm lane, mixed with genuinely overdue rows       | last of the task sections, own quiet =◌= glyph        |
| Badge               | attention-coloured                                      | never attention-coloured                              |
| Cap                 | 6 rows, competing with real overdue work                | 4 rows, competing with nothing                        |
| Over time           | grows and re-fires forever                              | can only shrink; never re-fires                       |
| Exit                | invent a date (a lie) or =:backlog:= (gaming the board) | one date, or one stamp Org writes for you             |
| Empty board         | still a section                                         | not rendered at all                                   |
| Membership rule     | "no date"                                               | "no date AND no record" — strictly narrower           |

The last row matters: an undated heading with a LOGBOOK trail was in the
old rule and is *not* here, which is exactly the R93 improvement being
preserved.

* The four follow-ups

** FIX-1 — the Overdue sort key is now the slot the label chose

=org-air-view--item-sort-time= keys on =(or deadline scheduled)=
unconditionally; =org-air-view--date-label= prints =OVERDUE Nd= from
whichever slot is actually PAST, deadline first.  For a heading overdue
by its SCHEDULE while its DEADLINE is still in the future the two
disagree, and the worst row in the alarm section sorts LAST — where the
6-row cap can hide it behind "…and N more".  Reproduced by the review
through the real renderer, and re-reproduced here on =main=:

#+begin_example
* TODO C   SCHEDULED: <2026-05-06 Wed>   DEADLINE: <2026-06-20 Sat>

main (R93):  OVERDUE 30d  OVERDUE 20d  OVERDUE 4d  OVERDUE 2d  OVERDUE 40d
R94:         OVERDUE 40d  OVERDUE 30d  OVERDUE 20d  OVERDUE 4d  OVERDUE 2d
#+end_example

*The fix.*  =org-air-view--overdue-time= hoists the label's own arm order
(deadline-if-past, else scheduled-if-past) into one function; the label
composes its number from it and =org-air-view--sort-by-date= keys on it
when =bucket= is =overdue=.  The FIX-2 law — *each section is ordered
worst-first by the very number its own rows print* — is now true by
construction rather than by coincidence of slot order.

*This is pre-existing, not an R93 regression*: the same order renders on
the parent, where those rows lived in =attention= under the same key with
the same labels.  But FIX-2 elevated the law to a stated rule and
=r93-21= claims to fence it, and *=r93-21='s corpus does not contain this
shape* — a heading carrying BOTH slots with only the scheduled one past.
Neither does any other corpus in the suite.  Measured directly: mutation
M1 (revert the key to =--item-sort-time=) reddens *nothing*.  The test
seat owns adding the shape; §"Handover" lists it first.

** FIX-2 — inactive planning stamps are plans, not updates

Org accepts =DEADLINE: [2026-06-14 Sun]=.  =org-ts-regexp-inactive=
matches it, so R93 read one stamp as both a deadline (the row went to
Overdue) and an update (age 1) — while the R93 design and README both
claimed the exclusion was *mechanical*: "a SCHEDULED, a DEADLINE or a
bare plan date can never move this clock."  That was true only of the
=<…>= spelling.

*The fix* (=org-air-query--plan-stamp-p=): the nearest planning keyword
to the LEFT of the match on the same line decides whose value the stamp
is.  =SCHEDULED:= / =DEADLINE:= own it → skip; =CLOSED:= owns it → keep
(it is the one planning keyword that records something that happened); no
keyword → an ordinary body or LOGBOOK stamp → keep.  Keyword-by-keyword,
not line-by-line, so a mixed planning line resolves correctly.

| corpus line                                       | main | R94       |
|---------------------------------------------------+------+-----------|
| =DEADLINE: [2026-06-14 Sun]=                      |    1 | UNKNOWN   |
| =SCHEDULED: [2026-06-14 Sun]=                     |    1 | UNKNOWN   |
| =CLOSED: [2026-06-14 Sun 09:00]=                  |    1 | 1         |
| =CLOSED: [2026-06-01 …] DEADLINE: [2026-06-14 …]= |    1 | 14        |

Both inactive-plan rows stay in Overdue, as they should; they simply stop
claiming to be updates.  The documentation's promise is now the code's.

** FIX-3 — a quoted old plan date is not the log's own moment

Org's default =org-log-note-headings= quote the OLD value with =%S=:

: - Rescheduled from "[2026-06-14 Sun]" on [2026-06-01 Mon 08:00]
: - New deadline from "[2026-06-13 Sat]" on [2026-05-01 Fri 08:00]

The quoted date is newer than the log's own whenever a task is moved
*earlier*, so newest-wins picked the abandoned plan.

*The fix* (=org-air-query--quoted-stamp-p=): a stamp wrapped in double
quotes is never this clock's witness.  This is the "prefer the stamp
after ` on `" rule stated as punctuation rather than wording, which makes
it independent of the note-heading format string — =%s= and =%S= are
quoted in every default heading, =%t= never is.

| line                                                      | main | R94 |
|-----------------------------------------------------------+------+-----|
| =- Rescheduled from "[2026-06-14 Sun]" on [2026-06-01 …]=  |    1 |  14 |
| =- New deadline from "[2026-06-13 Sat]" on [2026-05-01 …]= |    2 |  45 |

Both guards are constant-cost per match (one bounded backward search on
the current line; two character reads).  No new pass, no new read.

** FIX-4 — the inspector reads the SCAN mtime, not a live stat

Classify read the scan-time =:mtime= from =org-air-query-file-meta=; the
rail's =~file= line did a live =file-attributes=.  After an on-disk edit
with no rescan they disagreed — the review measured 165d vs 1d — breaking
decision 13 ("the number the inspector shows and the number the bucket
used cannot drift"), which held for the slot path but not the file path.

=org-air-view--item-updated-line= now reads
=org-air-classify-updated-floor= first and falls back to ONE bounded live
stat only for an item the scan never saw (built outside the scan).
Re-measured:

#+begin_example
                              main                     R94
AFTER SCAN (mtime 2026-01-01) bucket 165d / rail 165d   165d / 165d
AFTER on-disk edit, NO rescan bucket 165d / rail   1d   165d / 165d
#+end_example

Both numbers now move together on the next rescan, which is the only
moment either of them learns anything.

* Cache

=org-air-view--cache-version= 7 → *8*.

*No new slot.*  The record shape is byte-identical to v7 and the bump is
about MEANING: R94 narrowed what =updated= may contain (FIX-2, FIX-3).  A
v7 record is well-formed but was harvested under the OLD rule, so
hydrating it would keep a heading looking fresher than it is — and,
because =org-air-classify--untracked-p= now reads the same slot, would
also keep it out of the Untracked section it belongs in.  Wrong answers
that look right are worse than a cold miss, so v7 is discarded: skeleton
+ the R56 paced rescan, never a hang.

The =:mtime= the floor reads was already persisted and hydrated (R54-2),
so the warm path still answers with zero file opens.

* Performance and cost

Corpora: 1000 and 5000 files × 4 headings, each heading carrying a
SCHEDULED date, a closed CLOCK line, a LOGBOOK state change, a
*reschedule log line with a quoted old date* (so both new guards always
have work to do) and a body inactive stamp.  Both trees byte-compiled;
best-of-3.  Baseline = =main= extracted with =jj file show= into
=/tmp/r94/parent=.

| Phase               | main (R93) | R94     | Δ        |
|---------------------+------------+---------+----------|
| SCAN 1k / 4k items  | 1.626 s    | 1.658 s | +2.0 %   |
| SCAN 5k / 20k items | 8.710 s    | 8.862 s | +1.7 %   |
| CLASSIFY 4k items   | 0.074 s    | 0.077 s | +0.003 s |
| CLASSIFY 20k items  | 0.389 s    | 0.401 s | +0.012 s |

Classify's +3 % is the one extra predicate per item
(=--untracked-p= = a slot read plus =--dated-p=, both already computed
facts).  No new I/O — measured, not asserted, with
=insert-file-contents= / =find-file-noselect= / =file-attributes= /
=get-buffer-create= spied over an identical corpus:

#+begin_example
main SCAN     ifc=10 ffns=0 file-attributes=21 gbc=122
R94  SCAN     ifc=10 ffns=0 file-attributes=21 gbc=122
main CLASSIFY ifc=0  ffns=0 file-attributes=0  gbc=0
R94  CLASSIFY ifc=0  ffns=0 file-attributes=0  gbc=0
#+end_example

Identical in every column: classify still does *zero* I/O, and the floor
really is a hash lookup.

* Filter / bucket agreement

The R72 law is preserved by construction — each section body IS the
token's predicate:

| Token           | Predicate                          | Bucket      |
|-----------------+------------------------------------+-------------|
| =is:untracked=  | =org-air-classify--untracked-p=    | =untracked= |

=is:untracked= is deliberately NOT a synonym for =is:nodate=: the latter
is the date negation alone, so an undated heading with a LOGBOOK trail
answers =is:nodate= and not =is:untracked=.  It inherits exactly one
documented exception, the *pre-existing* one every sibling token shares:
a =:backlog:=-tagged item classifies to =(backlog)= alone while still
answering =t= to the raw token on its own merits.  R94 adds no new
inconsistency there.

* Migration and honest degradation

| What                                        | Before                          | After                                                        |
|---------------------------------------------+---------------------------------+--------------------------------------------------------------|
| historyless dateless heading, file hot       | *no section at all*             | Untracked                                                    |
| historyless dateless heading, file 210d old  | Needs attention at =210d quiet= | Untracked at =~210d quiet= (the number is marked as a bound)  |
| historyless DATED heading, file 210d old     | Needs attention at =210d quiet= | its own date section, when the date arrives                  |
| heading with history                         | unchanged                       | unchanged                                                    |
| =org-air-classify-updated= callers           | slot ‖ file mtime               | slot only; =…-updated-floor= is the mtime                     |
| existing v7 scan cache                       | loaded                          | clean cold miss + paced rescan                                |
| a board with no untracked items              | five sections                   | five sections, byte-identical (the descriptor is conditional) |
| =org-air-glyphs= without an =untracked= key  | n/a                             | user overrides keep working; the key is simply consulted      |

Nothing signals.  The one behaviour a user could miss is row 3: a
historyless heading that *is* dated no longer surfaces for its file's
age.  That is deliberate — it has a plan, and org-air keeps the plan
rather than second-guessing it — and it is stated in the README.
