* D1 — the funnel guard (data loss)

** Root cause

=org-air-view--render-current= erases and repaints *the current buffer*
and had **no precondition at all**.  Everything that repaints funnels
through it: the filter, the scope clears, the sort, the lens, the
calendar month/day nav and the resize repaint.  =org-air-refresh= even
*had* a mode check —

#+begin_src emacs-lisp
(if (and (not noninteractive) (eq major-mode 'org-air-view-mode))
    …refresh machine…
  …the unguarded synchronous render…)
#+end_src

— whose **else** arm is the unguarded synchronous render, so failing the
check made it *more* destructive, not less.

** The fix: guard the funnel, not the eight commands

The reviewer's instruction was explicit and is the one followed here:

#+begin_quote
"Do not 'fix' D1 by adding a =derived-mode-p= check to each of the 8
commands.  Patching the 8 known instances leaves the ninth, which will be
written next round."
#+end_quote

One base precondition, in =org-air-query.el= (the module every other
module requires), so the whole command surface shares *one* refusal
shape:

#+begin_src emacs-lisp
(defun org-air-surface-p (&rest modes)
  "Non-nil when the current buffer is one of the org-air surfaces MODES.
Each element is a MAJOR-mode symbol (via `provided-mode-derived-p') or a
buffer-local MINOR-mode symbol (`org-air-doc-session-mode',
`org-air-outline-mode')." …)

(defun org-air-require-surface (surface entry &rest modes)
  "Refuse unless the current buffer is one of MODES."
  (unless (apply #'org-air-surface-p modes)
    (user-error "Not in %s (run `M-x %s')" surface entry)))
#+end_src

and the **three buffer-erasing funnels** in =org-air-view.el= now state
the board precondition before doing anything:

| funnel                          | why it is a funnel                                 |
|---------------------------------+----------------------------------------------------|
| =org-air-view--render=          | the deepest paint: =erase-buffer= + full rewrite   |
| =org-air-view--render-loading=  | the other =erase-buffer= (the cold skeleton)       |
| =org-air-view--render-current=  | the named funnel the 8 destroyers reach            |

=org-air-view--refresh-repaint=, =org-air-view--render-section= and
=org-air-view--render-calendar= inherit the guard — they all end in one
of the three.  =org-air-refresh= additionally states it as its own first
body form, so it refuses *before* the token bump and the re-query rather
than midway through them.

The guard cannot be reached on any legitimate path: every painting
caller (=org-air-view--open-core=, the refresh machine's swap, the
synchronous re-query, the bookmark handler) already runs with the board
buffer current and the mode already ensured.  That is why the 1345-test
suite — which renders inside a board every single time — is untouched by
it except where a test deliberately drove a command from somewhere else
(§Gate).

* D6 — interactive mode scoping across the whole command surface

Emacs 29.1 is the floor, so =(interactive SPEC MODE…)= is available.  It
is now applied to **118 of the 132** commands; the other 14 are the
global entry points, which must stay offered everywhere.

** Where the guard goes, and why the placement matters

The rule is *the refusal must precede the prompt*.  Emacs evaluates a
command's =interactive= form before its body, so:

- =(interactive)= (no spec) → =(interactive nil MODE…)= and the guard as
  the **first body form**.  Nothing can prompt before it: the body has
  not started.
- a *spec-bearing* form (=(interactive (list (read-string …)))=,
  ="sTag: "=, =(progn (org-air-view--loading-guard) …)=) → the guard is
  hoisted **inside** the interactive form, ahead of the read:
  =(interactive (progn (org-air-view--require-board) …) org-air-view-mode)=.
  The two string specs (="sTag: "=, ="sSchedule (empty clears): "=) were
  rewritten to the equivalent explicit =read-string= so the guard could
  be placed before them at all.
- an *engine* command with a public non-interactive API
  (=org-air-visit-item=, =org-air-refile-item=) → the guard lives in the
  =interactive= form **only**, so =(org-air-visit-item ITEM)= from Lisp,
  the revisit view and the pane stays buffer-agnostic.

** The surface vocabulary

Named wrappers, so a call site reads as one token and the accepted set is
visible where it is asserted:

| helper                                  | surfaces                                          |
|-----------------------------------------+---------------------------------------------------|
| =org-air-view--require-board=           | board                                             |
| =org-air-view--require-item-view=       | board, review (the shared item verbs)             |
| =org-air-view--require-view=            | board, project, review, revisit                   |
| =org-air-view--require-rail-host=       | the four + rail + doc session                     |
| =org-air-view--require-rail=            | rail                                              |
| =org-air-view--require-pane-surface=    | entry pane (incl. the =*org-air-pane:*= indirect) + the four hosts |
| =org-air-project--require-view=         | project tree                                      |
| =org-air-project--require-doc-session=  | a live project doc session                        |
| =org-air-review--require-view=          | review                                            |
| =org-air-revisit--require-view=         | revisit                                           |
| =org-air-inbox--require-board=          | board (the refile engine's =e=)                   |
| =org-air-inbox--require-form=           | *state*, not mode: the transient form must hold an item |

Two placements are deliberately *not* mode preconditions:

- =org-air-refile-form-*= (11 transient suffixes, the D5 raw-error set)
  are guarded on **form state** (=(org-air-inbox--form-get :item)=), not
  on a mode — transient decides which buffer runs a suffix, so the state
  is the honest invariant.  They are still mode-*scoped* to the board so
  =M-x= stops offering them.
- =org-air-rail-toggle= already had an older, *stricter* precondition of
  its own (a doc buffer must carry a live session tree).  It gets the
  scoping and keeps its own refusal; layering a second guard on top would
  only have changed a message for no gain.

* D2 — silent capture loss, and the decision

** The defect

With the README's plain-=require= snippet — =(setq org-air-files '("~/org/"))=
and nothing else — =org-air-inbox-file= defaulted to
=(locate-user-emacs-file "org-air-inbox.org")=, i.e.
=~/.emacs.d/org-air-inbox.org=, which is **not** inside =org-air-files=.
So =c= wrote the note correctly, said "Captured to …", and the board
honestly reported *Inbox 0 — Inbox zero — nothing to process*.  Both
halves right, together a silent loss.

** The decision: do BOTH, and reject the fold-in

The reviewer's preferred fix was (a) "always include =org-air-inbox-file=
in the scan set".  **That is the one option this round rejects**, and it
was tried first and reverted:

- Folding the inbox into =org-air-query-files= fixes the *loss* but not
  the *incoherence*.  =org-air-files= would silently stop being the
  complete answer to "what does the board read" — the scan set would gain
  a member the user never listed, and a user who deliberately narrows
  =org-air-files= could not narrow the inbox out.
- It also *contradicts an existing contract*, and the suite proved it:
  =org-air-r60-3-inbox-never-excluded= (c) pins that an entirely-excluded
  source root yields **nothing**.  The fold-in made it yield the inbox.
  R60's law — the enumerated set is exactly (=org-air-files= − excludes,
  with the inbox exempted from the excludes) — is worth more than the
  convenience.

What ships instead closes the gap from *both ends*, and keeps the scan
set honest:

1. **The default derives from =org-air-files=.**  =org-air-inbox-file=
   now defaults to =nil=, and =org-air-inbox-effective-file= resolves it:
   =inbox.org= inside the first configured directory, or beside the first
   configured file.  =(setq org-air-files '("~/org/"))= therefore captures
   to =~/org/inbox.org= — inside the scan set by construction, so the
   default *cannot* lose a note.
2. **An explicit inbox outside the scan set is REFUSED**, not warned
   about.  =org-air-inbox-file-scanned-p= answers containment without
   running a scan and without requiring the file to exist yet, so
   =org-air-capture= can refuse *before the title prompt and before the
   file is created*:

   #+begin_example
   Inbox /home/u/elsewhere/org-air-inbox.org is outside `org-air-files', so the
   board would never show this capture; move it inside, add its directory to
   `org-air-files', or set `org-air-inbox-file' to nil to derive it
   #+end_example

   With nothing configured at all:
   =Nothing to capture into: set `org-air-files' first=.

A warning was considered and rejected: the round's own rule is that
silent loss is unacceptable *in either direction*, and a warning that
scrolls past is still a lost note.  Refusing costs one =user-error= and
loses nothing.

Because the default can now be =nil=, every reader of the raw variable
was routed through the resolver, so a *derived* inbox is recognised
exactly like a configured one: the exclude-context exemption
(=org-air-query--exclude-context=), =org-air-query--inbox-file-p=,
=org-air-classify--inbox-file-p=, the revisit queue's inbox exclusion,
=org-air-view--cache-key=, the changed-files inbox-first ordering, and
=org-air--relevant-file-p= (the after-save refresh scope).

Verified end to end (=/tmp= probe, README snippet verbatim):

#+begin_example
org-air-files            : ("/tmp/…/org/")
org-air-inbox-file       : nil
effective inbox          : /tmp/…/org/inbox.org
inside the scan set?     : t
board sees inbox item?   : t (of 2 items)
#+end_example

* D3 — encrypted Org is skipped; now it says so

The skip itself is correct and stays: =org-air-query--scan-file= refuses
to read an =.org.gpg= with no live buffer, because a background scan must
never block on pinentry.  (A file already open and decrypted *is* scanned
in place, as before.)  What was wrong is that the skip was invisible and
that the README claimed the opposite.

Two changes, neither of which touches the paint (no golden churn):

1. **README:161 corrected.**  The line now reads "directories are scanned
   recursively for =.org= files", followed by a new subsection —
   *Encrypted files are listed but not read* — that states the behaviour,
   the reason, and the workaround (open and decrypt the buffer).
2. **The scan says so.**  =org-air-query-items= now calls
   =org-air-query--announce-skips= at the end of a full scan:

   #+begin_example
   org-air: 1 file(s) in `org-air-files' were NOT read (1 encrypted) — M-x org-air-scan-report
   #+end_example

   Emitted **at most once per distinct skip set** (=org-air-query--skip-announced=),
   so a board refreshed all day says it once; governed by the new
   =org-air-report-skipped-files= (default =t=).  It is a =message=, not
   paint: zero byte-fixture impact, and it runs in batch too, so it is not
   another =(unless noninteractive …)= blind spot.
3. =org-air-scan-report= now explains each structured reason under the
   list (=org-air-query-skip-reason-explanations=), so a user who notices
   a file missing learns why in the same place:
