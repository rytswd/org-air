* R22-2 — cursor/RET take-3: RET on a row says "no org-air item" because point lands on a dead column [BUG — critical]

** Reproduction — the item text-property does NOT span the whole visual row
The user reports (post R21-1/R21-2): the cursor STILL sits on the leftmost
char, and pressing RET there says "there is no org-air item".  R21-1 (restore
saved column) and R21-2 (=--goto-row-title=) only fire on org-air's OWN motion
commands; the user drives the board with NATIVE Emacs motion (=<up>/<down>=,
=C-n/C-p=, =C-a=, mouse) which never calls =--goto-row-title=.  But the deeper,
measured fault is that even when point IS on a row, the at-point lookup can
fail — *the =org-air-item= text property does not cover the full visual line*.

Measured (source, =org-air-view-width 120=, the default two-pane/inline-rail
layout), first item row:
#+begin_src text
two-pane-p = t
col 0  org-air-item: nil      <-- leftmost char: NO item property
title  org-air-item: t
at col 0: org-air-view-pane--context-at-point = nil   ==> RET: "No org-air item at point"
item present somewhere on line: t (at col 2)           <-- the row DOES own an item, 2 cols in
#+end_src
Per-column property map of the row (=#= = has =org-air-item=, =.= = none):
#+begin_src text
..###################################################################...................................
^^                                                                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
||                                                                  └ the rail columns + trailing pad: no item
└┴ the 2-col `org-air-margin': no item
#+end_src
So the property spans only the BOARD content between the leading margin and the
rail — col 0–1 (the margin) and everything right of the divider carry NO
=org-air-item=.  Native motion (=C-a=, =<left>= to col 0, a mouse click on the
margin/rail/pad) parks point in one of those DEAD zones; the point-only lookup
in =org-air-view-pane--context-at-point= (org-air-view.el L3865) and
=org-air-view--item-at-point= (L5126) then returns nil and every row action
(=RET=, =v=, =r=, =D=, …) errors "No org-air item at point".

** Reproduction — root mechanism: the margin + rail are composited WITHOUT the row props
=org-air-view--insert-row= (L2011) DOES add =org-air-item= over the whole row it
inserts (=add-text-properties start (point)= at L2099) — but in the two-pane
layout the row is rendered at the NARROW =item-content-width= with
=org-air-view--pane-indented t=, so its prefix is only =org-air-item-indent=,
NOT the leading =org-air-margin=.  The 2-col =org-air-margin= is added DOWNSTREAM
by =org-air-view--indent-pane-lines= (L3207) as a bare =(concat margin text)=
where =margin= is a fresh =org-air-view--margin= (L953) string carrying NO
properties; and the rail columns are composited on the right by
=org-air-view--compose-columns= (L1251).  Net: the leading margin and the rail
share the visual line but not the item property.  (In the BOARD-ONLY layout —
narrow width / the popped-out side-window rail — the full line IS propertized,
so col 0 works there; the bug is the DEFAULT two-pane layout, the most common
view.)  This is why R21-1/R21-2 did not cure it: they normalise point only on
org-air's own motion, and they cannot help a point-ONLY lookup that fails on a
dead column the user reached natively.

** Reproduction — native motion bypasses the title normaliser
=org-air-view-mode-map= binds =n/p/j/k= (org-air motion → =--goto-row-title=)
and =<mouse-1>= (→ =org-air-view-pane-return=) but binds NONE of =<up> <down>
<left> <right> C-n C-p C-a C-e <home> <end>=.  So all arrow/emacs motion uses
the native commands, which never call =--goto-row-title= and routinely leave
point at col 0 (=C-a=, =<home>=, =<left>=) — squarely in the dead margin zone.

** Decision — make row actions LINE-based, and normalise point off dead columns
Belt + suspenders, exactly as the brief asks: (a) resolve the row's item from
ANYWHERE on the line (point-independent), so an action works no matter where on
the row point sits; (b) snap point off the dead columns onto the title on any
landing, including native motion + mouse.

*** (a) PRIMARY — a line-based row-property resolver, used by every row action
Add one resolver that finds the row property anywhere on the current line:
#+begin_src elisp
(defun org-air-view--row-property (prop)
  "Return PROP found ANYWHERE on the current row (line), or nil (R22-2).
A row's `org-air-item'/`org-air-doc'/`org-air-marker' covers only the board
content between the leading margin and the rail; the margin, the rail columns
and the trailing pad carry no row property, so a point-ONLY lookup fails there.
Scan the whole line so an action resolves the row regardless of point's column."
  (or (get-text-property (point) prop)
      (let* ((bol (line-beginning-position))
             (eol (line-end-position)))
        (or (get-text-property bol prop)
            (let ((pos (text-property-not-all bol eol prop nil)))
              (and pos (get-text-property pos prop)))))))
#+end_src
Route the at-point accessors through it (item first, then doc, then marker — so
the board item / project doc on the LEFT of the line always wins over any rail
property on the right):
- =org-air-view--item-at-point= (L5126): =(or (org-air-view--row-property
  'org-air-item) (user-error "No org-air item at point"))=.
- =org-air-view-pane--context-at-point= (L3860) + =org-air-view--view-pane-
  thing-at-point= (L3856): read each of =org-air-item= / =org-air-doc= /
  =org-air-marker= via =--row-property= instead of =get-text-property (point)=.
- The two inline lookups that bypass the helper — =org-air-set-tag= (L5099) and
  =org-air-set-schedule= (L5112) — switch to =org-air-view--item-at-point= (so
  there is ONE resolver).
This ALONE makes RET / v / r / D / T / S-RET / TAB / inspector-follow work from
any column on the row (margin, rail, pad), curing the "No org-air item" error.

*** (b) SECONDARY — normalise point off dead columns to the title
A buffer-local =post-command-hook= snaps point onto the row title ONLY when the
command left point on a row line at a column the item property does not cover
(the dead margin / rail / pad).  Crucially it is a NO-OP when point already
sits on a propertized column — so it never fights R21-1 (the restored column is
always within the item span) nor deliberate in-title motion:
#+begin_src elisp
(defun org-air-view--normalize-point ()
  "Snap point onto the row title when it lands on a DEAD column (R22-2b).
Runs in `post-command-hook'.  Acts only when the current line owns a row
(`org-air-item'/`org-air-doc' present somewhere on it) AND point's column has
NO row property (the leading margin, the rail, the trailing pad).  Idempotent:
when point is already on a propertized column it does nothing, so it composes
with R21-1's restored column and never reintroduces a col-0 snap."
  (when (and (not (window-minibuffer-p))
             (memq major-mode '(org-air-view-mode org-air-project-mode))
             (not (get-text-property (point) 'org-air-item))
             (not (get-text-property (point) 'org-air-doc))
             (or (org-air-view--row-property 'org-air-item)
                 (org-air-view--row-property 'org-air-doc)))
    (org-air-view--goto-row-title)))
#+end_src
Install it (inert under =noninteractive=, like the other view hooks) in
=org-air-view-mode= and =org-air-project-mode= alongside the inspector / view-
pane post-command hooks (org-air-view.el ~L890; org-air-project.el ~L1330).
Because it only moves point (no re-render) and short-circuits on the common
"already on the item" case, it is cheap in =post-command-hook=.

*** Interaction with R21-1 / R21-2 / the inspector follow
- R21-2 already lands org-air motion on the title; R22-2b extends that to
  NATIVE motion + mouse without rebinding every key.
- R21-1 restores the user's SAVED column on a re-render; that column is within
  the item span (propertized), so =--normalize-point= is a no-op after it — no
  col-0 snap reintroduced.
- The inspector / view-pane follow reads the row via =--view-pane-thing-at-
  point=, now line-based, so it follows the row regardless of point's column and
  never fights the normaliser (which runs first / is idempotent).

** Byte / batch contract
=--row-property= and =--normalize-point= read text properties and move point
only; they touch no buffer text and are inert under =noninteractive= (the hook
is not installed in batch; the cold render still ends on =--goto-first-item=,
unchanged).  Every board + project byte golden is byte-identical.

* R22-1 — priorities A–E: only #A renders a marker; #B–#E render nothing [BUG]

** Reproduction — three stacked faults; #A is the only one that survives them
The user wants priority markers for #A THROUGH #E; today only #A shows a small
coloured square.  Measured (source, =load-prefer-newer=):
#+begin_src text
org-air-priority-show       = (65)            ; = '(?A) — ONLY A is "shown"
org-air-priority-colors keys = (65 66 67)     ; = A B C — no D, no E
--priority-face for D        = org-air-face-priority-c   ; D falls into the `_ catch-all
--priority-face for E        = org-air-face-priority-c   ; E too
#+end_src
*Fault 1 (the dominant one).*  =org-air-view--priority-slot= (org-air-view.el
L1478) and the inline =--insert-item= branch (L2125) gate the square on
=(member char org-air-priority-show)=.  With =org-air-priority-show= = ='(?A)=
ONLY #A passes; #B–#E render the blank 2-col slot — even though their priority
char IS computed.  This is why "only #A shows".
*Fault 2.*  =org-air-priority-colors= (L551) and =org-air-view--priority-face=
(L1416, a =pcase= with cases =?A/?B/?C= and a =_= → =priority-c=) only know
A/B/C.  So #D and #E would draw with C's yellow-green colour/face even once
shown — no distinct hue.  org-air-faces.el L370/381/391 declare only =org-air-
face-priority-a/-b/-c=.
*Fault 3 (subtle, found by reading the parser).*  Even after showing #B,
=[#B]= records NO priority at all.  =org-air-query--item-at-point= (org-air-
query.el L95) computes =:priority= as
#+begin_src elisp
(let* ((heading (org-get-heading t t nil t))
       (priority (org-get-priority heading))
       (default-priority (org-get-priority "")))
  (and priority (/= priority default-priority) priority))
#+end_src
The =(/= priority default-priority)= test means to drop the "no cookie" case
(a cookie-less heading returns the DEFAULT priority value), but Org's
=org-default-priority= is =?B= — so an EXPLICIT =[#B]= has =priority ==
default-priority= and is suppressed to nil.  Measured on bare headings (default
Org, =org-priority-lowest= = ?C):
#+begin_src text
heading [#A] -> get-priority 2000  default 1000  recorded 2000  char A
heading [#B] -> get-priority 1000  default 1000  recorded nil   char nil   <-- #B LOST
heading [#C] -> get-priority    0  default 1000  recorded 0     char C
heading [#D] -> get-priority -1000 default 1000  recorded -1000 char D
heading [#E] -> get-priority -2000 default 1000  recorded -2000 char E
#+end_src
So #B is doubly invisible (Fault 1 hides it, Fault 3 erases its value).  Note
#D/#E DO parse and =org-air-view--priority-char= (L1021,
=(- org-priority-lowest (/ priority 1000))=) recovers them correctly even with
=org-priority-lowest= = ?C — so NO change to =org-priority-lowest= is needed;
the gap is purely show-set + colours/faces + the #B parser bug.

** Decision — show A..E, add D/E colours + faces, and record explicit #B
*** (1) Show all five by default
=org-air-priority-show= default → ='(?A ?B ?C ?D ?E)= (the brief: "up to #E").
Keep the blank-slot pixel-lock: =--priority-slot= still reserves the fixed
2-col slot and renders two blanks when the row has no shown priority, so all
titles stay V6-aligned.
*** (2) Extend the hot→cool colour ramp to D and E
=org-air-priority-colors= gains D and E, continuing A=hot … E=coolest:
#+begin_src elisp
(defcustom org-air-priority-colors
  '((?A . ("#D32F2F" . "#BF616A"))   ; red      (hot)
    (?B . ("#E0631E" . "#D08770"))   ; orange
    (?C . ("#689F38" . "#A3BE8C"))   ; yellow-green
    (?D . ("#0097A7" . "#88C0D0"))   ; teal/cyan  (cool)
    (?E . ("#5C6BC0" . "#7E8CC0")))  ; indigo     (coolest)
  ...)
#+end_src
(The exact D/E hues are a tuning detail for the test seat; the contract is a
distinct, progressively cooler hue per level, reconciled with the faces below.)
*** (3) Faces + face resolver for D and E
Add =org-air-face-priority-d= / =org-air-face-priority-e= in org-air-faces.el
(mirroring the A/B/C blocks: 256-colour light/dark fg from the ramp + a TTY
=t= inherit — D inherits a calm faded/cool tier, E the coolest), and extend
=org-air-view--priority-face= (L1416) so it returns them:
#+begin_src elisp
(defun org-air-view--priority-face (char)
  (pcase char
    (?A 'org-air-face-priority-a) (?B 'org-air-face-priority-b)
    (?C 'org-air-face-priority-c) (?D 'org-air-face-priority-d)
    (?E 'org-air-face-priority-e) (_ 'org-air-face-priority-c)))
#+end_src
=--priority-char= (L1021) already yields A..E unchanged; the svg square
(=--svg-priority-square= L1448) is a pure function of (colour, cw, ch) so it
draws the D/E hue automatically once the colour/face exist — no svg change.
*** (4) Record an explicit #B (fix Fault 3 at the source)
Detect the explicit cookie via the priority regexp instead of the value-equals-
default heuristic, so =[#B]= is recorded while a cookie-LESS heading stays nil:
#+begin_src elisp
:priority (let ((heading (org-get-heading t t nil t)))
            (when (string-match org-priority-regexp heading)   ; explicit [#X] present
              (org-get-priority heading)))
#+end_src
Measured: this records A/B/C/D/E for explicit cookies and nil for no-cookie
headings (verified on the bare-heading fixture above; =org-priority-regexp=
group 2 is the letter, A..E all match).  The high-priority bucket gate
(org-air-classify.el L129, =>= get-priority "[#A]"=) is unchanged — still only
#A counts as high-priority, which is correct.

* R22-4 — scope vs filter clarity: both rail blocks say "all items" [POLISH]

** Reproduction — the two roles are already separated in BEHAVIOUR but not in WORDS
The user has asked three times to tell SCOPE from FILTER because they LOOK
identical.  Measured (source) — the rail's =org-air-view--insert-rail-filters=
(org-air-view.el L2490) renders, with nothing active:
#+begin_src text
Filter
  No filters · all items          <- says "all items"
Scope
  all items                       <- ALSO says "all items"
#+end_src
and the mode-line (=--mode-line-content= L817) reads
=org-air · N items · no filter · scope all items= — again "all items" twice.
The canonical meaning IS already implemented distinctly:
- SCOPE (=s=) is a purely STRUCTURAL source lens — =org-air-scope= (L4942)
  offers =all / @group / ⌂ file= ONLY; the =#tag= option was DROPPED in R19-4d
  (the comment at L4951 is explicit: "Scope is a purely STRUCTURAL lens now …
  Tags belong entirely to =/=").  So the brief's option (iii) "fold tag-scope
  into filter" is ALREADY shipped — scope no longer overlaps tags.
- FILTER (=/=) is the live tag lens — AND/OR (=M-/=), =\\= clears.
The ONLY remaining confusion is WORDING + visual: both empty-states say "all
items", and =--scope-label= (L2482) returns the bare "all items" with no cue
that it is the SOURCE/DATASET selector.  So this is a labelling fix, not a
behaviour change.

** Decision — name SCOPE as the SOURCE/DATASET (with a count); FILTER as the lens
Make each block self-evident by VERB + a count, and give them distinct visual
language.  No behaviour change (the fold is done).

*** (1) FILTER block = the live tag lens; empty-state stops claiming the dataset
- Empty: =none= (faded) — drop "· all items" (the dataset is Scope's job).
- Active: the tag PILLS joined by the combinator word (=#a AND #b=), then
  =Match: AND   M-/ toggles · \\ clears= — unchanged, already clear.
- When a filter narrows the loaded set, append =N of M shown= (visible-after-
  filter of loaded-under-scope) so the lens reports what it removed.
- Visual: keep the lens = tag PILLS (the existing svg tag idiom).

*** (2) SCOPE block = the SOURCE selector, named and counted
- Rename the rail header =Scope= → =Source= (the word the user keeps reaching
  for) — it is a SOURCE/DATASET selector, not a second filter.
- Value reads as a dataset + a count:
  - no scope: =all items · M loaded=
  - group:    =@group · M loaded= (=M= = items the org-ql scope returned)
  - file:     =⌂ file.org · M loaded=
  then =s changes · S clears= when a scope is active.
- Visual: a DATASET chip — a distinct leading glyph (=⊟= / the source glyph) and
  the dataset face (e.g. =org-air-face-group=/the bumped origin face), visibly
  different from the filter's tag pills, so "source vs lens" reads at a glance.
The verbs in the value separate too: SOURCE teaches =s/S= (re-runs org-ql),
FILTER teaches =/ \\ M-/= (instant, no reload) — so the distinction (reload vs
live) is taught in-line.

*** (3) Mode-line + Actions hint
- Mode-line: =org-air · N items · filter <none|#a AND #b> · source <all items|⌂
  file.org>= — relabel =scope= → =source= and =no filter= → =filter none=, so
  the two segments no longer both read "all items" (=--mode-line-filter-text=
  L807 and the =scope= segment L831).
- Actions rail hint: distinguish the two verbs explicitly — =/ filter (tags)= and
  =s source (file/group)= — instead of a bare =s scope=.

** Byte / batch contract — a SMALL, deliberate rail/mode-line re-bless
