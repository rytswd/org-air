* R26-8 — first-load "Loading…" hang: honest async (cache-first + chunked refresh) [FEATURE — meatiest]

** Reproduction + measurement — the hang is the synchronous scan, and it is NOT inevitable
The user asks whether the freeze is just "how Emacs is".  It is not.
Today's cold path (=org-air-view=, org-air-view.el:5227, the R20-1 design):
paint the chrome skeleton, =redisplay=, then run the WHOLE =org-ql= query
SYNCHRONOUSLY — the frame is visible but Emacs is unresponsive until the
scan returns.  Measured on the real Air repo tree: *cold scan 1.432s over
69 files / 1493 headings; warm re-scan 0.019s* — the user's own board is
the same order of magnitude, so every cold start freezes input for one to
several seconds.  The 75× cold/warm gap is the tell: the DATA barely
changes between sessions; we re-derive it from scratch every time.
History honoured: R19-1's naive async was fragile (partial paints, timer
leaks), R20-1 went sync-fast-paint for robustness.  This design keeps
R20-1's robustness properties and removes the synchronous wait.

** Options evaluated (pick + justify)
1. *Persist the scan cache to disk; paint last-known board instantly* —
   startup cost becomes "read one =.eld= file" (tens of ms for ~1500
   items); needs serialisation + invalidation.  CHOSEN.
2. *Refresh via chunked org-ql slices on an idle timer* — keeps the UI
   responsive during the real scan; slices are small (measured ≈21ms/file
   ⇒ a 3-file slice ≈ 60–70ms, well under perception); in-process, no
   moving parts beyond one timer.  CHOSEN (the refresh half of 1).
3. *Child Emacs process streaming results* — true parallelism, but: the
   whole org/org-ql config (todo keywords, customs) must be replicated
   into the child; results cross a serialisation boundary ANYWAY (so we
   need option 1's serialiser regardless); version/config skew and orphan
   processes are new failure classes; and the win over slicing is ~1
   second of background latency on a board that is ALREADY painted.
   REJECTED for now — the option-1 serialiser deliberately leaves this
   open as a future transport.
Decision: *1 + 2* — cache-first paint, chunked in-process refresh.

** Decision — the cache
#+begin_src elisp
(defcustom org-air-cache-file
  (expand-file-name "org-air/board-cache.eld"
                    (or (getenv "XDG_CACHE_HOME") "~/.cache"))
  "Persisted board scan cache; nil disables persistence entirely.")
#+end_src
- Contents (one printable plist): =:version= (bump ⇒ discard), =:key=
  =(org-air-files org-air-inbox-file)= (mismatch ⇒ discard), =:mtimes=
  alist FILE → mtime captured per file AT SCAN TIME, =:items= the item
  structs with the MARKER slot serialised as =(FILE . POS)= (markers do not
  print; titles are already =substring-no-properties=; org-timestamp
  objects are plain sexps).  Written ATOMICALLY (temp file + rename) after
  every completed scan; read errors / corrupt file / version / key
  mismatch ⇒ silently treated as "no cache" (cold path).  Never read or
  written under =noninteractive=.
- Marker hydration: a small resolver =org-air-view--item-pos= accepts a
  live marker OR the =(FILE . POS)= cons (the pane already accepts file
  strings); visit/triage on a cache-cold item hydrates on demand.  The
  live scan REPLACES cached items on completion, so cons markers are a
  startup-window state, not a steady state.

** Decision — the state machine (per board buffer)
#+begin_src text
        ┌──────────── cache miss/invalid ────────────┐
COLD ───┤ paint skeleton · header "loading 0/N files" ├─→ REFRESHING
        └─────────────────────────────────────────────┘
CACHED ─ paint FULL board from cache instantly
   │      · all mtimes match  → FRESH        (no scan at all)
   │      · any mtime differs → REFRESHING   (header "stale · refreshing…")
REFRESHING ─ idle-timer slices scan `org-air-refresh-files-per-slice'
   │         (default 3) files each via `org-air-query-items-in-files'
   │         (the R19-1 seam, already in the tree); accumulate privately;
   │         UI fully interactive; slice progress in the header count slot
   ├─ all slices done → SWAP items ONCE, re-render, clear marker,
   │                    write cache → FRESH
   ├─ a slice errors  → keep the painted board, state FAILED,
   │                    header "stale · refresh failed (g retries)"
   └─ `g' pressed     → cancel pending slices (token), restart from the
                        current file list — g IS this same path
FRESH ─ `g' / after-save hook → REFRESHING (mtime fast-path applies)
#+end_src
Robustness rules (the R19-1 lessons, made law):
- *No partial paints*: slices accumulate into a private list; the board
  repaints exactly ONCE per refresh (swap + =--render-current= with point
  preserved).  No mid-scan reflow, ever.
- *Token-guarded timers*: one buffer-local incrementing refresh token;
  every timer callback checks it and self-cancels when stale; kill-buffer
  cancels outright; =unwind-protect= clears the in-flight state so the
  buffer can never wedge (the R20-1 guarantee, kept).
- *Timers never touch windows* — they only build data; rendering happens
  through the same =--render-current= the resize path already trusts.
- *Guards during REFRESHING*: the board is USABLE (that is the point);
  triage verbs on an item whose source file's mtime changed since the
  cache snapshot soft-error ("still refreshing this file…") — positions in
  UNCHANGED files are valid by construction (mtime match).
- =--loading-guard= / the modal "Still loading" user-error retires for the
  CACHED path (nothing modal remains); COLD keeps the skeleton but input
  stays live (the guard protects only data-dependent verbs, as today).

** Byte / batch contract
=noninteractive= takes the EXACT current synchronous path: no cache read,
no cache write, no timers — every golden and the gate's runtime are
byte-/behaviour-identical.  Interactively, the header's count slot gains
the =stale · refreshing…= / progress text while refreshing (display-only,
transient); no golden captures it.

** Testability (R26-8) — deterministic, no sleeping in the gate
The slice runner is a named function (=org-air-view--refresh-run-slice=)
the timer schedules; ERTs call IT directly in a loop — the whole machine is
testable synchronously with zero timers and zero waits:
- ERT (cache round-trip): scan the fixtures, write the cache to a temp
  =org-air-cache-file=; fresh buffer + cache read ⇒ the painted board is
  byte-identical to the live-scan board (marker slots cons-hydrated).
- ERT (instant stale paint + marker): cache present, one fixture file
  touched ⇒ first paint equals the CACHED board, header contains
  =stale · refreshing=; running slices to completion repaints with the new
  item and CLEARS the marker.
- ERT (mtime fast-path): cache present, nothing touched ⇒ FRESH with NO
  slice ever scheduled (assert the file queue is empty).
- ERT (interleaving): between slices, filter/sort/motion commands run and
  the board does NOT repaint mid-refresh (single-swap rule); the swap
  preserves point per =--save-position=.
- ERT (failure honesty): a slice stubbed to signal ⇒ board text unchanged,
  header shows =refresh failed=, =g= restarts and completes.
- ERT (corrupt cache): garbage cache file ⇒ cold path, no error surfaced.
- ERT (batch purity): under =noninteractive= with a cache file present,
  the render never reads it (goldens already enforce byte-identity; add an
  explicit "cache file untouched" access assertion).
- ERT (token safety): =g= mid-refresh cancels the old token — a late stale
  slice callback is a no-op (call it manually with the old token).
