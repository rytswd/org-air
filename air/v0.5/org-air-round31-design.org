* R31-1 — INLINE two-pane + header x-overflow: close the last raw-column seam, lock the inline contract, guard the glyph-advance class [BUG / HARDENING + TEST]

** Reproduction — the inline width math is already correct
=org-air-view--render= dispatches the orientation, then re-measures the
host width ONLY under =side-window= (=org-air-rail--host-width=, already
usable-columns per R29-1).  For =two-pane= (INLINE) it keeps
=width= = =org-air-view--render-width= untouched.
=org-air-view--two-pane-body= then splits:
- =rail-width= = =org-air-view--rail-width width= (28/32/42 tier),
- =divider= = =org-air-view--divider= (=" │ "=, display width 3),
- =item-width= = =(max 20 (- width rail-width 3))=,
and =org-air-view--compose-columns= zips =item(item-width) │
rail(rail-width)= so each row = =item-width + 3 + rail-width= = =width=
exactly (when not clamped).  The header is composed by
=org-air-view--render-lines width= -> =org-air-view--insert-banner=,
which justifies to =w= = render-width with a reserved trailing column
(S7).  Since =width= = =org-air-layout-current-width= =
=org-air-layout--usable-columns=, every inline line is exactly usable
wide.  The sweeps above confirm it at every width; the live fringe-less
sim confirms it end-to-end (79 in an 80-body window, fits).

The board entry =org-air-view= =pop-to-buffer='s the dashboard BEFORE
the first =org-air-view--render= ("Display the buffer first so width
derivation measures the window that actually shows the dashboard (U1)"),
so even the first inline paint measures the real window and takes the
usable-columns branch — never the =frame-width= fallback.

Why R29-1's own inline ERT already passed (and stays green):
=org-air-r29-1-fringeless-no-line-exceeds-usable= DID render the inline
two-pane and assert every line <= usable — and it PASSED, because it is
true.  R29-1 did not "miss" inline; inline was correct because it flows
through the same render-width primitive.  What R29-1 lacked is an inline
assertion pinned to the CONTRACT columns (header ends at usable-1;
divider column constant) so a future refactor of the two-pane split or
the header budget cannot silently reintroduce a fringe-less inline
overshoot.  R31-1 adds exactly those locks.

** Root cause of the residual raw-column risk — Seam A
=org-air-layout-current-width= (org-air-layout.el) resolves the
displaying window, then falls back:
#+begin_src elisp
(cond
 ((window-live-p window) (org-air-layout--usable-columns window))
 ((window-live-p (selected-window))
  (org-air-layout--usable-columns (selected-window)))
 (t (frame-width)))            ; <<< raw columns, NOT usable
#+end_src
The final =(frame-width)= is the ONE remaining term in the whole chain
that is not reduced by the fringe-less continuation-glyph column.  It is
reached only when there is neither a window showing the buffer nor a
live selected window (a minibuffer-only or during-startup frame) — so
the live board never composes against it, and no golden exercises it.
But it is the last unguarded seam of the R29-1 class, and in a
fringe-less GUI it yields exactly usable+1.  Leaving it raw means the
class is "fixed everywhere the tests look" but not CLOSED.

** Root cause of the screenshot glyph — Seam B (not a width-math bug)
The status band and the date/meta separators use East-Asian
*Ambiguous-width* glyphs (=·= U+00B7 in the count/scope separators; =✕=,
=…=, =↑=, =↓=, =→=, =↻=).  =string-width= / =char-width= report 1 for
each.  The renderer composes AND measures with =string-width=, so it is
self-consistent under ANY =char-width-table= regime — forcing those
chars to width 2 keeps every composed line exactly the render width
(the padding shrinks to compensate; verified).  The line therefore fits
usable whether ambiguous glyphs are 1 or 2 columns, PROVIDED the frame
paints them at their declared =char-width=.  The only way the user sees
a continuation glyph is a FONT whose glyph ADVANCE exceeds the declared
=char-width= (a font/config property Emacs cannot derive from
=char-width-table=).  That is not an org-air width-math defect and
cannot be fixed by threading usable-columns; the honest remedies are (a)
ship glyphs that are unambiguously single-width, and (b) document the
=char-width-table= / language-environment config for users whose fonts
paint ambiguous glyphs wide.

** Decision — close Seam A, lock the inline contract, guard Seam B
1. *Seam A (one-term source change, byte-invisible).*  Route the last
   fallback through the R29-1 primitive.  When there is no live window
   at all there is no window to measure usable columns FROM, so the
   honest closure is: prefer the selected window's usable columns
   (already the second branch); for the final fallback, reduce the
   raw frame width by the fringe-less reserve the same way
   =window-max-chars-per-line= would — i.e. return
   =(max 1 (1- (frame-width)))= on a graphical frame (no window to
   query, so mirror the -1 the continuation column costs), and plain
   =(frame-width)= on a TTY/batch frame (no reserve).  A tiny helper
   =org-air-layout--usable-frame-columns= keeps the graphic/TTY split in
   ONE place beside =org-air-layout--usable-columns= (no fork; same
   contract, frame tier).  Result: NO composition, in ANY orientation
   or frame state, can be sized to usable+1.  Batch/TTY unchanged
   (=frame-width= there has no reserve, so the value is identical).
2. *Lock the inline contract (executing ERTs, extend R29-1's matrix).*
   Add inline-mode assertions pinned to the CONTRACT columns, not just
   "<= usable": the header ends at exactly render-width-1 with a blank
   final column, every two-pane row equals render-width, and the
   divider column is identical on every composed row.  These pass on the
   current code (they document + freeze the already-correct behaviour)
   and FAIL if a future two-pane/header refactor drifts fringe-less.
3. *Guard Seam B (glyph-advance class).*  A pure ERT asserting every
   status/separator/legend glyph org-air emits has =char-width= 1 (so
   the renderer's budget can never disagree with a correctly-configured
   frame), plus a compose-invariance ERT proving the header still fits
   usable when =char-width-table= marks the ambiguous chars WIDE (the
   self-consistency property).  Document the font/char-width remedy in
   the manual for the residual font-advance case.  No glyph is changed
   (V6 / goldens hold); if a future round wants VS15 text-presentation
   selectors that is a separate, golden-moving decision, explicitly
   deferred.

Explicitly out of scope: changing any glyph, any column width, or any
golden (V6 pixel-lock, byte-identical batch); font-advance detection
(Emacs owns =char-width-table=; org-air inherits it).
