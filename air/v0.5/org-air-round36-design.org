* Scope of this document
Round-36 DESIGN doc — ONE item, the header overflow the user has now
diagnosed precisely and that every fix since R29 kept missing because
they all chased the *usable-columns SOURCE* (R34 finally pinned that to
=window-body-width=) and never MEASURED THE ACTUAL COMPOSED HEADER

- *R36-1* HEADER TRAILING-WHITESPACE OVERFLOW.  The board header AND the
  loading-skeleton header compose a line whose content is right-aligned
  to =window-body-width − 1= and then a RESERVED TRAILING SPACE (the S7
  "one-column right margin", the mirror of the visible left margin) is
  appended so the line FILLS the whole body — its LAST column is a blank.
  On the user's real frame that final blank column is the one drawn OFF
  the right edge, so the user sees a left margin but "NONE on the RIGHT —
  in fact … a TRAILING EMPTY SPACE that's OFF the window", and the =↦=
  continuation/truncation arrow past the right content.  [BUG —
  release-blocker; the R29/R31/R33/R34 miss]

  USER (exact words, GUI): "there is some padding on the LEFT, but NONE
  on the RIGHT — in fact, on the right, there is a TRAILING EMPTY SPACE
  that's OFF the window", with the =↦= arrow still shown past the right
  content.  The screenshot is the LOADING SKELETON header ("Wed 08 Jul ∙
  loading 3/50 files"), so the loading chrome overflows too.

* Measured baseline (reproduction harness — the miss, finally MEASURED)
The prior rounds asserted on the =usable-columns= VARIABLE and never on
the composed line, so they could not see this.  Measuring the literal
banner string at several =window-body-width= values (headless, no GUI)
shows the exact defect:

#+begin_src text
  w=40  NORMAL  len=40  string-width=40  ends-in-whitespace=t  last8="0 items "
  w=80  NORMAL  len=80  string-width=80  ends-in-whitespace=t  last8="0 items "
  w=120 NORMAL  len=120 string-width=120 ends-in-whitespace=t  last8="0 items "
  w=191 NORMAL  len=191 string-width=191 ends-in-whitespace=t  last8="0 items "
  w=191 LOADING len=191 string-width=191 ends-in-whitespace=t  last8="0 files "
#+end_src

Two facts, both from the literal string:
1. =string-width= equals =w= EXACTLY (it is NOT a wide-glyph or a
   length>width overshoot — R34 already pinned =w= = =window-body-width=,
   so the composed line fills the body precisely).
2. The line ALWAYS ENDS IN A TRAILING SPACE.  The right status is
   justified so its last *visible* glyph sits at column =w−2=, and column
   =w−1= (the final body column) is a RESERVED BLANK.

So the excess the user sees is NOT extra content and NOT a wide glyph —
it is the *reserved right-margin column itself*, emitted as literal
trailing whitespace at the very last column of the body.  The left margin
("  " before "org-air") sits INSIDE the window; its intended mirror on
the right is drawn AT the last body column, which on the user's frame is
the column that falls off the right edge → "trailing empty space that's
OFF the window", and the =↦= continuation glyph over it.

** Where it is emitted (single choke point)
=org-air-view--insert-banner= (org-air-view.el ~1976) composes the line:

#+begin_src emacs-lisp
;; Budget for the status: window minus the left token, a >=2-col
;; gap, and the reserved one-column right margin.
(budget (- w (string-width left) 2 1))      ; <- the extra `1' reserves a right column
...
;; Justify with a trailing space so the status ends at W-1 and the
;; final column W is always blank (the reserved margin).
(line (org-air-view--justify left (concat right " ") w))   ; <- the appended " "
#+end_src

The =(concat right " ")= appends the reserved margin space; =budget='s
trailing =1= keeps room for it.  =org-air-view--justify= then pads
=left + middle-padding + (right " ")= to EXACTLY =w= via
=org-air-view--pad-to=, so the line always fills the body and always ends
in that blank.  This is the S7 hack: "so a zero-fringe GUI never draws a
continuation glyph over it".

** Why the S7 trailing-space hack is now BOTH redundant AND harmful
R34 made =org-air-layout--usable-columns= fringe-aware: on a *zero-fringe*
GUI it already returns =window-body-width − 1=, reserving the last body
column for the continuation glyph at the WIDTH source.  So the header no
longer needs to reserve a column by hand — R34 reserves it upstream.  The
hand-reserved trailing space is therefore:
- *Redundant* on zero-fringe (R34 already gives the spare column).
- *Harmful* on the fringed frame (R34 gives usable = full body, so the
  hand-reserved blank lands on the LAST body column, which the fringe/edge
  then clips — exactly the user's report).

** The correct pattern already exists in-tree (day-header)
=org-air-view--render-day-pane= (org-air-view.el ~4152) composes its own
full-width header with the SAME =org-air-view--justify= primitive but
with NO reserved trailing space:

#+begin_src emacs-lisp
(org-air-view--justify
   (concat (org-air-view--margin) …day-nav…)
   (propertize (format "%d items" total) 'face 'org-air-face-faded)
   width)                       ; right = "N items", NO trailing " "
#+end_src

Its right status' last glyph sits at column =width−1= (the true last
column) with no trailing blank.  So the banner is the *sole* offender;
the fix makes the banner follow the day-header's already-correct pattern.

** Confirmed: board header and loading skeleton SHARE the composer
=org-air-view--render= (~6131) and =org-air-view--render-loading= (~6453)
BOTH insert the header through =org-air-view--insert-banner= (the loading
path passes =items= = nil and relies on =org-air-view--loading= /
=org-air-view--refresh-state= for the "loading I/N files" count slot).  So
ONE fix in =insert-banner= corrects BOTH headers.  The measured LOADING
row above is byte-for-byte the user's screenshot chrome.

* R36-1 — remove the reserved trailing margin; right-align the status to the last usable column [BUG]
** Decision — the banner's right status ends at column =usable−1= with NO trailing pad; the left margin is counted INSIDE the width, never mirrored as trailing whitespace
The header line's TOTAL composed width (left margin + content) must be
=<= window-body-width= with NO trailing whitespace past the content's
right edge.  Concretely, in =org-air-view--insert-banner=:

1. Drop the appended margin space: compose =(org-air-view--justify left
   right w)= (NOT =(concat right " ")=).  The right status' last glyph
   then lands on column =w−1= — the true final body column — and
   =org-air-view--justify='s =pad-to= adds ZERO trailing padding (the
   middle gap already absorbs the slack), so the line does not end in
   whitespace.
2. Drop the reserved column from the budget: =budget = (- w (string-width
   left) 2)= (remove the trailing =1=).  The =>=2= keeps the minimum gap
   between the left token and the right status; no right column is
   reserved.
3. The left margin ("  " inside "  org-air") stays counted INSIDE =w= (it
   always was); it is NEVER mirrored as a trailing right blank.

Why this fixes BOTH geometries WITHOUT reverting R34:
- *Fringed frame (this user):* R34 gives usable = body (e.g. 191).  The
  status' last glyph now sits at column 190 (the last body column) with
  no trailing blank → nothing to draw off the right edge, no phantom
  margin column, no =↦=.
- *Zero-fringe GUI:* R34 gives usable = body − 1.  The header composes to
  body−1, ending in real content at column body−2, leaving the last body
  column spare for the continuation glyph — the S7 goal, now provided by
  R34's WIDTH source (not the hand-reserved space).
- *TTY / batch / mock:* usable = =window-body-width= as today; the ONLY
  change is that the banner no longer appends a trailing space (goldens
  re-baselined, below).

R34's =org-air-layout--usable-columns= guard is preserved verbatim — this
round does NOT touch the width source, only the composer that consumes it.
